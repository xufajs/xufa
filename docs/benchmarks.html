How they are measured

  • Every library runs every round in a process of its own, the libraries taking turns, and the median of the rounds is shown (5 rounds unless said).
  • The databases are local servers: PostgreSQL 18 and MongoDB on the same machine, and SQLite in memory.
  • Machine: Intel Core i7-13700H (20 threads), Windows 11, Node.js 22.21.1. HTTP also on Linux on the same machine (Ubuntu 26.04 on WSL2, Node.js 22.21.1), whose numbers it shows first.
  • Colors: the bars and badges of xufa are green where it is ahead by 5% or more, red where it is behind by as much, and grey in between, where the difference is within what a run varies.
  • ⚠ marks a result whose rounds are more than 10% apart: the machine was busy, so read it as approximate. A Windows desktop is a noisy place to measure; the ratios hold better than the absolute numbers.
  • A process of its own, for a reason: what a process does before its first request can make every request after it slower, for as long as it runs. When thousands of objects get properties of their own names first (as the first compile of ajv does, with its meta-schema), V8 optimizes the request path worse: about a third fewer requests a second on fastify, and a seventh fewer on @xufa/http, on every route, though the code that did it never runs again. The same work after the first requests costs nothing. So no server inherits what another did, and xufa's packages do no such work before traffic (the README of the repository has the guideline). V8's profiler (--cpu-prof) puts every process in the slow state, so it cannot show this: compare runs, each in a process of its own.

Where the database does the work (an update of thousands of rows, a sort of a big table), the libraries are about even: the time is the database's. Where the library does the work (building queries, making objects, the round trips of the driver), xufa is from 2 to 18 times faster. @xufa/sequelize is faster than the ORM's own API at findByPk: it reads one row, where the ORM's get() asks for a few to make sure only one matches (as Django does).

What makes the difference: queries are prepared the second time their text runs, values are read and sent in the binary format, and queries are pipelined, so 64 queries at once do not wait for each other on a connection. In the process, xufa is ahead in every scenario: 1.96× on large JSON responses (written as bytes), 1.21× on bodies parsed and validated, and from 1.06× to 1.24× on the rest, level with node:http answering by hand on hello: xufa writes the head of most responses itself (fastHead), where Node.js checks and assembles every header. Over the loopback, the socket and the HTTP parser of Node.js are a part of each response that is the same for both, so the frameworks come closer: from 1.02× to 1.66× where the rounds agree.

The rows of a child logger are what a server sees, its request.log being a child. There, a line costs about the same in both (1.00×), and so does a call at a disabled level, which V8 makes into nothing in both. pino's root logger is slower than its children (it has many properties of its own, and V8 keeps them as a dictionary): that is most of the difference on the rows of a root logger. A child is made at 1.05× pino: as in pino, its parent is its prototype, so it copies nothing but its bindings, written once when it is made; a logger set at a level has a prototype shared with every logger at that level, with the functions of the level. A line adds its level, made once for each level, and its time, made once a millisecond: Date.now() alone is close to half of the cost of a line on this machine.

The signatures are the same work, done by node:crypto; the difference is the key. jsonwebtoken tries a secret as a PEM key first, which throws (two thirds of the time of HS256), and parses a PEM key again on each call; @xufa/jwt does not try what has no -----BEGIN, and keeps the KeyObject of each key given as a string. Given a KeyObject, nothing is parsed by either, and they are even. Decoding, which verifying does first, parses the header once and splits the token once (jws does each two and three times). On Linux (bench/results/jwt-linux-2.md), where a key that fails to parse costs less, the gains are a little smaller: 3.78× and 4.12× for HS256, 1.63× and 1.71× for RS256, 2.60× and 1.45× for ES256, 1.34× for decoding.

Two differences, both in what a client sends, whose frames are masked. Without bufferutil, ws masks byte by byte in JavaScript, and @xufa/websocket from 384 bytes copies natively and masks 8 bytes at a time: about as fast as ws with bufferutil, with no native module to build (0.95× to 1.30× of it). And a masked frame is a copy of the message, which ws writes into a buffer allocated for it; @xufa/websocket uses the buffers of the frames already written again, as copying into new memory costs from 6 to 22 times more (on Linux, from 2 to 18). That is the gain of 16 KB with bufferutil too; at 1 MB the copy is a smaller part of the time. Small messages are not masked enough to tell, and with deflate zlib takes the time. Received, a message over several chunks of the socket is copied into a buffer of its own by both, as it is the application's.
