Overview Reference

@xufa/browser

Chrome and Edge, as installed on the machine, driven through the DevTools Protocol: pages, locators, the keyboard and the mouse, with the API of Playwright for what it has. No dependencies and no browsers to download. The browser tests of xufa (the admin, the page of @xufa/faults) and the crawler of these docs run on it.

Quick start

npm install --save-dev @xufa/browser
import { chromium } from '@xufa/browser';

const browser = await chromium.launch();
const page = await browser.newPage({ locale: 'en-US' });
await page.goto('http://localhost:3000/admin/');
await page.fill('#username', 'ada');
await page.click('button:has-text("Log in")');
await page.waitForSelector('text=Welcome');
const titles = await page.$$eval('li.book', (items) => items.map((item) => item.textContent));
await browser.close();

Launching

findBrowser() gives the browser it starts: CHROME when set, else Chrome, Chromium or Edge where they install themselves (Windows, macOS, Linux); null when there is none, so tests can be skipped: 

import { chromium, findBrowser } from '@xufa/browser';

describe.skipIf(!findBrowser())('the admin, in a browser', () => {
  let browser;
  beforeAll(async () => {
    browser = await chromium.launch();
  });
  afterAll(() => browser?.close());
  // ...
});
Option of launch()What it is
executablePathThe browser (findBrowser() by default).
headlessWithout a window (true).
argsMore arguments of the browser.
timeoutMs it has to start (30000).

Each launch has a profile of its own, removed when it closes. browser.newContext({ locale, viewport, timeout }) makes a context: its pages share cookies and storage, kept apart from those of other contexts. browser.newPage() makes a page in a context of its own, closed with the page.

Selectors

SelectorThe elements
li.book > a, h1, h2CSS, lists too.
li:has-text("emma")With the text anywhere inside, in any case.
:text("Next"), text=NextThe smallest elements with the text; quoted (text="Next"), all of it as written.
div:visibleThose that are seen.
role=button[name="Save"]By ARIA role (implicit or not) and accessible name.
#books >> .editThe next part, inside the elements of the one before.
li >> nth=-1One of them by index (from the end when negative).
li:not(:has-text("Dune"))These pseudo-classes inside :not, :is, :where and :has.

page.getByText(text) and page.getByRole(role, { name }) are locators of these.

Actions

await page.click('li:has-text("Emma") button');
await page.fill('#when', '2026-10-12'); // inputs, textareas, dates, contenteditable
await page.selectOption('#shelf', { label: 'Aisle B' });
await page.check('#done');
await page.press('#name', 'Enter');
await page.keyboard.type('Ada');
await page.keyboard.press('Control+a');
await page.mouse.move(100, 100);
await page.mouse.down();
await page.mouse.move(160, 130, { steps: 5 }); // a drag
await page.mouse.up();

An action waits for its element to be there, visible, enabled, still (the same box for two frames) and the one a click at its center would hit; then it acts as a user would, with input events of the browser. { force: true } skips the checks.

Locators

const books = page.locator('li.book');
await books.count(); // 2
await books.filter({ hasText: /^Dune/ }).locator('button').click();
await books.nth(1).getAttribute('class');
await page.locator('.edit').click(); // fails: strict, 2 elements

A locator finds its elements again each time it is used, so it outlives renders. Its actions are strict: they fail when the selector has more than one element.

Waiting

await page.waitForSelector('#cover', { state: 'detached' }); // attached, visible (default), hidden
await page.waitForFunction(() => document.querySelectorAll('.row').length === 10);
const [response] = await Promise.all([
  page.waitForResponse((res) => res.url().endsWith('/api/books') && res.ok()),
  page.click('button:has-text("Save")'),
]);
await response.json();
await page.waitForURL(/#\/books/);

page.goto() waits for load (or waitUntil), and gives the response of the document: null when only the #hash changes.

Events

page.on('console', (message) => console.log(message.type(), message.text()));
page.on('pageerror', (error) => problems.push(error.message));
page.once('dialog', (dialog) => dialog.accept('Ada'));
page.on('response', (response) => response.status() >= 500 && problems.push(response.url()));

Dialogs nobody listens to are dismissed. Resources that fail to load are console errors, as in DevTools.

Errors

A wait that runs out is a TimeoutError that says what it waited for and why it was not done, where the page was, and the line of the test that called it: 

TimeoutError: page.click("#save"): Timeout 3000ms exceeded (disabled), at http://127.0.0.1:3000/admin/#/Book/1
    at test/books.browser.test.js:42:16

XUFA_BROWSER_DEBUG=1 logs the messages of the protocol (bodies: with their params). page.setDefaultTimeout(ms), or the timeout of a context, changes the 30 seconds.

Coming from Playwright

import { chromium } from 'playwright-core' becomes import { chromium } from '@xufa/browser'. What it has is what xufa's tests and crawler use: the page and its waits, locators, the keyboard and the mouse, events, contexts with their locale and viewport, and PNG screenshots. Not there: Firefox and WebKit, frames, routing of requests, tracing, video, downloads and storage states. For end-to-end suites with fixtures and web-first assertions, see @xufa/test-web.

How it works

The browser is started with --remote-debugging-pipe: messages are JSON on two pipes, with no port and no WebSocket. Pages are targets attached in flat mode, contexts are browser contexts. The selector engine and the checks of actions are one function, sent to each document and run there. Launching takes about 250 ms.

TypeScript

Declarations in the package: Browser, BrowserContext, Page, Locator, Response, TimeoutError..., with the results of evaluate() and $$eval() inferred from their functions.
