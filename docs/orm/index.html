ORM

@xufa/orm (or xufa/orm) has models and QuerySets in the spirit of Django, on SQL and NoSQL databases, with no dependencies. The same models and queries run on every backend, and give the same results.

new Database({ backend: 'fs', dir: 'data' }); // data/<table>.json; layout: 'files' for data/<table>/<key>.json

The fs backend keeps the objects in files, for content, settings and small catalogs that live with the application, or where there is no database. Queries run in memory with everything the memory backend does; what changes is written after each operation, or when a transaction commits (nothing when it rolls back), and read back when the database connects. With layout: 'files' each object is a file, and only the objects that changed are written. Files are written to a temporary file and renamed; dates, bytes and bigints keep their type; encrypted fields are written encrypted. One process writes a folder (a lock file, .xufa.lock, refuses another one). With tenants or several databases, a collection can live in files while the others are in a database.

watch: true (or { delay }, 50 ms by default) reads again the files changed from outside while the database is open (edits by hand, a deploy, git pull): the collections whose files changed, or with layout: 'files' only the objects whose files were changed, added or removed. What changes while a transaction is open is read when it ends. onChange(tables) is called after, and the cached objects of those models are dropped; onError(err) is called when a file cannot be read (JSON half saved by an editor), and the data stays as it was until the file changes again. When the application writes a file before its change from outside is read, the two are merged by object: the objects changed only from outside keep that change, and an object changed on both sides keeps the application's, with an onError error of code XUFA_ORM_ERR_FS_CONFLICT (with table and keys). Only the objects that changed are serialized again, and with layout: 'files' only their files are written: about 0.5 ms an object on Windows (NTFS and the antivirus look at each new file) and 0.1 ms on Linux, so thousands written at once take seconds on Windows. 

new Database({
  backend: 'fs',
  dir: 'content',
  layout: 'files',
  watch: true,
  onChange: (tables) => console.log('changed', tables),
});

A quick tour

const { Database, Model, fields, or, F, Count, Sum } = require('@xufa/orm');

class Author extends Model {
  static fields = {
    name: fields.string({ maxLength: 100 }),
    email: fields.string({ null: true, unique: true }),
    createdAt: fields.datetime({ autoNowAdd: true }),
  };

  static options = { ordering: ['name'] };
}

class Book extends Model {
  static fields = {
    title: fields.string({ maxLength: 200 }),
    pages: fields.integer({ null: true, min: 1 }),
    author: fields.foreignKey(() => Author, { relatedName: 'books', onDelete: 'cascade' }),
  };
}

const db = new Database({ backend: 'sqlite', filename: 'app.db' });
db.register(Author, Book);
await db.connect();
await db.sync(); // creates the tables (or collections and indexes) that do not exist

const ada = await Author.objects.create({ name: 'Ada' });
await ada.books.create({ title: 'Notes', pages: 120 });

const books = await Book.objects
  .filter({ author__name__istartswith: 'a', pages__gte: 100 })
  .exclude(or({ title__contains: 'draft' }, { pages: null }))
  .selectRelated('author')
  .orderBy('-pages')
  .limit(10);
books[0].author.name; // 'Ada'

await Book.objects.filter({ author: ada }).update({ pages: F('pages').add(1) });
await Book.objects.values('author__name').annotate({ books: Count(), pages: Sum('pages') });

Models and options

A model is a class extending Model, with static fields and, optionally, static options:

OptionWhat it does
tableThe name of the table (the snake case of the class name by default). Dots are part of the name.
schemaThe schema of the table in PostgreSQL. SQLite names the table schema.table, MongoDB the collection.
orderingThe default order of its QuerySets: ['-createdAt', 'name'].
indexes[['a', 'b'], { fields: ['c'], unique: true }]. In SQL, condition makes a partial index: { fields: ['c'], unique: true, condition: '"deleted" IS NULL' }.
abstractA parent whose fields its children get; it has no table. fields.extend(Parent, { ... }) writes them for TypeScript.
primaryKeyThe fields of a composite primary key, or false for a model without one (see Primary keys).
fillfactorPostgreSQL, 10 to 100: room left in the pages of the table for the new versions of updated rows. Updates of tables updated often get about twice as fast when they change no indexed column.
cachetrue or { ttl, indexes }: get() by key answered from a cache (see Caches).
databaseThe database of the model, with Databases.

Every field takes null, default (a value or a function), unique, index, primaryKey, choices, column and validate (rules of the value: functions or expressions that give a message, or false, when it is not valid; see Validation rules). In SQL databases a field can also say its column exactly: sqlType ('VARCHAR(255)') and dbDefault (a DEFAULT of the column).

datetime and date take PostgreSQL's infinite dates as Infinity and -Infinity (or those words as text), after and before every other date. SQLite keeps them as the texts infinity and -infinity, which sort the same way; MongoDB has none and refuses them.

Arrays, hstore, geometries

These fields are native types of PostgreSQL. The other backends store them too, as JSON text (SQLite) or documents (MongoDB), so the same models run everywhere. 

class Place extends Model {
  static fields = {
    tags: fields.array(fields.string({ maxLength: 20 })), // VARCHAR(20)[]
    attributes: fields.hstore({ null: true }), // HSTORE: { wifi: 'yes', seats: '40' }
    location: fields.geometry({ shape: 'POINT', srid: 4326 }), // GEOMETRY(POINT,4326)
    area: fields.geography({ shape: 'POLYGON', null: true }), // GEOGRAPHY(POLYGON)
  };
}

await Place.objects.create({
  tags: ['cafe', 'quiet'],
  attributes: { wifi: 'yes' },
  location: { type: 'Point', coordinates: [-3.7038, 40.4168], crs: { type: 'name', properties: { name: 'EPSG:4326' } } },
});
await Place.objects.filter({ tags: ['cafe', 'quiet'] }).count(); // arrays and maps are compared as wholes
  • Arrays, as Django's ArrayField: their items are checked by the field given (null items are kept). Arrays of hstore, JSON or ranges work too.
  • hstore, as Django's HStoreField: values are strings or nulls (numbers and booleans are taken as their text). The database needs the extension hstore.
  • Geometries of PostGIS are GeoJSON values; their SRID is their crs. They are written as EWKT and read back from PostGIS's EWKB. A value without a crs is stored without an SRID. Coordinates must be numbers: text that is not one is refused, not stored as 0. The database needs the extension postgis.

TTL indexes

An index of one datetime field with expireAfter (seconds, or text as '30d') is a TTL index, as MongoDB's: its objects expire that long after the date of the field (0: at the date). 

class LogEntry extends Model {
  static fields = { message: fields.text(), createdAt: fields.datetime({ autoNowAdd: true }) };

  static options = { indexes: [{ fields: ['createdAt'], expireAfter: '30d' }] }; // deleted 30 days after createdAt
}

class Session extends Model {
  static fields = { token: fields.string(), expiresAt: fields.datetime() };

  static options = { indexes: [{ fields: ['expiresAt'], expireAfter: 0 }] }; // deleted at expiresAt
}

app.register(orm.plugin, { database: db, sync: true, expire: true }); // db.expire() every minute while the app runs

MongoDB deletes them itself (expireAfterSeconds). In every backend, db.expire() deletes the objects that expired as QuerySets delete them, with their relations as onDelete says (MongoDB's own deletes do not), and db.startExpiry({ interval: '1m' }) or the plugin's expire call it on an interval. Objects that expired are found until they are deleted. In a cluster any process can do it; for tenants, start it in their setup.

Encrypted fields

fields.encrypted(field, options) keeps the values of a field encrypted in the database with AES-256-GCM: the objects have their values, and the database has text it cannot read ($xenc$1$<key id>$<iv>$<ciphertext>) in a TEXT column (and in the files of the fs backend). The memory backend keeps the values as they are. 

setEncryptionKeys({ keys: { k1: process.env.ENCRYPTION_KEY } }); // or XUFA_ENCRYPTION_KEYS='k1:<base64>'

class Patient extends Model {
  static fields = {
    name: fields.string(),
    ssn: fields.encrypted(fields.string({ maxLength: 11 })),
    email: fields.encrypted(fields.string(), { deterministic: true, unique: true }),
    history: fields.encrypted(fields.json(), { null: true }),
  };
}

await Patient.objects.create({ name: 'Ada', ssn: '123-45-6789', email: 'ada@example.com', history: { allergies: [] } });
const ada = await Patient.objects.get({ email: 'ada@example.com' }); // deterministic: found by equality
ada.ssn; // '123-45-6789'
// Patient.objects.filter({ ssn: '123-45-6789' }) throws: ssn takes isnull only
  • Keys are 32 random bytes (generateEncryptionKey()), in base64 or hex, by id: the first (or current) encrypts, all of them decrypt. Set them with setEncryptionKeys() or XUFA_ENCRYPTION_KEYS='k2:<base64>,k1:<base64>'.
  • Authenticated and bound to their column: a value changed in the database, or copied to another column or table, is refused with EncryptionError. context keeps the old 'table.column' after a rename.
  • Queries: encrypted fields take isnull, and no orders nor aggregates other than Count. With deterministic: true the same value gives the same text, so they also take exact and in and can be unique or indexed; the database can then tell which rows share a value, not what it is.
  • Rotating keys: add the new key as the current one, await reencrypt(Model), then remove the old one.
  • Encrypting a field with values: acceptPlaintext: true reads the values written before; migrate (the column becomes TEXT), reencrypt(Model), and remove the option.

Computed fields

A field with computed has the value it computes from the other fields of its object: an expression of @xufa/expression on them, or a function of the object. Its field (decimal, string...) gives the type of the value, which is coerced and validated as any other. 

class Line extends Model {
  static fields = {
    product: fields.string(),
    price: fields.decimal({ precision: 10, scale: 2 }),
    quantity: fields.integer(),
    discount: fields.integer({ default: 0 }),
    // Stored: a column, set by the ORM, which queries can use.
    total: fields.decimal({ precision: 12, scale: 2, computed: 'price * quantity * (100 - discount) / 100', stored: true }),
    // Not stored: computed when it is read.
    label: fields.string({ computed: '`${quantity} x ${product}`' }),
    big: fields.boolean({ computed: 'Number(total) >= 100' }),
    // A function: what it reads is given in `uses`.
    code: fields.string({ computed: (line) => `${line.product.toUpperCase()}-${line.quantity}`, uses: ['product', 'quantity'], stored: true }),
  };
}

const line = await Line.objects.create({ product: 'pen', price: '2.50', quantity: 4 });
line.total; // '10.00'
line.label; // '4 x pen'
await Line.objects.filter({ total__gte: '100' }).orderBy('-total'); // stored: a column like any other
await Line.objects.filter({ product: 'pen' }).update({ quantity: 50 }); // total and code computed again
Not stored (default)stored: true
The valueComputed each time it is read, from the values of the object thenComputed when the object is saved, and kept in a column
QueriesNone: filter, orderBy and values refuse it (QueryError)As any field: filters, orders, aggregates, indexes, unique
update()Nothing to doWhen it changes a field the computed field reads, the objects updated are computed again (in the same transaction)
In toJSON()YesYes
  • What an expression reads: the fields of its object by name (and foreign keys by their attname, authorId), other computed fields, relations once loaded (author?.name), and the globals of the expressions (Math, Number...). The ORM finds the fields it reads, so an update of other fields does not compute it again. A function says it in uses; without it, every update computes it again.
  • Decimals are text ('2.50'): price * quantity is a number, but price + 1 joins text, so write Number(price) + 1. A number computed for a decimal field is rounded to its scale, half away from zero.
  • Set by the ORM only: giving one to create() or new Model(), setting one that is not stored, or naming one in update() throws. The resources of orm.resource() ignore them in bodies, and jsonSchema() marks them readOnly.
  • recompute() computes again the stored fields of a QuerySet and saves those that changed (their number): after adding a stored computed field to a table with rows (as any new column, with null: true or a default for the migration), or when what it reads was changed outside the ORM. A stored field that reads relations is computed when its object is saved; recompute() brings it up to date after the related objects change.
  • The expressions are code of the model: they run on its objects, so they can call the methods of the values they read. Expressions written by users go to @xufa/expression with contexts of data instead.

Validation rules

The rules of a field (validate) and of a model (options.rules) can be expressions of @xufa/expression, functions, or either with its message. A rule gives true when the value is valid, false when it is not (its message, or a default one), or a string: the message. 

class Event extends Model {
  static fields = {
    name: fields.string({ validate: { rule: 'value.trim().length >= 3', message: 'At least 3 characters.' } }),
    seats: fields.integer({ validate: ['value >= 1', 'value <= 100 || "100 seats at most."'] }),
    start: fields.date(),
    end: fields.date(),
  };

  static options = {
    rules: [
      { rule: 'end >= start', message: 'The end cannot come before the start.', field: 'end' },
      'seats <= 10 || !name.startsWith("Small") || "A small event has 10 seats at most."',
      (event) => event.name !== 'cancelled',
    ],
  };
}

await Event.objects.create({ name: 'Small talk', seats: 20, start: '2026-10-05', end: '2026-10-06' });
// ValidationError (400): errors { __all__: ['A small event has 10 seats at most.'] }
  • A rule of a field reads its value as value, once coerced; it is not run on nulls (null: true says whether they are allowed).
  • A rule of a model reads the fields of the object by name (and its computed fields). Its message goes to the errors of field, or to __all__ (as in Django) without one. The rules of the parents of a model are its rules too.
  • When they run: in validate(), so on save(), create() and bulkCreate() (not with validate: false). The rules of a model run once the fields are valid, as Django's clean() after clean_fields(). update() runs the rules of the fields it sets, not those of the model: it does not load the objects.
  • Mistakes: an expression that does not compile throws when the model is first used; a rule that throws when it runs (text.length of a null) throws its error, as a mistake of the rule and not of the object (text?.length reads nulls).

Relations

A foreign key author keeps the key in authorId and, once loaded (selectRelated, prefetchRelated, await book.load('author'), or assigned), the object in author. The model it points to gets the reverse relation, relatedName (<model>Set by default): author.books is a QuerySet, and author.books.create() sets the key.

Option of foreignKeyWhat it does
onDeletecascade (default), setNull, protect or doNothing, done by the ORM so that it is the same on every database
relatedNameThe name of the reverse relation
attnameThe name of the key (author_id)
toFieldA unique field of the other model to point to, instead of its primary key
dbOnDelete, dbOnUpdateON DELETE and ON UPDATE of the foreign key in SQL (cascade, setNull, restrict, noAction), for writes made outside the ORM
dbConstraint: falseNo constraint in the database at all

A many-to-many relation tags (of a Book to a Tag) goes through a model with a foreign key to each, made when the models are registered (or given as through). book.tags is the QuerySet of the tags of a book, with add(), remove(), set() and clear(); tag.books (its relatedName) is the other way. Both can be in conditions (Book.objects.filter({ tags__name: 'x' })) and in prefetchRelated.

Primary keys

A model without a primary key gets id. A key of several fields (primaryKey: true on each, or options.primaryKey: ['student', 'course']) is composite, as Django's CompositePrimaryKey: instance.pk is the array of their values, and pk in queries takes arrays (get({ pk: [1, 'math'] }), pk__in: [[1, 'math'], [2, 'logic']]). No foreign key can point to such a model, except to a unique field with toField; MongoDB does not support them.

options.primaryKey: false makes a model without a primary key, for tables that have none (logs, tables of other systems). Its rows are inserted, read, counted, updated and deleted with QuerySets, but its objects cannot be found again by themselves: save() of a saved one, delete() and refresh() throw.

Objects

  • save({ fields }): inserts or updates, validating first.
  • delete(), refresh(), load(name), pk.
  • validate(): throws a ValidationError with errors by field and the status code 400.
  • toJSON(): the values, with the relations loaded.
  • Hooks: Model.on('beforeSave' | 'afterSave' | 'beforeDelete' | 'afterDelete', fn).
  • Model.schema({ input }): the schema of the objects as @xufa/schema makes them, typed (Schemas of routes). Model.jsonSchema({ exclude, partial }): the same schema in the form of OpenAPI 3.0 (nullable: true).

QuerySets

Model.objects is a lazy QuerySet. Refining it gives a new one; it runs when it is awaited or iterated (for await).

RefineRun
filter, exclude, orderBy, limit, offset, slice, only, values, valuesList, selectRelated, prefetchRelated, annotate, using, selectForUpdate, limitPer get, first, last, count, exists, aggregate, create, getOrCreate, updateOrCreate, bulkCreate, update, delete

limitPer(names, count, offset) gives the first objects of every group: Book.objects.orderBy('-pages').limitPer('author', 3) is the three longest books of each author, with a ROW_NUMBER() window in SQL.

Conditions

Conditions are those of Django: field__lookup, and relation__field to follow foreign keys (joins in SQL, $lookup in MongoDB), reverse and many-to-many relations (Author.objects.filter({ books__title__contains: 'x' }): each author once).

gt, gte, lt, lte, in, range, isnullComparisons
 
const { Q, and, or, not, F, Raw } = require('@xufa/orm');

Book.objects.filter(or({ pages__gte: 500 }, { author__name: 'Ada' }));
Book.objects.filter(new Q({ pages__gte: 500 }).or({ author__name: 'Ada' })); // the same
Book.objects.exclude(not({ title__icontains: 'notes' }));
Book.objects.filter({ pages__gt: F('chapters').mul(10) }); // compare with another field
Book.objects.filter(Raw(`length(${Raw.TABLE}.title) > ?`, [10])); // SQL of your own (SQL databases)

The conditions of one filter() on a relation of many are of the same row; those of chained calls, of any. A null is not equal, greater or less than anything, and exclude() keeps the rows with nulls, as in Django.

Aggregates

const { Count, Sum, Avg, Min, Max, Raw } = require('@xufa/orm');

await Book.objects.aggregate({ books: Count(), pages: Avg('pages') });
await Book.objects.values('author__name').annotate({ books: Count(), longest: Max('pages') });
// Across reverse relations (SQL databases): LEFT JOINs.
await Author.objects.values('name').annotate({ books: Count('books'), pages: Sum('books__pages') });
// Fragments of SQL (SQL databases).
await Book.objects.aggregate({ long: Raw('SUM(CASE WHEN pages > 300 THEN 1 ELSE 0 END)') });

Count takes { distinct: true }. A sum of no values is null.

Writing in bulk

  • update(values) and delete() of a QuerySet write every row it matches, with F() for values from other fields: update({ views: F('views').add(1) }). delete() follows the onDelete of the relations.
  • bulkCreate(objects) inserts many rows. In PostgreSQL, 500 objects or more go through COPY (the option copyRows of the database changes that number; false: never).
  • As in Django, bulkCreate can ignore the rows that break a unique key ({ ignoreConflicts: true }), or update the rows there ({ updateConflicts: true, updateFields: ['name'], uniqueFields: ['code'] }): INSERT ... ON CONFLICT in SQL databases.

Transactions and locks

await db.transaction(async () => {
  const account = await Account.objects.selectForUpdate().get({ pk: 1 }); // FOR UPDATE (PostgreSQL)
  account.balance -= 100;
  await account.save();
  await db.transaction(async () => {
    // a savepoint
  });
}); // commits when the function ends; rolls back when it throws

The queries inside the function run in the transaction, wherever they are in your code. Nested transactions are savepoints. selectForUpdate({ skipLocked, noWait, mode: 'share' }) locks the rows read. MongoDB has transactions on replica sets and sharded clusters, without savepoints.

Migrations

As in Django: await db.makeMigrations({ dir: 'migrations' }) compares the models with the schema the migration files describe, and writes a file (0002_auto.js) with the operations between them: tables created and dropped, fields added, dropped and altered, indexes and the fillfactor. A field added gets its default in the rows that exist; one without null or a default is refused.

await db.migrate({ dir }) applies the files not applied yet, in order, each in a transaction where the database has them, and records them (xufa_migrations). db.showMigrations({ dir }) lists them. 

// migrations/0003_rename.js: written by hand
module.exports = {
  operations: [
    { op: 'renameColumn', table: 'book', from: 'name', to: 'title' },
    { op: 'sql', sql: 'CREATE INDEX book_title_trgm ON book USING gin (title gin_trgm_ops)' },
    { op: 'run', fn: async (db) => { /* a data migration */ } },
  ],
};

SQLite has no ALTER COLUMN: its tables are made again, with the foreign keys checked after. In MongoDB, migrations make collections and indexes, fill the fields added and unset those dropped.

Stores of objects (blobs)

Stores of objects are backends too: a model is a container (a folder, a bucket), an object of the model is an object of the store. Its primary key (a string) is the key of the object; its fields.blob() the body; its fields.blobInfo() what the store knows of it (size, etag, updatedAt, contentType); its other fields the metadata of the object. The querysets are the same: 

class Upload extends Model {
  static fields = {
    key: fields.string({ primaryKey: true }), // the key of the object (its path)
    content: fields.blob(), // the body
    size: fields.blobInfo('size'),
    contentType: fields.blobInfo('contentType'),
    owner: fields.string({ null: true }), // metadata
  };
}

const files = new Database({ backend: 'disk', dir: 'uploads' }).register(Upload); // or { backend: 'memory-blob' }

await Upload.objects.create({ key: 'reports/q3.pdf', content: request.body, owner: 'ada' }); // a stream, a Buffer...
const report = await Upload.objects.get({ key: 'reports/q3.pdf' });
reply.type(report.contentType).send(await report.content.stream());
await Upload.objects.filter({ key__startswith: 'reports/' }).only('key', 'size'); // a listing: no bodies read
  • A body is written as a Buffer, a string, a readable stream, a Blob, or the body of another object (copied); it is read as a BlobValue, whose body is read only when asked: stream(), buffer(), text(), json(), and url() where the store gives URLs.
  • Conditions on the key (exact, in, startswith) are asked to the store; the rest run in memory on what it gives. The metadata of objects is read only when a query needs it, with a read for each object listed.
  • save() of an object read writes its metadata alone, not its body; a new body is written. update() and delete() of querysets work on every object matched.
  • The content type is the one given, or the one of the extension of the key.
  • A model of these backends has a primary key that is a string and one fields.blob(), no relations nor unique fields but the key. No transactions: db.transaction(fn) runs fn, its writes made at once.

disk (dir) keeps each object as a file, <dir>/<table>/<key>, its body as it is (the folder can be served, copied or backed up), and content types and metadata in <dir>/.meta/<table>/<key>.json. Files are written to a temporary file and renamed. Keys stay in their folder: .., empty parts, absolute paths, backslashes, colons and the names Windows keeps are refused. url: (table, key) => string gives the URLs of url() where the folder is served. memory-blob is in memory, for tests. With tenants, a store can be a database of each tenant.

s3 (bucket, region) is S3 and the stores that speak its API (Cloudflare R2, MinIO, Backblaze B2, Wasabi, DigitalOcean Spaces, Alibaba OSS...), with fetch and SigV4 signatures of its own (no SDK). The objects of a model are in the bucket under <prefix><table>/; endpoint is the URL of a store that is not AWS, and credentials are the AWS_* variables when not given. Streams are sent in parts (a multipart upload of partSize, 8 MiB, aborted when it fails), so their size need not be known. The metadata is one header, and changing it alone copies the object on itself (the body is not sent again). url() is a signed URL (expiresIn, up to 7 days), or the one under publicUrl (a CDN); createBucket: true makes the bucket in sync(). 

new Database({ backend: 's3', bucket: 'uploads', region: 'eu-west-1' }); // AWS, credentials of AWS_* variables
new Database({ backend: 's3', bucket: 'uploads', endpoint: 'https://<account>.r2.cloudflarestorage.com', region: 'auto', credentials });

Several databases

An app can keep its models in several databases, even of different backends: the books in PostgreSQL, the events in MongoDB, the sessions in memory. It takes three steps:

  1. Name the databases. One of them is called default: every model that is not sent elsewhere goes there.
  2. Send the models that do not go to default, by name in routes, or in the model itself with the option database. Only the exceptions are written down.
  3. Register the models in the Databases: each one is put in its database, and Book.objects queries it from then on.
const { Databases, Model, fields } = require('@xufa/orm');

class Session extends Model {
  static fields = { token: fields.string() };
  static options = { database: 'cache' }; // this model says where it goes
}

const dbs = new Databases(
  {
    // 1. The databases, by name.
    default: { backend: 'postgres', url: process.env.DATABASE_URL },
    events: { backend: 'mongodb', url: process.env.MONGO_URL, database: 'events' },
    cache: { backend: 'memory' },
  },
  // 2. The exceptions.
  { routes: { Event: 'events', AuditLog: 'events' } }
);
dbs.register(Author, Book, Event, AuditLog, Session); // 3. Author and Book go to default
await dbs.connect();
await dbs.migrate({ dir: 'migrations' }); // migrations/default, migrations/events, migrations/cache

await Event.objects.create({ kind: 'login' }); // in MongoDB
await Book.objects.filter({ author__name: 'Ada' }); // in PostgreSQL
await dbs.transaction('default', async () => { /* ... */ });

Where each model of that example goes:

ModelDatabaseBecause
Author, Bookdefault (PostgreSQL)Nothing sends them elsewhere.
Event, AuditLogevents (MongoDB)Their route.
Sessioncache (memory)Its option database.

The database of a model is, in this order: its option database; its route in routes; the route '*' when there is one (a database for every model not named); and default (another name with new Databases(config, { defaultName: 'main' })). A model sent to a database that is not in the list is an error when the models are registered.

Model.objects.using(db) runs one QuerySet in another database. Relations between models of different databases are followed with more queries (prefetchRelated, load(), the reverse accessors), but a query cannot join them: with Event in MongoDB, Book.objects.filter({ events__kind: 'login' }) is an error. A foreign key to a model of another database needs dbConstraint: false, as no database can check it, and a transaction is of one database.

Tenants

With Tenants, each tenant (a customer, an organization) has its own data: config(id) says where, and code run in a tenant uses its databases. The databases of a tenant are opened (and set up) the first time it is used, and those of the last max tenants used are kept open. With the HTTP plugin, each request runs in its tenant (see With @xufa/http).

One database per tenant

config gives the options of one database: every model of the tenant is in it.

const { Tenants } = require('@xufa/orm');

const tenants = new Tenants({
  models: [Author, Book],
  config: async (id) => ({ backend: 'postgres', url: `postgres://app@db:5432/tenant_${id}` }),
  setup: (db) => db.migrate({ dir: 'migrations' }),
  max: 100, // databases kept open
});

await tenants.run('acme', () => Book.objects.count()); // the books of acme

Several databases in a tenant

A tenant can have several databases too, as in Several databases above: config gives databases (by name, one of them default) instead of the options of one database, and the models go to them by the same rules. Routes can be given once for every tenant (routes of Tenants), and changed for one tenant (routes in what config gives). 

class Session extends Model {
  static fields = { token: fields.string() };
  static options = { database: 'cache' }; // in every tenant
}

const tenants = new Tenants({
  models: [Author, Book, Event, AuditLog, Session],
  routes: { Event: 'events', AuditLog: 'events' }, // for every tenant
  config: async (id) => ({
    databases: {
      default: { backend: 'postgres', url: `postgres://app@db:5432/tenant_${id}` },
      events: { backend: 'mongodb', url: 'mongodb://db:27017', database: `events_${id}` },
      cache: { backend: 'memory' },
    },
    // Only for this tenant (optional): a small customer keeps its audit log in PostgreSQL.
    routes: id === 'small' ? { AuditLog: 'default' } : {},
  }),
  setup: (db) => db.sync(), // db: the Databases of the tenant; each of its databases is set up
});

await tenants.run('acme', async () => {
  await Event.objects.create({ kind: 'login' }); // MongoDB, database events_acme
  await Session.objects.create({ token: 't' }); // memory
  return Book.objects.filter({ author__name: 'Ada' }); // PostgreSQL, database tenant_acme
});

Where each model goes:

ModelTenant acmeTenant smallBecause
Author, BookdefaultdefaultNothing sends them elsewhere.
EventeventseventsThe route of every tenant.
AuditLogeventsdefaultThe route of every tenant, changed by the route of small.
SessioncachecacheIts option database, which comes before any route.

Every database a model is sent to must be in the databases of the tenant: a tenant without cache fails when it is opened (its database cache is not one of default, events). A tenant whose config gives one database (no databases) keeps every model in it, whatever the routes, so config can give one database to some tenants and several to others. As with Databases, a query cannot join models of two databases of a tenant, and relations between them are followed with more queries.

Caches

A model with the option cache (true, or { ttl, indexes }) answers get() by its primary key, or by a unique field of indexes, from the cache of its database. Saving or deleting an object removes it; update() and delete() of QuerySets clear the model. Inside transactions the cache is neither read nor filled. Values are copied in and out.

CacheWhere
MemoryCache({ max, ttl })In the process: an LRU of max keys. The default.
SharedCache({ bus, store })One copy in the primary of a cluster, asked by the workers; store (in the primary): where it keeps them, a MemoryCache by default.
LocalCache({ bus })A copy in each process, with invalidations sent to the others: reads never leave the process.
NetCache of @xufa/netcacheA copy in each machine, every write sent to the others: the cache of several machines. In a cluster, the store of the SharedCache of the primary (new SharedCache({ bus, store })).
 
const { bus } = require('@xufa/cluster');
const db = new Database({ backend: 'postgres', url, cache: new LocalCache({ bus, max: 50000 }) });

A cache that fails to read or to write is a miss: the database answers, and onCacheError(err, { operation }) of the Database (or of cached()) is told; without it, a warning (code XUFA_ORM_CACHE) is emitted once for each database. A delete that fails is an error (what the cache keeps would be old): the save() or delete() that asked for it fails.

Cached querysets

.cached({ ttl }) keeps the results of a queryset (objects, values(), count(), exists(), aggregate(), first()...) until a model it reads is written: every write to a model with the option cache, from anywhere in the app, gives it a new version, and results are kept by the versions of the models they read (those of its conditions, orders and values too: writer__name reads Writer). With a SharedCache or a NetCache the versions are shared, so a write in one process is seen by all. Every model it reads needs the option cache. Inside transactions nothing is read nor kept, and a commit gives its models new versions again. Objects with related ones are not kept: cache their values(). 

const top = await Book.objects.filter({ author__country: 'ES' }).orderBy('-sales').limit(10).cached({ ttl: 60000 });

Functions

orm.cached(fn, { key, ttl, cache, name }) keeps the results of a function of yours: the same arguments (whatever the order of the keys of objects) give the result kept for ttl ms, calls made while one runs wait for it, and errors are not kept. fn.invalidate(...args) and fn.clear() forget them; a shared cache needs a name. 

const rates = orm.cached(async (currency) => fetchRates(currency), { ttl: 600000 });

With @xufa/http

const orm = require('@xufa/orm');

app.register(orm.plugin, { database: db, migrate: { dir: 'migrations' } });
// or { database: db, sync: true }, or { tenants: { tenants, resolve, authorize } }: below

The plugin connects the database when the app starts (migrating it when asked), gives it as app.db, and closes it with the app. A ValidationError is answered with 400 and the messages of each field (errors), a duplicate of a unique field (UniqueError) with 409 and its fields, and get() of nothing with 404. With tenants, a request without one gets 400 (unless required: false), and one of a tenant that does not exist, 404.

With tenants, resolve(request) gives the tenant of a request (a header, the host, the user), and authorize(request, id, reply) says whether the request may use it, before it is entered (its database is not even looked up): false is answered with 403, and an error it throws is sent as it is. With @xufa/auth, users may use the tenants of their claims: 

app.register(orm.plugin, {
  tenants: {
    tenants,
    resolve: (request) => request.headers['x-tenant'],
    authorize: (request, id, reply) => app.auth.canUseTenant(request, id, reply), // 401 without a user, 403 if not its
  },
});

Without authorize, any request may use any tenant it names, and a warning says so when the app starts; authorize: false is for tenants taken from the user itself, which need no check.

With cancel: true, the reads of a request stop when its client goes away (request.signal): the queries that have not started throw (an AbortError), and PostgreSQL cancels the one that runs, so the server stops working for nobody. Writes are not stopped (one the client did not wait for may still be wanted), nor the statements of a transaction. Outside requests, QuerySet.signal(signal) and orm.withSignal(signal, fn) do the same: 

const books = await Book.objects.filter({ pages__gte: 100 }).signal(AbortSignal.timeout(2000));
await orm.withSignal(signal, async () => report());

Resources

orm.resource(Model, options) makes the routes of the objects of a model, as the ModelViewSets of Django REST framework: list, get, create, update (PUT and PATCH) and delete, registered with a prefix. 

app.register(
  orm.resource(Book, {
    filters: { author: ['exact', 'in'], pages: ['gte', 'lte'] },
    ordering: ['title', 'pages'],
    search: ['title', 'author__name'],
    related: ['author'],
    readOnly: ['owner'],
    auth: { list: false, get: false, create: true, update: true, delete: 'admin' }, // rules of @xufa/auth
    hooks: { beforeCreate: (values, request) => ({ ...values, owner: request.user.sub }) },
  }),
  { prefix: '/books' }
);
app.register(orm.resource(Author, { actions: ['list', 'get'] }), { prefix: '/authors' });
RouteActionAnswer
GET /bookslist{ count, limit, offset, results }, with ?limit=&offset=, ?ordering=-pages, ?search= and the filters (?pages__gte=100, ?author__in=1,2)
GET /books/:idgetThe object, or 404
POST /bookscreate201 and the object
PUT /books/:idupdateEvery writable field set (those not given take their default)
PATCH /books/:idupdateThe fields given set
DELETE /books/:iddelete204
  • queryset(request): the objects of a request (all by default); one out of it is not found by any route, so (request) => Book.objects.filter({ owner: request.user.sub }) gives each user theirs.
  • fields or exclude: what is answered; serialize(object, request) answers something else.
  • writable or readOnly: what bodies set (all but the primary key and the fields the ORM sets). Other fields of the model in a body are ignored; keys that are no field are a 400.
  • strict: true: those other fields are refused too, every key refused in one ValidationError (400 with errors by key: { id: ['This field is read-only.'] }). In a PUT or PATCH, a read-only key with the value the object has is taken (a body can be the object as it was read).
  • filters, ordering and search: the query parameters lists take (others are a 400); pageSize (50), maxPageSize (500), pagination: false, lookup (the field of /:id).
  • auth: the rule of @xufa/auth for every action, or one by action. hooks: beforeCreate, afterCreate, beforeUpdate, afterUpdate, beforeDelete.
  • Errors are answered with their status: 400 (with the messages of each field), 404, and 409 for duplicates and protected objects.
  • openapi: with @xufa/openapi, the routes are documented (operations, parameters, bodies and objects from Model.schema(), responses, security): { tag } names their tag, false leaves them out. Only documented: what they accept and answer does not change.

Faults (tests of resilience)

db.faults makes operations of a database fail, wait or hang, as a database that is down, slow or lost would, to see what an app does then (in its tests, or in staging). dbs.faults does it to every database of Databases, and tenants.faults to the databases of every tenant (rules can name tenants). 

db.faults.fail({ operations: 'write', models: [Order], rate: 0.2 }); // 1 write of Order in 5 fails
db.faults.delay({ operations: 'read', ms: 300, jitter: 200 }); // reads take 300 to 500 ms more
const hung = db.faults.hang({ models: ['Payment'] }); // they do not end until hung.release()
tenants.faults.down({ tenants: ['acme'] }); // every operation of acme fails (connect too)
db.faults.up(); // no more down
db.faults.clear(); // no more faults
  • A rule matches operations (select, count, aggregate, insert, update, delete, transaction, connect; 'read' and 'write'), models and tenants; rate is the chance of each match (faults.random of your own in tests), after leaves the first matches alone, times removes it after that many.
  • Each rule counts its hits; remove() takes it away, release() lets what it holds go on.
  • The errors are FaultErrors (code XUFA_ORM_ERR_FAULT, status 503: the HTTP plugin answers 503), or the error given.
  • Without rules, the operations are as they were. Objects the cache of a model gives do not reach the database: no fault happens to them.
  • cache.faults of MemoryCache, SharedCache, LocalCache (and NetCache) makes the cache fail: get, set, delete, clear (read, write), keys by prefix or regular expression. cache.faults.down() shows that the app still answers without its cache.

The rules are those of @xufa/faults, which the faults of @xufa/client and of the bus of @xufa/cluster use too; err instanceof FaultError is true of the errors of all of them.

Schemas of routes

Model.schema() gives the JSON Schema of the objects of a model as @xufa/schema makes them: its functions take it, and in TypeScript it carries the type of the objects (as JSON). 

const { s } = require('@xufa/schema');

const BookOut = Book.schema(); // the objects: replies
const NewBook = s.omit(Book.schema({ input: true, additionalProperties: false }), ['id', 'createdAt']);
const BookPatch = s.partial(NewBook); // the body of an update

app.post('/books', { schema: { body: NewBook, response: { 201: BookOut } } }, async (request, reply) => {
  reply.code(201);
  return Book.objects.create(request.body); // request.body: { title: string; writerId: number | string; pages?: ... }
});
  • Each field is its JSON: dates are strings (format: date-time), bytes base64, decimals strings; choices are an enum; null: true takes null (type: ['integer', 'null']).
  • A foreign key is its key (writerId). Many-to-many relations and the bodies of blobs are not in it.
  • Not required: fields that can be null, have a default, are given by the database (the automatic id, autoNow, what a blob backend knows) or are computed (readOnly).
  • input: true leaves out what is never given (computed fields, what a blob backend gives); other options are those of s.object().
  • In TypeScript the type comes from static fields (those of its parents too with fields.extend()); choices written as const give their values as a type.
  • A model without a primary key (primaryKey: false) or with a composite one has no automatic id, in its type too when static options keeps the literal (as const, or satisfies ModelOptions). primaryKey is not inherited, but TypeScript reads the options of the parent in a child without options of its own.

TypeScript

The declarations type models from their fields. Give the model an interface of the same name, and use Model.query() for QuerySets of the model (TypeScript cannot type Model.objects by the class). 

import { Model, fields, type Fields } from '@xufa/orm';

const bookFields = { title: fields.string(), author: fields.foreignKey(() => Author) };
class Book extends Model {
  static fields = bookFields;
}
interface Book extends Fields<typeof bookFields> {}

const books: Book[] = await Book.query().filter({ author__name: 'Ada' }); // book.title, book.authorId, book.author

Children of a model: fields.extend(Parent, { ... }) gives the fields of the parent (and of its parents) with those given, as the ORM merges them (null removes one). The model is the same; TypeScript then knows them all (Fields<typeof Article.fields>, Article.schema()), and accepts the class as a child of its parent. 

class Timestamped extends Model {
  static options = { abstract: true };
  static fields = { createdAt: fields.datetime({ autoNowAdd: true }), updatedAt: fields.datetime({ autoNow: true }) };
}
const articleFields = fields.extend(Timestamped, { title: fields.string() });
class Article extends Timestamped {
  static fields = articleFields;
}
interface Article extends Fields<typeof articleFields> {} // article.title, article.createdAt...

A child that removes a field of its parent (null) is not one TypeScript accepts as its child (// @ts-expect-error on its class).

The same on every backend

Each backend compiles the description of a query to its database, and they give the same results:

  • Nulls are never equal, greater or less than anything, and sort first ascending and last descending.
  • contains, startswith and endswith are case sensitive everywhere (SQLite's LIKE is not, so they are compiled without it).
  • Unique fields allow many nulls (partial unique indexes in MongoDB).
  • JSON values, arrays and maps are compared as wholes.
  • A sum of no values is null; groups of a missing field and of a null are the same group.
  • Decimals are compared, ordered and summed as numbers, exactly (MongoDB keeps them as Decimal128); sums and averages are numbers.

What differs, as it does between the databases:

  • Transactions: MongoDB has them on replica sets and sharded clusters only, and has no savepoints.
  • Decimals in MongoDB have 34 digits at most (Decimal128): a decimal field with a larger precision is refused. Decimals written as strings by earlier versions of the ORM are read as they are but compared as text: await db.migrateDecimals() converts them in the server (the number of values, by model).
  • Foreign keys are constraints in SQL; in MongoDB, a key can point to nothing.
  • The order of strings is the collation of the database.
  • Raw queries: db.backend.raw(sql, params) in SQL; db.backend.db is the @xufa/mongo database in MongoDB.

Not yet: ordering and values across reverse relations (conditions and aggregates follow them), generic relations, and a command line for migrations.
