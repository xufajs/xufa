Overview Reference

@xufa/openapi

OpenAPI documents of the routes of an app of @xufa/http (and fastify), and an explorer to read and try them, with no dependencies but @xufa/yaml. The code and the tests are those of @fastify/swagger 9.9.1; what xufa adds documents the resources of the ORM and the security of @xufa/auth with nothing to write.

Quick start

npm install @xufa/openapi
import xufa from 'xufa';
import openapi from '@xufa/openapi';
import openapiUi from '@xufa/openapi/ui';

const app = xufa();
await app.register(openapi, { openapi: { info: { title: 'Books', version: '1.0.0' } } });
await app.register(openapiUi, { routePrefix: '/docs' });

app.register(orm.resource(Book, { filters: ['author'], ordering: ['pages'] }), { prefix: '/books' });

await app.listen({ port: 3000 }); // http://localhost:3000/docs

Register it (awaited) before the routes it documents: it sees them as they are added. app.swagger() is the document, and app.swagger({ yaml: true }) the same as YAML.

Documenting routes

A route is described by its schema: params, querystring, headers, body and response, with tags, summary, description, operationId, deprecated, security and hide in it. Shared schemas (app.addSchema({ $id })) become components.schemas. 

app.get('/books/:id', {
  schema: {
    tags: ['books'],
    summary: 'A book',
    params: { type: 'object', properties: { id: { type: 'integer' } } },
    response: { 200: { $ref: 'Book#' }, 404: { description: 'Not found', type: 'null' } },
  },
}, handler);
  • openapi: the document to start from (info, servers, components, security, tags), or swagger for Swagger 2.
  • transform({ schema, url, route }) and transformObject({ openapiObject }) change what is written; a route's config.swaggerTransform replaces transform for it.
  • hideUntagged, hiddenTag, exposeHeadRoutes, stripBasePath, refResolver, decorator.

Route schemas can have the keywords of OpenAPI (style, explode, example, x- extensions): @xufa/http accepts them as annotations, as fastify does, and still refuses other unknown keywords, so typos are caught.

What xufa adds

In OpenAPI 3 documents (xufa: false leaves it out):

  • Resources of the ORM: each route of orm.resource(Book) gets its tags, summary and operationId (listBook, getBook, createBook, updateBook, partialUpdateBook, deleteBook), its parameters (the filters, ordering, search and page of the list), its body (the writable fields, from Book.schema(); null as OpenAPI 3.0 or 3.1 asks; the other fields of the object marked readOnly, never required, their description saying what the resource does with them: ignored, or with strict refused unless an update gives the value the object has) and its responses (the object as it is answered, its read-only fields marked too; the page, the errors). The object is in components/schemas once and the operations refer to it: components are named def-0, def-1... as @fastify/swagger does (their title is their $id), or by their $id (Book) with refResolver: { buildLocalReference: (json, baseUri, fragment, i) => json.$id || `def-${i}` }. The resource's option openapi names their tag ({ tag: 'Library' }) or leaves them out (false).
  • Any route can be documented by its config.openapi: a schema that only describes it, under its own schema (which wins). It is never used to validate or serialize, so documenting a route does not change what it accepts or answers.
  • The strategies of @xufa/auth become components.securitySchemes: the access tokens (http bearer JWT), API keys (apiKey in their header or query), HTTP Basic, and the strategies of Passport (OAuth 2.0 with their URLs, bearer, API keys). A route with config.auth gets the security of its strategies: those of the rule, or any of them.

From a document (design first)

openapi.operations makes the routes of an OpenAPI 3 document you wrote first: each operation is a route with the schemas of its parameters, body and responses (validated and serialized by @xufa/http), and the handler of its operationId. Operations without a handler answer 501, so the API can be served, and tried in the explorer, before it is written. 

await app.register(openapi, { mode: 'static', specification: { path: './openapi.yaml' } });
await app.register(openapiUi);
await app.register(openapi.operations, {
  path: './openapi.yaml', // or document: { openapi: '3.1.0', ... }
  handlers: {
    listBooks: async (request) => Book.objects.all(),
    getBook: { preHandler: app.auth.authorize('reader'), handler: async (request) => Book.objects.get({ pk: request.params.id }) },
  },
  prefix: '/api',
});
  • components.schemas become shared schemas, and the $refs to them follow: recursive schemas work. In requests, readOnly properties are not required; in responses, writeOnly ones (passwords) are not answered.
  • Parameters in path, query and headers are validated; an optional JSON body may be left out (the handler gets null); responses with JSON are serialized by their schemas.
  • Security of the operation (or of the document) is the config.auth of its route for @xufa/auth: the strategies of its schemes (security: { bearer: 'jwt' } maps names); security: [] is public. Without @xufa/auth, an app with secured operations does not start.
  • handlers by operationId (or 'GET /path'): a handler or the options of its route; a handler of no operation is an error, and missing: 'throw' makes every operation need one.
  • The formats of OpenAPI (int32, byte, binary, password...) are known to @xufa/http (byte is checked as base64).
  • validateResponses: true (or validateResponse of a handler): what a handler answers is checked against the schema of its status; one out of its contract is a 500 with the errors, instead of reaching the client. request.operation: its id, validateResponse(payload, status) and validateRequest() (with attachValidation: true).
  • missingStatus (501, or 404) and requestIdHeader (x-request-id).
  • Documents split in files are read whole: $refs to other files are followed (to URLs with remote: true), schemas become schemas of the document. openapi.bundle(path) gives that document, to serve it too. Swagger 2.0 documents are read as OpenAPI 3 (openapi.fromSwagger2()).

The explorer

@xufa/openapi/ui serves the document and an explorer, by default at /documentation: the page, /json, /yaml, and /initializer.js (what starts it: a file, not inline, so strict Content Security Policies allow it). Its routes are not in the document.

  • ui: 'swagger' (Swagger UI, the default), 'scalar' or 'redoc', from a CDN (cdn) at pinned versions.
  • assets: a folder of swagger-ui-dist served at <routePrefix>/static instead of the CDN (needed for OAuth logins from the explorer: its redirect page must be of the same origin).
  • uiConfig (the configuration of the explorer, as JSON), initOAuth, title, routePrefix.
  • transformSpecification(document, request, reply): the document of a request (on a copy).
  • uiHooks: { onRequest, preHandler }, to protect its routes; csp: true (or a policy) for a Content-Security-Policy.
app.register(openapiUi, {
  routePrefix: '/docs',
  ui: 'scalar',
  uiHooks: { onRequest: app.auth.authorize('staff') },
  csp: true,
});

A document of yours

mode: 'static' serves a document instead of making one: specification: { path, baseDir } (a JSON or YAML file, read with @xufa/yaml) or { document }; postProcessor(document) changes it.

Coming from @fastify/swagger

  • @fastify/swagger can be replaced by @xufa/openapi (an import, or a require()): same options, same app.swagger(), and the same documents (its test suite runs on it).
  • @fastify/swagger-ui: @xufa/openapi/ui has its routes (/documentation, /json, /yaml) and main options (routePrefix, uiConfig, initOAuth, transformSpecification, uiHooks), and loads the explorer from a CDN (or a folder) instead of installing it.
  • json-schema-resolver, rfdc and yaml are written in (yaml as @xufa/yaml).

Tests

The suite of @fastify/swagger (290 tests: OpenAPI 3 and Swagger 2, dynamic and static, every document checked by swagger-parser) is ported to vyntra by tools/port-swagger; test/xufa tests what xufa adds and the explorer.

TypeScript

The declarations of @fastify/swagger on @xufa/http, with the types of openapi-types written in, and of the explorer (@xufa/openapi/ui); config.openapi is typed in the config of routes.
