Overview Reference

@xufa/session

Sessions of browsers for @xufa/http, as those of Django and Laravel: values kept between the requests of a browser by a signed cookie, in memory or in a database of @xufa/orm (any backend, deleted when they expire), with flash messages and CSRF tokens. No dependencies.

Quick start

import xufa from '@xufa/http';
import { sessionPlugin } from '@xufa/session';

const app = xufa();
app.register(sessionPlugin, { secret: 'a secret of 32 characters or more!!' }); // process.env.SESSION_SECRET

app.get('/visits', async (request) => {
  const visits = (request.session.get('visits') || 0) + 1;
  request.session.set('visits', visits);
  return { visits };
});

const first = await app.inject('/visits');
const cookie = first.headers['set-cookie'].split(';')[0]; // what a browser keeps
const second = await app.inject({ url: '/visits', headers: { cookie } });
console.log(first.json(), second.json());
{ visits: 1 } { visits: 2 }

Values

request.session has get(key), set(key, value), has, delete, all() and clear(). Values are JSON. A session is saved when the reply is sent, if it changed; a request that does not use it makes none (and no cookie).

Logins and logouts

app.post('/login', async (request, reply) => {
  const user = await checkPassword(request.body);
  request.session.regenerate().set('userId', user.pk);
  return reply.redirect('/');
});
app.post('/logout', async (request, reply) => {
  request.session.destroy();
  return reply.redirect('/');
});

regenerate() gives the session a new id and deletes the old one: an id someone learned before the login is worth nothing after it. destroy() ends the session and clears its cookie.

Log out everywhere

A session tied to its user with await request.session.login(user.pk) (which regenerates it too) can be logged out with every other session of that user: in every browser, process and machine that shares the store. 

app.post('/login', async (request) => {
  const user = await checkPassword(request.body);
  await request.session.login(user.pk); // request.session.user is '42' from now on
  return { ok: true };
});
app.post('/logout-everywhere', async (request) => {
  await request.session.logoutEverywhere(); // this one too
  return { ok: true };
});
app.post('/logout-others', async (request) => {
  await request.session.logoutOthers(); // this one goes on, with a new id and CSRF token
  return { csrf: request.session.csrfToken() };
});
// An admin ending the sessions of a user (a password changed, an account locked).
await app.sessions.logoutUser(user.pk);

Ending every session of a user does not delete them one by one: the store keeps a generation of each user (under user:<id>, which no cookie can name: their ids are signed): logging out everywhere raises it, and a session made in an older generation is emptied at its next request (request.session.endedEverywhere says so). It works with every store, costs one more read of the store for the requests of sessions with a user, and a generation lasts as long as a session can (maxAge).

That read goes away where the generation is kept with the user: app.sessions.useGenerations({ read(id, request), write(id, generation) }) reads it from there (undefined: the store's) and writes it at each raise. @xufa/auth does it with the users of AbstractUser, whose row has sessionGeneration: the request reads its user anyway, and nothing else.

The sessions of a user

The record of a user keeps the ids of its sessions too (written at its logins and new ids, not at every request), and each session its device: its user agent, address, login and last request (written with the session, or touchAfter after it was last written: an hour by default). app.sessions.list(userId) gives those still there, last seen first, each named by its handle, a hash of its id (an id would open the session; a handle only names it), and app.sessions.end(userId, handle) ends one. request.session.handle is that of the session of a request: a page of "your devices" marks it, and ends the others. 

app.get('/account/sessions', async (request) =>
  (await app.sessions.list(request.session.user)).map((item) => ({
    ...item, // { handle, agent, ip, since, seen, expiresAt }
    current: item.handle === request.session.handle,
  }))
);
app.post('/account/sessions/:handle/end', async (request) => ({
  ended: await app.sessions.end(request.session.user, request.params.handle),
}));

Two logins of a user at the same moment, in two processes, may leave one of them out of the list (it is read and written whole); the session itself is not touched, and a logout everywhere ends it all the same. A user keeps its last 100 sessions in the list.

Flash messages

flash(key, value) keeps a value for the next request only, as Rails and Laravel do: a message set before a redirect, shown by the page after it. flash(key) reads it. 

request.session.flash('notice', 'Saved');   // then reply.redirect('/books')
const notice = request.session.flash('notice'); // in the next request; gone after it

Messages for the user, as Django's: message(text, level) keeps one for the page shown next (this one, or the next one after a redirect), and messages() gives those waiting, as { text, level }, once. Templates have them as messages (The context of every view). 

request.session.message('The book was saved', 'success');
return reply.redirect(app.reverse('book-detail', [book.pk])); // its page shows the message, once

CSRF

With csrf: true, POST, PUT, PATCH and DELETE of a session need its token: forms send csrfToken() back in a field _csrf, and scripts in the header x-csrf-token; a 403 otherwise. Requests without a session (they act as nobody) and routes with config: { csrf: false } (webhooks) need none. While a session keeps nothing, its token goes in a signed cookie of its own (sid_csrf, as Django's csrftoken), not in the store: a visitor who only sees pages with forms makes no session, and the writes of a browser with that cookie are checked against it (a login form). A session that starts keeping something keeps that token; a login makes a new one. 

<form method="post" action="/books">
  <input type="hidden" name="_csrf" value="{{ csrf }}">
  ...
</form>

Stores

memoryStore() (the default) keeps sessions in the process: for tests and development. ormStore(db) keeps them as objects of a model of the ORM (table xufa_sessions) in any backend, for every process and machine with the database; its TTL index deletes those that expired (db.expire(), or the option expire of the plugin of the ORM). A store of your own has get(id), set(id, data, expiresAt) and delete(id).

ormStore(db, { asyncCommit: true }) (in a project, sessions: { asyncCommit: true } of xufa.yaml) writes sessions without waiting for the disk, in PostgreSQL: SET LOCAL synchronous_commit TO OFF, the statements of the write sent together. A page that writes its session (a counter of visits, a cart) answers about twice as fast; a crash of the database server may lose the writes of its last fraction of a second (a user logged out again, a message lost), and nothing else. The records of the users (the generations of "log out everywhere", their lists of sessions) always wait for the disk: a crash does not undo a logout everywhere. Projects made by xufa new have it on (false turns it off); the store alone has it off.
