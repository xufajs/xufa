Overview Reference

@xufa/jwt

JSON Web Tokens with the API of jsonwebtoken, and of jws and jwa below it, without dependencies: everything is done by node:crypto. It passes the test suites of the three (607 tests, with the vectors of RFC 7515 and checks against openssl) and tests of its own on attacks on verification. @xufa/auth signs and verifies its tokens with it.

Quick start

npm install @xufa/jwt
const crypto = require('node:crypto');
const jwt = require('@xufa/jwt');

const token = jwt.sign({ sub: '42', role: 'admin' }, process.env.JWT_SECRET, { expiresIn: '15m', issuer: 'app' });
const claims = jwt.verify(token, process.env.JWT_SECRET, { algorithms: ['HS256'], issuer: 'app' });
console.log(claims.sub, claims.role, claims.exp - claims.iat);

// Asymmetric keys: the private one signs, the public one verifies.
const { privateKey, publicKey } = crypto.generateKeyPairSync('ec', { namedCurve: 'P-256' });
const signed = jwt.sign({ sub: '42' }, privateKey, { algorithm: 'ES256', keyid: 'k1' });
console.log(jwt.verify(signed, publicKey).sub, jwt.decode(signed, { complete: true }).header);
try {
  jwt.verify(signed, publicKey, { algorithms: ['HS256'] }); // an EC key takes ES256/384/512 only: never HMAC nor none
} catch (err) {
  console.log(err.name, err.message);
}

sign()

sign(payload, secretOrPrivateKey, options, callback): the token, or with a callback (err, token).

OptionWhat it does
algorithmHS256 by default; see Algorithms.
expiresIn, notBeforeexp and nbf: seconds, or a span as text ('15m', '2 days').
audience, issuer, subject, jwtidaud, iss, sub, jti (a payload that has them already is refused).
keyid, headerkid, and more fields of the header.
noTimestampNo iat.
mutatePayloadSets the claims on the payload given (not on a copy).
encodingOf a payload given as text (utf8).
allowInsecureKeySizesRSA keys under 2048 bits.
allowInvalidAsymmetricKeyTypesKeys of another kind than the algorithm.

The key: a string or Buffer (a secret, or a key in PEM), a KeyObject, or { key, passphrase }.

verify()

verify(token, secretOrPublicKey, options, callback): the payload (or { header, payload, signature } with complete: true). The key can be a function (header, callback) that finds it (with the kid of the header), when verify() is given a callback.

OptionWhat it checks
algorithmsThe ones taken; without it, those of the kind of the key.
audienceaud: a value or a list, strings or RegExps.
issuer, subject, jwtid, nonceiss (a value or a list), sub, jti, nonce.
typeThe typ of the header (RFC 8725), such as 'at+jwt' for access tokens: a value or a list, ignoring case and application/.
maxAgeThe age of iat: seconds or text.
clockTolerance, clockTimestampSeconds of leeway for exp, nbf and maxAge; the time taken as now.
ignoreExpiration, ignoreNotBeforeNot exp, not nbf.

decode()

decode(token, { complete, json }): the payload (or header, payload and signature) without verifying anything: for reading the kid before choosing a key, never for trusting the claims.

Algorithms

HS256/384/512 (HMAC), RS256/384/512 (RSASSA-PKCS1-v1_5), PS256/384/512 (RSASSA-PSS), ES256/384/512 (ECDSA), none (only when it is in algorithms and no key is given), and two jsonwebtoken does not have: EdDSA (Ed25519 and Ed448, RFC 8037) and ES256K (ECDSA on secp256k1, RFC 8812).

What verify() refuses

  • An algorithm the options do not take. Without algorithms, those of the kind of the key: a secret takes HS*, RSA keys RS* and PS*, EC keys ES*, Ed25519 and Ed448 EdDSA; so a token cannot choose HMAC with a public key as its secret (algorithm confusion), nor none.
  • A key of another kind than the algorithm: an EC key of another curve, RSA-PSS keys of other parameters.
  • A signature that is not valid (HMAC compared in constant time) or of the wrong size (ECDSA: an all-zero signature is not valid either).
  • exp passed and nbf not reached, and the claims of the options (a RegExp audience never takes a token without aud).
  • A header with crit: RFC 7515 (4.1.11) says extensions that are not understood must be refused. jsonwebtoken does not look at it.

Errors

JsonWebTokenError (message: 'invalid signature', 'jwt malformed', 'invalid algorithm'...), TokenExpiredError (expiredAt) and NotBeforeError (date), as jsonwebtoken has them. A key of another kind than the algorithm throws an Error that says which algorithms it takes.

jws and jwa

const jws = require('@xufa/jwt/jws'); // sign, verify, decode, isValid, createSign, createVerify (streams)
const jwa = require('@xufa/jwt/jwa'); // jwa('ES256') is { sign(input, key), verify(input, signature, key) }

Coming from jsonwebtoken

  • require('jsonwebtoken') can be replaced by require('@xufa/jwt'): the options, the checks, the messages and the errors are those of jsonwebtoken 9.
  • Added: EdDSA and ES256K; the option type of verify(); named imports from ES modules (import { sign } from '@xufa/jwt').
  • Stricter: tokens with crit are refused; a RegExp in audience tests strings only (jsonwebtoken tests a missing aud as the text "undefined", which /.*/ takes); maxAge: 0 is a limit; clockTolerance must be a number of seconds (jsonwebtoken joins a string such as '5' to exp as text, and takes Infinity); exp, nbf and iat of Infinity or NaN, and empty payloads, are refused when signing.
  • Fixed: an iat of 0 is kept; a payload with keys such as toString signs; a payload that is not JSON and an ECDSA signature of the wrong size are JsonWebTokenErrors, not a SyntaxError or TypeError; decode() of a payload that is not JSON is null, as any token that is not one.
  • From the open pull requests of jws: jws.decode(token, { encoding }) reads the payload in the encoding it was signed with, and createVerify() passes its encoding and json to it.
  • These come from the open pull requests of jsonwebtoken, jws and jwa that hold; the tests of jsonwebtoken that assert the old behaviour are changed by tools/port-jwt (a list of the deviations, checked on each port).
  • No dependencies (jsonwebtoken has jws, jwa, ms, semver and seven of lodash).

Performance

Operations a second against jsonwebtoken 9, the best of 5 rounds (node bench/micro/jwt.js, Node.js 22, Windows 11, i7-13700H), with keys given as text:

Casejsonwebtoken@xufa/jwt@xufa/jwt / jsonwebtoken
HS256 sign36,108163,7344.53x
HS256 verify29,784148,3514.98x
RS256 sign1,0291,7661.72x
RS256 verify17,47835,9452.06x
ES256 sign10,91131,9122.92x
ES256 verify8,47813,4421.59x
decode286,184398,1891.39x

The signatures are the same work, done by node:crypto; the difference is the key. jsonwebtoken tries a secret as a PEM key first (which throws: two thirds of the time of HS256) and parses a PEM key again on each call. @xufa/jwt does not try what has no -----BEGIN, and keeps the KeyObject of each key given as a string. Given KeyObjects, both are as fast (RS256 verify: 35,549 and 36,278). Decoding (and so verifying) parses the header once and splits the token once, where jws does each two and three times. On Linux (WSL2, same machine) the gains are a little smaller: 3.8× and 4.1× for HS256, 1.6× and 1.7× for RS256, 2.6× and 1.5× for ES256, 1.3× for decoding.

With a callback: RSA signatures in the thread pool

With a callback, sign() makes RSA signatures (RS, PS) in libuv's thread pool, so the event loop does not wait for their half a millisecond; jsonwebtoken makes them on the loop. The rest is done on the loop, with a callback too: it takes 20 to 90 µs, about what the hand-off to the pool costs. 64 tokens at a time (node bench/micro/jwt-async.js; bench/results/jwt-async-1.md on Windows, jwt-async-linux-1.md on Linux), in the pool against on the loop:

CaseTokens a second, 4 threads (1 thread)Stall of the loop, p99One token alone
RS256 sign, Windows3.35× (1.02×)42.4 → 0.7 ms538 → 573 µs
RS256 sign, Linux3.33× (1.00×)42.1 → 0.7 ms557 → 604 µs
RS256 verify, Linux1.37× (0.65×)1.2 → 0.4 ms20 → 56 µs
ES256 sign, Linux1.45× (0.66×)1.7 → 0.3 ms23 → 62 µs

An RSA signature gains everywhere: no stall, and 3.3× as many tokens a second when cores are free. The others stall the loop a few milliseconds for 64 tokens at most, and in the pool they lose up to a third of their speed when every core is busy (one thread: a server of a cluster), so they stay on the loop.

Tests

The suites of jsonwebtoken, jws and jwa, ported to vyntra by tools/port-jwt from checkouts of their repositories (requires and mocha's hooks rewritten, tests unchanged): the vectors of RFC 7515, and signatures made by openssl verified, and the other way. And test/security.test.js: algorithm confusion, none, signatures taken off or of other tokens, headers and payloads changed, all-zero ECDSA signatures (CVE-2022-21449) and critical extensions.
