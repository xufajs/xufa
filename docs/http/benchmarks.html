Benchmarks

Requests a second of @xufa/http, fastify and node:http answering by hand, on the same machine, in scenarios from a small JSON reply to a body validated and a large reply serialized. Where xufa is faster, and why, is in From fastify.

HTTP

@xufa/http against fastify 5.12.5 and node:http (where it can answer the same), in requests a second (more is better), on Linux (Ubuntu 26.04 on WSL2, on the same machine; Windows below). In the process, without sockets, the numbers are the cost of the framework alone; over the loopback (autocannon, 100 connections, pipelining 10), the socket and Node.js's HTTP parser are part of the cost of every response.

In the process, xufa is ahead in every scenario: 1.96× on large JSON responses (written as bytes), 1.21× on bodies parsed and validated, and from 1.06× to 1.24× on the rest, level with node:http answering by hand on hello: xufa writes the head of most responses itself (fastHead), where Node.js checks and assembles every header. Over the loopback, the socket and the HTTP parser of Node.js are a part of each response that is the same for both, so the frameworks come closer: from 1.02× to 1.66× where the rounds agree.

On @xufa/http, the routes of the document answer from 1.00× to 1.55× the requests of the same routes on fastify (5 of 6 marked ⚠: their rounds more than 10% apart, so read them as approximate). Validating the replies against the document too (validateResponses) costs what the table says: each reply is checked as plain data before it is serialized (the larger the reply, the more), and the validators are made on the first request of each route, not before (which slows a whole process: see How they are measured).

Run them yourself

node bench/inproc.js                                  # in the process: the cost of the framework alone
node bench/run.js --workers 4                         # over the loopback, with autocannon
node bench/run.js --workers 4 --scenarios hello,big-json --rounds 5 --out results/mine

Every framework and scenario runs in a process of its own, so that no measure inherits the optimizations (or the garbage) of another, and each response is checked before it is measured. The scenarios are in bench/scenarios, the same routes for each framework. Read the processor time per request as much as the requests a second, close what else uses the machine, and prefer Linux: on Windows the loopback is slow and noisy. From Windows, tools/bench-linux runs them in WSL. The options are in bench/README.md; every benchmark of xufa is in Benchmarks.
