HTTP

@xufa/http is the HTTP layer of xufa: a fast web framework for Node.js with the API of fastify, and no dependencies outside the packages of xufa. The package xufa gives it too.

Install

npm install @xufa/http   # or: npm install xufa
const xufa = require('@xufa/http');
// or: import xufa from '@xufa/http'  /  import { xufa } from '@xufa/http'

const app = xufa({ logger: true });

app.register(
  async (users) => {
    users.decorate('db', new Map([[1, { id: 1, name: 'Ada' }]]));

    users.get(
      '/:id',
      {
        schema: {
          params: { type: 'object', properties: { id: { type: 'integer' } } },
          response: { 200: { type: 'object', properties: { id: { type: 'integer' }, name: { type: 'string' } } } },
        },
      },
      async (request, reply) => users.db.get(request.params.id) ?? reply.code(404).send()
    );
  },
  { prefix: '/users' }
);

await app.listen({ port: 3000 });

The API is fastify's

Read fastify's documentation: server options, routes, hooks, plugins and encapsulation, decorators, validation and serialization, content type parsers, reply, request, the logger, inject(), the type providers of TypeScript. All of it applies. Code written for fastify, and plugins written with fastify-plugin, run on xufa.

xufa runs fastify's own test suite (main branch, 6.0.0-alpha.4), ported: 2,248 tests pass, and the 23 skipped are those of ajv-only features. The TypeScript declarations are fastify's, ported with their type tests.

Validation: @xufa/schema

The default validator compiles schemas with @xufa/schema (loaded when a route first has a schema) and reports errors as ajv does (instancePath, keyword, params, message), so attachValidation, schemaErrorFormatter and error handlers work unchanged. By default it converts types (coerceTypes: 'array'), applies defaults and removes additional properties, as fastify configures ajv.

The ajv options that the validator shares are read from ajv.customOptions: coerceTypes, useDefaults, removeAdditional, allErrors, strict (and strictSchema), formats, keywords. Options of the validator itself go in ajv.validatorOptions. 

const app = xufa({
  ajv: {
    customOptions: { coerceTypes: false, allErrors: true, formats: { slug: /^[a-z0-9-]+$/ } },
  },
});

Not supported, because they are ajv's own: ajv plugins (ajv.plugins only accepts []), ajv-errors messages, $async schemas and the $merge and $patch keywords. A validatorCompiler of your own can still use ajv for them.

Names and error codes

  • Error codes are XUFA_ERR_* (fastify's FST_ERR_*), with the same suffixes: XUFA_ERR_NOT_FOUND, XUFA_ERR_VALIDATION... They are in xufa.errorCodes. Warnings are XUFAWRN* and XUFASEC*; errors of plugin loading are BOOT_ERR_* (avvio's AVV_ERR_*).
  • The class of the errors is XufaError; the root of the plugin names is xufa; the diagnostics channels are tracing:xufa.request.handler and xufa.initialization.

Plugins

xufa.plugin() is fastify-plugin:

const { plugin } = require('@xufa/http');

module.exports = plugin(
  async (app, options) => {
    app.decorate('db', await connect(options.url));
  },
  { name: 'db', xufa: '0.x' }
);

The range of versions a plugin needs is xufa in its metadata. Plugins written for fastify load: their fastify range is not checked, since it is a range of fastify versions, and decorators.fastify counts as decorators.xufa.

WebSockets

@xufa/websocket is @fastify/websocket for xufa: routes with { websocket: true }, whose upgrades go through the hooks of the route first. 

app.register(require('@xufa/websocket/plugin'));
app.get('/chat', { websocket: true }, (socket, request) => {
  socket.on('message', (message) => socket.send(`echo: ${message}`));
});

Logger

logger: true, or logger options, create an @xufa/logger: pino's options and API, without transports. Give it a stream (logger: { stream }), or a logger of your own as loggerInstance (pino works). To pretty-print in development, pipe the output: node app.js | pino-pretty.

Responses as bytes

Routes with a response schema whose output can be large (arrays, maps, recursive schemas) write their JSON as UTF-8 bytes and send that Buffer, without making a string first. A string joined from many pieces must be copied into one before it can be written to a socket; for large responses that copy costs about as much as making the JSON. When the route has onSend hooks, they get a string, as in fastify.

Where it is faster

  • xufa writes the head of most responses itself (below), where Node.js checks and assembles every header of every response: most of what a small response costs.
  • The router matches static paths with one map lookup, and compiles its tree into one function once it is hot: 1.15× to 1.67× find-my-way on routes with parameters (Router performance).
  • The query string is left unparsed until request.query is read.
  • Serializers write large responses as bytes (above): about 1.4× fastify on a big JSON response.
  • Validation is compiled by @xufa/schema.

On Linux, xufa answers from 1.06× to 1.96× the requests of fastify in the process, and from 1.02× to 1.66× over the loopback (1.11× on a small JSON response). On Windows, whose loopback is slower, the socket takes most of the time of a small response and the two are about even there. See Benchmarks.

The head of responses

For most responses, xufa writes the status line and the headers itself, as one string, instead of calling res.writeHead(): they are the same bytes (a self-test compares them with those of Node.js when the server starts, and turns this off for good if they differ), and the names and values of the headers are checked as Node.js checks them. It covers HTTP/1.1 responses kept alive with any status from 200, with a body of known length or none (HEAD, 204, 304, empty replies), and headers set on reply.raw too, merged as writeHead() merges them. Node.js writes the others: streams, trailers, HTTP/1.0 and connections that close.

  • reply.raw.getHeaders() gives what it gives after writeHead(): the headers set on reply.raw, and those of the reply too when there were some. Code that wraps res.writeHead() of Node.js (some tracing tools do) does not see these responses go through it.
  • xufa({ fastHead: false }) leaves every head to Node.js.

TypeScript

The declarations are fastify's with the names of xufa: XufaInstance, XufaRequest, XufaReply, XufaPluginAsync, XufaSchema, the type providers... 

import xufa, { type XufaInstance, type XufaPluginAsync } from '@xufa/http';

const users: XufaPluginAsync = async (app) => {
  app.get<{ Params: { id: string } }>('/:id', async (request) => ({ id: request.params.id }));
};

const app: XufaInstance = xufa();
app.register(users, { prefix: '/users' });

Tests

The tests of fastify and of the libraries it uses are ported, not rewritten: a tool of the repository converts their node:test suites to vyntra and renames what fastify calls itself. Tests of what xufa does differently are written apart, so a new port does not overwrite them.
