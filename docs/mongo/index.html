Overview Reference

@xufa/mongo

A MongoDB driver with the API of the official driver for what applications use most, and no dependencies: its own BSON, the wire protocol (OP_MSG), SCRAM authentication, TLS, mongodb+srv://, replica sets, read preferences, retryable writes, transactions and compression. It is about twice as fast as the official driver, and four times for many queries at once. The MongoDB backend of @xufa/orm is made with it.

Quick start

npm install @xufa/mongo
import { MongoClient, ObjectId } from '@xufa/mongo';

const client = await new MongoClient('mongodb://localhost:27017/app').connect();
const users = client.db().collection('users');

const { insertedId } = await users.insertOne({ name: 'Ada', born: new Date('1815-12-10') });
const found = await users.find({ name: /^a/i }, { sort: { name: 1 }, limit: 10 }).toArray();
await users.updateMany({ born: { $lt: new Date('1900-01-01') } }, { $set: { era: 'xix' } });
for await (const group of users.aggregate([{ $group: { _id: '$era', n: { $sum: 1 } } }])) console.log(group);

await client.close();

Cursors

const cursor = users.find({ era: 'xix' }).sort({ born: 1 }).skip(20).limit(10).project({ name: 1 });
const page = await cursor.toArray();

for await (const user of users.find({}, { batchSize: 500 })) process(user); // batches as they are read
const first = await users.find().sort({ _id: 1 }).next();

toArray(), next(), for await, sort, skip, limit, project, batchSize and close(). The next batch is asked for while the one before is read (prefetch: false waits instead).

Inserts

As in the official driver, insertOne and insertMany set _id on the documents without one. insertMany sends its documents in messages of a few megabytes, any number of them, encoding the next while the server inserts one. With { ordered: false }, a large insert is cut in parts that the connections of the pool send at the same time, and the server inserts them in parallel: 50,000 documents go almost four times as fast as with the official driver. 

await events.insertMany(manyEvents, { ordered: false });

Updates and deletes

await users.updateOne({ _id: id }, { $set: { name: 'Ada Lovelace' }, $inc: { logins: 1 } });
await users.updateMany({ 'tags.name': 'old' }, { $set: { 'tags.$[t].name': 'new' } }, { arrayFilters: [{ 't.name': 'old' }] });
await users.replaceOne({ email }, { email, name }, { upsert: true });
await users.deleteMany({ lastLogin: { $lt: yearAgo } });

Write concern

await audit.insertOne(entry, { writeConcern: { w: 'majority', j: true, wtimeout: 5000 } });

Sessions and transactions

const session = client.startSession();
try {
  await session.withTransaction(async () => {
    await accounts.updateOne({ _id: from }, { $inc: { balance: -100 } }, { session });
    await accounts.updateOne({ _id: to }, { $inc: { balance: 100 } }, { session });
  });
} finally {
  await session.endSession();
}

withTransaction(fn) commits when fn ends and aborts when it throws; by hand, startTransaction(), commitTransaction() and abortTransaction(), with inTransaction. Transactions need a replica set or a sharded cluster (MongoDB has none on a single server).

As the official drivers do, withTransaction() runs the whole transaction again when it meets a TransientTransactionError (a write conflict with another transaction, an election, a network error inside it), and its commit again (with a majority write concern) when its result is unknown (UnknownTransactionCommitResult), until { timeout } (120 s) has passed. So fn may run more than once: it should only write in the transaction. Network errors get those labels from the driver; err.hasErrorLabel(label) tells.

Connection strings

mongodb://user:password@host1:27017,host2:27017/app?replicaSet=rs0&authSource=admin, with the options above as parameters. mongodb+srv://cluster.example.com/app finds the hosts in the SRV records of DNS, and the options in its TXT record (as the official driver does, TLS is on).

Replica sets

The members are found from the hosts given (their hello), and checked every heartbeatFrequencyMS, and at once when one fails. Writes go to the primary. When the primary changes, commands wait for the new one, up to serverSelectionTimeoutMS. Sharded clusters (mongos) and single servers work too.

Read preferences

readPreferenceReads go to
primaryThe primary.
primaryPreferredThe primary, or a secondary when there is none.
secondaryA secondary.
secondaryPreferredA secondary, or the primary when there is none.
nearestAny member.

Among the members a preference allows, those within localThresholdMS of the fastest are used in turn.

const report = await orders.aggregate(pipeline, { readPreference: 'secondaryPreferred' }).toArray();

Retryable writes and reads

insertOne, insertMany (each message), updateOne, replaceOne, deleteOne and the commit of transactions are sent again once, on the new primary, when their server fails, with the same session and transaction number, so the server applies them once. Reads are retried once too (retryReads).

Compression

compressors: 'zstd,zlib' asks the server for them; the messages after the handshake are compressed with the first one agreed (none by default). zstd needs Node.js 22.15 or later. Worth it over slow or metered networks.

Authentication and TLS

SCRAM-SHA-256 and SCRAM-SHA-1 (authMechanism), against authSource (the database of the URL, or admin). TLS with tls: true (or ?tls=true) and tlsOptions, the options of tls.connect (certificates, authorities).

BSON

serialize(document) and deserialize(buffer), and the types ObjectId, Binary, Timestamp, Decimal128, Int32, Double, MinKey and MaxKey.

Decimal128.fromString('19.99') makes a decimal of a text, exactly: one of more than 34 digits, or out of the range of the type, throws a RangeError rather than being rounded. toString() gives the text of the standard ('19.99', '1E+3'), toParts() its sign, coefficient and exponent, and Decimal128.fromParts() makes one of them. They give the same bytes and texts as the official bson, from three to fifteen times as fast.

Errors

MongoServerError, with the code of the server (11000 for duplicate keys) and its message; MongoNetworkError for connections; both are MongoError.

Performance

BSON is encoded into a buffer reused for every message, and decoded without calling into C++ for short strings, with the keys of the documents of a reply made once. ObjectIds are three integers (no buffer each). The commands of the same tick are written to the socket with one system call, and many commands share a connection at the same time.

Coming from mongodb

  • The API is that of the official driver for what applications use most; code that uses it runs as it is.
  • int64 values are numbers while they are safe integers (the official driver gives numbers or Long, depending on promoteLongs).
  • Not yet: change streams, GridFS, client-side field level encryption, and read preferences with tags.
