Overview Reference

@xufa/cluster

Runs an app in a cluster of processes, one by CPU, so it uses every core: the primary forks the workers, forks again those that die, and stops them all gracefully. A bus carries events and requests between the processes, so a worker can ask the primary for what only it keeps (counters, caches, locks), and the same code runs in one process in development and tests. Pools of nodes share other servers (models, renderers, anything that takes a few tasks at once) among the workers: the primary hands out their slots in order. No dependencies.

Quick start

npm install @xufa/cluster
import { start, bus } from '@xufa/cluster';
import xufa from 'xufa';
import config from './config.js'; // loadConfig() of @xufa/config: read in every process

start({
  workers: config.cluster.workers, // os.availableParallelism() when undefined; 0 runs everything in one process
  primary: async ({ bus }) => {
    const counts = new Map();
    bus.on('hit', (path) => counts.set(path, (counts.get(path) || 0) + 1));
    bus.on('hits', () => Object.fromEntries(counts)); // a request: its result is the reply
  },
  worker: async ({ id, onShutdown }) => {
    const app = xufa();
    app.addHook('onRequest', async (request) => bus.send('hit', request.url));
    app.get('/stats', () => bus.request('hits'));
    await app.listen({ port: config.server.port, host: '0.0.0.0' }); // every worker listens on the same port
    onShutdown(() => app.close());
  },
});

The configuration (@xufa/config) is a module that every process requires: the primary and each worker read the same files and variables (the workers get those of the primary), so they agree, and one with errors stops the primary before it forks a worker. Its schema can hold the cluster's own options: 

// config.js
export default loadConfig({
  schema: {
    server: { port: { type: 'port', default: 3000, env: 'PORT' } },
    cluster: { workers: { type: 'integer', min: 0, env: 'WORKERS' } }, // WORKERS=0 in development: one process
    database: { url: { type: 'url', env: 'DATABASE_URL', sensitive: true }, backend: { type: 'string', default: 'postgres' } },
  },
});

How it runs

The same file runs in every process. In the primary, start() runs primary and forks the workers; in each worker, it runs worker. Workers listening on the same port share it (Node.js gives each connection to one of them). With workers: 0 there is one process, which runs both functions: the bus delivers its messages in that process, so nothing else changes.

The context

primary and worker get { bus, id, isPrimary, isWorker, onShutdown }: id is the id of the worker (0 in the primary). The module also gives isPrimary and isWorker, and stop().

Graceful shutdown

stop(), SIGINT or SIGTERM (Ctrl+C, a container stopping) stop the cluster: the primary asks every worker to stop; each runs its shutdown functions (onShutdown(fn), in reverse order of registration: close the server first, then the database) and exits; those that do not exit in shutdownTimeout are killed; then the primary runs its own. 

worker: async ({ onShutdown }) => {
  const db = await new Database({ ...config.database }).connect();
  onShutdown(() => db.close()); // runs second
  const app = makeApp(db);
  await app.listen({ port: config.server.port });
  onShutdown(() => app.close()); // runs first: no new requests, the ones in flight end
};

Workers that die

A worker that dies is forked again. One that dies soon after it started (in less than 5 seconds) was failing, so the next waits: half a second, then twice as long each time, up to 30 seconds, so a broken deploy does not fork thousands of processes. onWorkerExit tells you each time.

Events and requests

// In the primary: handlers. Their result (or the promise of it) is the reply of a request.
bus.on('lock', async ({ key }, worker) => locks.acquire(key, worker.id));

// In a worker:
bus.send('hit', '/books'); // an event to the primary
const granted = await bus.request('lock', { key: 'report' }, { timeout: 5000 }); // a request and its reply
bus.broadcast('invalidate', { model: 'Book' }, { others: true }); // to every other worker, through the primary

// In the primary:
bus.sendTo(3, 'reload', {}); // to worker 3
bus.broadcast('config', newConfig); // to every worker

Messages use the IPC of node:cluster with the advanced serialization (structured clone): Dates, Maps, Sets, BigInts, typed arrays and shared references arrive as they were sent. An error thrown by the handler of a request rejects the request with a BusError with its message, name and code.

API of the bus

MemberWhat it does
on(event, handler), off(event, handler)handler(data, sender): the sender is the worker (in the primary) or null.
send(event, data)An event to the primary.
request(event, data, { timeout })The reply of the primary's handler (30 s by default; 0: no limit).
sendTo(workerId, event, data)An event to a worker (from the primary).
broadcast(event, data, { except, others })An event to every worker: from the primary, or from a worker (others leaves the sender out).
workers, clustered, isPrimaryThe ids of the workers; whether messages go to other processes.

bus is the same object in every module of a process; new Bus() makes another.

In one process

With workers: 0, or without start() (tests), the same calls deliver the messages to the handlers of the same process: request() gives the reply of the local handler, broadcast() runs the local handlers. Code written for a cluster runs as it is.

Pools

Some work goes to other servers that take only a few tasks at once each: document converters, renderers, a service with a few licenses. When every worker sends to them on its own, some nodes get too many tasks and others none. A pool puts the nodes in the primary: it keeps their slots (the tasks each node takes at once) and a queue of tickets, and gives each free slot to the next ticket, whichever worker sent it. The work itself (the function, the request it answers, its promise) stays in the worker that waits; only the ticket and the node go through the bus. 

import { createPool } from '@xufa/cluster';

// In the primary (here, the only process): the nodes, one task at once each.
const pool = createPool('converters', {
  nodes: [{ id: 'a', url: 'http://10.0.0.1:8080' }, { id: 'b', url: 'http://10.0.0.2:8080' }],
});
const sleep = (wait) => new Promise((resolve) => setTimeout(resolve, wait));

// In any process: the work runs when a node is free, and gives it back when it ends.
const results = await Promise.all(
  [1, 2, 3].map((n) =>
    pool.use(async (node, { signal }) => {
      await sleep(10 * n); // as fetch(`${node.url}/convert`, { signal })
      return `task ${n} on ${node.id}`;
    })
  )
);
console.log(results);
console.log(pool.stats());
pool.close();
[ 'task 1 on a', 'task 2 on b', 'task 3 on a' ]
{
  name: 'converters',
  nodes: 2,
  slots: 2,
  free: 2,
  running: 0,
  waiting: 0,
  byNode: [
    { id: 'a', slots: 1, running: 0, failures: 0 },
    { id: 'b', slots: 1, running: 0, failures: 0 }
  ]
}

In a cluster, the primary makes the pool and the workers use it by its name:

import { start, createPool, usePool } from '@xufa/cluster';
import { Discovery } from '@xufa/discovery';

start({
  primary: async () => {
    const discovery = new Discovery({ service: 'converters' }); // the converters say they are there
    await discovery.start();
    createPool('converters', { nodes: discovery, slots: (peer) => peer.meta.slots || 1, leaseTimeout: '5m' });
  },
  worker: async () => {
    const converters = usePool('converters');
    const app = makeApp();
    app.post('/convert', (request) =>
      converters.use((node, { signal }) => client.post(`${node.meta.url}/convert`, request.body, { signal }), { retries: 2 })
    );
    await app.listen({ port: 3000 });
  },
});

Nodes and slots

nodes is a list (ids, or objects with an id, given to the work as they are) or a source of peers: an object with peers and the events up and down, as a Discovery of @xufa/discovery. pool.add(node) and pool.remove(id) change them by hand. slots is how many tasks a node takes at once (1), or a function of the node (peer.meta.slots). A free slot goes to the next ticket, higher priority first: on the node with most free slots, and between equals on the one given work longest ago, so the work spreads. Tickets wait while there are no nodes (the nodes can start at zero, see autoscaling).

Using a node

  • pool.use(fn, options) runs fn(node, { signal, attempt }) on a free node and gives the slot back when it ends, whether it gave a result or failed. With retries, a failure tries again on another node while there are others (avoidFailed), for the errors retryOn(err, attempt) says (all).
  • fallback: { node, after, wait }: somewhere else for the work, as a load balancer in front of the nodes. From the attempt after on ({ retries: 5, fallback: { after: 3, node: { id: 'lb', url } } }: three attempts on the pool, then the balancer), or when no node is free in wait (every node down, or busy), fn runs on its node, without a slot, with fallback: true in its context. node can be node(attempt, error), made for each attempt.
  • pool.acquire(options) waits for a node and gives its lease: lease.node, lease.signal, and lease.release(failed), which you call when done.
  • Both take priority (higher first) and signal (to stop waiting: the ticket leaves the queue). pool.stats() gives the nodes, slots, free slots, leases running and tickets waiting, by node too.
  • createPool(name, options) in the primary gives the pool (with use and acquire for the primary itself); usePool(name) in any process gives its client. With workers: 0 both are in the one process.

Slots that come back

A slot comes back to the pool when:

  • the work ends (use), or its lease is released (acquire);
  • its worker dies: its leases end and its tickets leave the queue;
  • its node goes (down, remove): the lease is taken back, the signal of the work aborted (XUFA_POOL_NODE_DOWN), and use tries again on another node when it has retries;
  • the lease passes leaseTimeout: taken back the same way (XUFA_POOL_LEASE_TIMEOUT), so a work that hangs does not keep the node forever.

Autoscaling

The pool emits demand with its stats when they change, and autoscale scales the nodes by it: the nodes wanted are the tickets waiting plus the leases running, divided by perNode, between min and max. Up at once (then not more often than upEvery), down only when the demand was lower for downAfter, to the most it wanted in that time: nodes running work are not taken away because the queue is empty. 

createPool('converters', {
  nodes: discovery,
  autoscale: {
    perNode: 2, // tasks a node takes
    min: 0,
    max: 64,
    upEvery: '10s',
    downAfter: '10m',
    scale: (count) => kubernetes.scaleDeployment('converters', count), // yours
  },
});

Across machines

The primary of each machine keeps its own pool, so with several machines of the app two of them could send work to the same node at once. Two things prevent it, and they go well together:

  • Shared slots (shared: ormSlots(db)): the slots of the nodes are rows of a database of @xufa/orm (any backend, the one the app has). A pool gives a slot only when it takes its row, with an update only one machine can make, so a node never gets more works at once than its slots among every machine. A machine renews the slots it holds (every ttl / 3); those of a machine that died are free again when their ttl passes. When every free slot is taken by others, the tickets wait and the pool looks again every pollEvery, or at once when another machine says it gave a slot back (notify).
  • Busy answers: a node that answers 429 (an error with statusCode or status 429, as those of @xufa/client, or what busy(err) says) is left aside for its Retry-After (or busyFor), and use() runs the work on another node, or on the same one when it is free again, without counting an attempt (up to maxBusy, 20). The pool emits busy. Nodes that refuse what they cannot take protect themselves from any client, of xufa or not. 
import { createPool, ormSlots } from '@xufa/cluster';

// In the primary of every machine: the same database, the same nodes.
const db = new Database({ backend: 'postgres', url: process.env.DATABASE_URL });
createPool('converters', {
  nodes: discovery,
  slots: (peer) => peer.meta.slots || 1,
  shared: ormSlots(db, { ttl: '30s' }), // its model (table xufa_pool_slots) is registered in db: db.sync() makes it
  notify: netcache, // a slot given back is told to the other machines: their tickets waiting are served at once
  pollEvery: '2s', // what notify misses: datagrams lost, the slots of machines that died
});

// A node that refuses: the work goes elsewhere.
app.post('/infer', async (request, reply) => {
  if (running >= capacity) return reply.code(429).header('retry-after', '1').send();
  // ...
});

notify is a NetCache of @xufa/netcache (its publish, over TCP to the machines connected), a Discovery of @xufa/discovery (datagrams, which can be lost) or an object with publish(data) and subscribe(handler). The slots that come back without a message (those of a machine that died) are still found every pollEvery. pool.health({ minNodes, maxWaiting }) (of the pool, or of usePool() in a worker) is a check of xufa.health: down with fewer nodes than minNodes (1), degraded with more tickets waiting than maxWaiting, with the nodes, slots and works; not critical by default. store.held(pool) gives the slots held now by node. With @xufa/queue, a job whose node answers busy fails that run (tried again after its backoff) and the node is left aside.

Options and errors

OptionDefaultWhat it does
nodesA list, or a source of peers (peers, up, down).
slots1Tasks a node takes at once, or (node) => number.
leaseTimeoutnoneA lease longer is taken back ('5m').
waitTimeoutnoneA ticket that waits longer is rejected.
maxWaitingnoneTickets waiting at most; more are rejected at once.
autoscale{ scale, perNode, min, max, upEvery, downAfter, initial }.
sharedA store of slots shared by the machines: ormSlots(db, { ttl }).
notifyTells the other machines when a slot comes back: a NetCache, a Discovery, or { publish, subscribe }.
pollEvery'500ms'How often to look again when other machines hold every free slot.
busyFor'1s'How long a node that answered busy is left aside, when it does not say.
busy429(err) => boolean: which errors are busy answers (also an option of usePool).

Errors are PoolErrors with a code and a statusCode: XUFA_POOL_FULL and XUFA_POOL_WAIT_TIMEOUT (503), XUFA_POOL_LEASE_TIMEOUT (504), XUFA_POOL_NODE_DOWN (502), XUFA_POOL_BUSY (429, a busy answer of your own), XUFA_POOL_CLOSED, and XUFA_POOL_UNKNOWN when no process made the pool. The pool also emits up, down, revoke, busy and scale. With @xufa/queue, jobs of a kind wait for a node of a pool before they are claimed.

Shared state

Other packages of xufa use the bus for what the workers must share:

  • @xufa/orm: SharedCache({ bus }) keeps the cache of the models in the primary, one copy for every worker; LocalCache({ bus }) keeps one in each worker and invalidates the others.
  • @xufa/auth: the lockout of logins can keep its counts in the primary, so every worker counts the same failures.

Faults (tests of resilience)

bus.faults (of @xufa/faults) loses, delays or holds the messages a process sends, to see what the app does when its workers miss events or requests get no reply. 

bus.faults.drop({ events: 'cache:invalidate', rate: 0.1 }); // 1 in 10 lost
bus.faults.delay({ operations: 'broadcast', ms: 500 });
bus.faults.fail({ operations: 'request', events: 'lock' }); // a BusError (code XUFA_FAULT)
bus.faults.drop({ operations: 'request' }); // no reply: the timeout of the request
  • Operations: send, sendTo, broadcast (the group events) and request; the filter events.
  • Events: fail, down and drop lose them; delay delivers them late; hang when released.
  • Requests: fail and down reject with a BusError; drop rejects after the timeout; delay and hang wait before sending.
