Guide

This guide builds a small application with xufa: an HTTP API whose data lives in a database, with validation, logins, migrations and tests. Each part used here is a package of its own; the HTTP and ORM pages have the whole of each.

Getting started

xufa needs Node.js 22.22.3 or later (24.15 or later on the 24 line), and nothing else.

npm install xufa

xufa gives the HTTP framework (@xufa/http) and, as xufa/orm, the ORM (@xufa/orm). The ORM talks to SQLite through node:sqlite, and to PostgreSQL and MongoDB through its own drivers: there is no driver to install.

Your first app

The HTTP layer has the API of fastify. If you know fastify, you know it: routes, hooks, plugins, decorators and schemas are the same, and code written for fastify runs on it. 

// app.js
import xufa from 'xufa';

function build() {
  const app = xufa({ logger: true });

  app.get('/health', async () => ({ ok: true }));

  app.register(
    async (users) => {
      users.get('/:id', async (request, reply) => {
        if (request.params.id !== '1') return reply.code(404).send();
        return { id: 1, name: 'Ada' };
      });
    },
    { prefix: '/users' }
  );

  return app;
}

export { build };

if (require.main === module) build().listen({ port: 3000 });

Plugins written for fastify (with fastify-plugin) load as they are. For your own, use xufa.plugin(), which is fastify-plugin: 

import { plugin } from 'xufa';

export default plugin(
  async (app, options) => {
    app.decorate('mailer', createMailer(options));
  },
  { name: 'mailer', xufa: '0.x' }
);

Configuration

xufa/config (@xufa/config) reads the configuration of the app from layers: config/default.*, the file of the environment (config/production.yaml when NODE_ENV is production), local files of the machine, .env files and the variables of the environment. Its schema converts the values (the PORT of the environment is a text; server.port is a number), fills in defaults, and stops the app with every error at once. Put it in a module of its own, and require it where it is needed: 

// config.js
import { loadConfig } from 'xufa/config';

export default loadConfig({
  envPrefix: 'APP', // APP__SERVER__PORT=8080 sets server.port
  schema: {
    server: { port: { type: 'port', default: 3000, env: 'PORT' } },
    database: {
      backend: { type: 'string', values: ['sqlite', 'postgres', 'mongodb'], default: 'sqlite' },
      filename: { type: 'string', default: 'app.db' },
      url: { type: 'url', env: 'DATABASE_URL', sensitive: true },
    },
    auth: { jwtKey: { type: 'string', env: 'JWT_KEY', required: true, min: 32, sensitive: true } },
    jobs: { purgeEvery: { type: 'duration', default: '1h' } },
  },
});
# config/production.yaml
database:
  backend: postgres
jobs:
  purgeEvery: 10m
# .env: of this machine, for development (keep it out of git)
JWT_KEY=a-key-for-development-only-32-bytes-or-more

The configuration is frozen, and config.get('database.url') fails for a key that is not there. console.log(config) and JSON.stringify(config) show it without its secrets (the keys sensitive, and those named as secrets: password, token...). Missing the key in production, the app does not start: 

The configuration (production) has errors:
  - auth.jwtKey: is required (set JWT_KEY)

Values can be templates of the variables and of other keys: url: 'http://{{ config.server.host }}:{{ config.server.port }}'. Configuration of servers (HTTP, Consul) and secrets (Vault, the files of Docker and Kubernetes) are layers too, with await loadRemoteConfig({ remote: [...] }). The rest is in Configuration. 

// app.js
import config from './config.js';
// ...
if (require.main === module) build().listen({ port: config.server.port, host: '0.0.0.0' });

Adding the ORM

Models are classes with their fields. The same models run on every backend: sqlite, postgres, mongodb, and memory for tests. 

// models.js
import { Model, fields } from 'xufa/orm';

class Author extends Model {
  static fields = {
    name: fields.string({ maxLength: 100 }),
    email: fields.string({ unique: true, null: true }),
  };

  static options = { ordering: ['name'] };
}

class Book extends Model {
  static fields = {
    title: fields.string({ maxLength: 200 }),
    pages: fields.integer({ null: true, min: 1 }),
    author: fields.foreignKey(() => Author, { relatedName: 'books' }),
    createdAt: fields.datetime({ autoNowAdd: true }),
  };
}

export { Author, Book };

The ORM's plugin connects the database when the app starts, gives it as app.db, and closes it with the app. sync: true creates the tables that do not exist, which is enough to start; migrations are for what comes after. 

import xufa from 'xufa';
import * as orm from 'xufa/orm';
import config from './config.js';
import { Author, Book } from './models.js';
import books from './routes/books.js';

function build({ database } = {}) {
  const app = xufa({ logger: true });
  // { backend: 'sqlite', filename: 'app.db' }, or in production { backend: 'postgres', url: 'postgres://...' }
  const db = database || new orm.Database({ ...config.database });
  db.register(Author, Book);
  app.register(orm.plugin, { database: db, sync: true });
  app.register(books, { prefix: '/books' });
  return app;
}

Models and routes

Model.objects is a QuerySet, as in Django: refine it with filter, exclude, orderBy, limit..., and await it. Conditions follow relations with __. Model.schema() gives the schema of the objects (typed, as @xufa/schema makes them), for the schemas of routes. 

// routes/books.js
import { s } from 'xufa/schema';
import { Book } from '../models.js';

export default async function books(app) {
  const body = s.omit(Book.schema({ input: true }), ['id', 'createdAt']);

  app.get('/', async (request) => {
    const { author, minPages = 0 } = request.query;
    let books = Book.objects.filter({ pages__gte: minPages }).selectRelated('author').orderBy('-pages');
    if (author) books = books.filter({ author__name__icontains: author });
    return books.limit(50);
  });

  app.get('/:id', async (request) => Book.objects.get({ pk: request.params.id }));

  app.post('/', { schema: { body } }, async (request, reply) => {
    reply.code(201);
    return Book.objects.create(request.body);
  });

  app.patch('/:id', { schema: { body: s.partial(body) } }, async (request) => {
    const book = await Book.objects.get({ pk: request.params.id });
    Object.assign(book, request.body);
    return book.save();
  });

  app.delete('/:id', async (request, reply) => {
    await Book.objects.filter({ pk: request.params.id }).delete();
    reply.code(204);
  });
};

These routes are what orm.resource() makes for a model, with filters, ordering, search and pages: app.register(orm.resource(Book, { filters: ['author'], related: ['author'] }), { prefix: '/books' }). Write them by hand when they do something else.

A foreign key keeps its key in its own attribute: author is the object (once loaded), authorId the key. The schema of the body asks for authorId. Objects serialize with their loaded relations (toJSON()), so a book found with selectRelated('author') is sent with its author: 

[{ "id": 1, "title": "Notes", "pages": 120, "authorId": 1, "createdAt": "2026-10-04T07:36:54.639Z",
   "author": { "id": 1, "name": "Ada", "email": null } }]

Validation and errors

Values are checked twice. The schema of a route (here, the one Book.schema() made) rejects a request before the handler runs, as fastify does. The fields check their values again when an object is saved: types, maxLength, min and max, choices, null, and your own validate functions, so routes without a schema are safe too. With the plugin, both become responses:

ErrorResponse
The schema of the route (@xufa/schema)400, as fastify answers it
ValidationError of the ORM400, with the messages of each field in errors
NotFoundError (get() found nothing)404
 
{ "statusCode": 400, "code": "XUFA_ERR_VALIDATION", "error": "Bad Request", "message": "body/pages must be >= 1" }
{
  "statusCode": 400,
  "code": "XUFA_ORM_ERR_VALIDATION",
  "error": "Bad Request",
  "message": "Validation failed for Book: pages: Ensure this value is at least 1.",
  "errors": { "pages": ["Ensure this value is at least 1."] }
}
{ "statusCode": 404, "code": "XUFA_ORM_ERR_NOT_FOUND", "error": "Not Found", "message": "No Book matches the query" }

The schemas of routes that are not of a model are written with xufa/schema (@xufa/schema): plain JSON Schemas, made by code, from which the bodies of creates and updates are made too. 

import { s } from 'xufa/schema';

const Review = s.object(
  { stars: s.integer({ minimum: 1, maximum: 5 }), text: s.optional(s.string({ maxLength: 2000 })), bookId: s.integer() },
  { additionalProperties: false }
);
app.post('/reviews', { schema: { body: Review } }, handler);
app.patch('/reviews/:id', { schema: { body: s.partial(s.omit(Review, ['bookId'])) } }, handler);

Users and logins

xufa/auth (@xufa/auth) hashes passwords, gives JSON Web Tokens and checks them. Its plugin adds the routes of logging in, refreshing and logging out, with failed logins locked after five tries; you give it how to find a user: 

// models.js
import * as auth from 'xufa/auth';

class User extends Model {
  static fields = {
    email: fields.string({ unique: true }),
    password: fields.string(), // auth.hashPassword(password)
    role: fields.string({ default: 'user' }),
  };
}

class RefreshToken extends Model {
  static fields = auth.refreshTokenFields(fields);

  static options = { indexes: [{ fields: ['expiresAt'], expireAfter: 0 }] }; // deleted when they expire
}
// in build()
db.register(Author, Book, User, RefreshToken);
// and expire: true in the plugin of the ORM: it deletes the refresh tokens that expired (their TTL index)
app.register(auth.plugin, {
  keys: config.auth.jwtKey, // 32 bytes or more: the schema checks it
  login: {
    findUser: (email) => User.objects.filter({ email: email.toLowerCase() }).first(),
    claims: (user) => ({ sub: String(user.id), role: user.role }),
  },
  refresh: { store: auth.modelStore(RefreshToken) },
});

Routes say who may use them with config: { auth }: true for any user, a role, or a function of the user. Without a valid token they answer 401, and 403 without the role: 

app.post('/', { schema: { body }, config: { auth: true } }, async (request, reply) => { ... });
app.delete('/:id', { config: { auth: 'admin' } }, async (request, reply) => { ... });
curl -X POST localhost:3000/auth/login -H 'content-type: application/json' \
  -d '{"username":"ada@example.com","password":"analytical"}'
# {"accessToken":"eyJ...","tokenType":"Bearer","expiresIn":900,"refreshToken":"..."}
curl -X DELETE localhost:3000/books/1 -H 'authorization: Bearer eyJ...'

Codes of authenticator apps (TOTP), refresh tokens in cookies, keys per tenant and the rest are in Auth.

Migrations

Migrations work as in Django. makeMigrations compares the models with the schema that the migration files describe, and writes a file with the operations between them. migrate applies the files not applied yet, each in a transaction where the database has them. 

// scripts/make-migrations.js
import { Database } from 'xufa/orm';
import config from '../config.js';
import { Author, Book } from '../models.js';

async function main() {
  const db = new Database({ ...config.database }).register(Author, Book);
  await db.makeMigrations({ dir: 'migrations' }); // writes migrations/0002_auto.js, for example
}

main();
// The app applies them when it starts.
app.register(orm.plugin, { database: db, migrate: { dir: 'migrations' } });

The files are JavaScript, and you can edit them. Renames are not detected: write { op: 'renameColumn', table, from, to } or { op: 'renameTable', from, to }. For SQL of your own, write { op: 'sql', sql }; for data migrations, { op: 'run', fn: async (db) => {} }.

A project in one file

Django's settings.py and the project's urls.py are names and values, and so is a project of xufa: xufa.yaml at its root (or xufa.yml, xufa.json, xufa.js when a value must be a function). xufa puts the app together from it: sessions, bodies of forms, templates, static files, emails, accounts and their pages, roles, the admin, error pages, redirects. The project keeps only its apps. 

# xufa.yaml
name: LocalLibrary
apps: [accounts, catalog]           # INSTALLED_APPS: folders
database: { url: sqlite:data/locallibrary.db, audit: { redact: [password] } }
siteUrl: http://127.0.0.1:8000
mail: { from: LocalLibrary <library@example.com> }
auth: { user: accounts.User, loginBy: username, pages: /accounts }
rbac:
  groups: accounts.Group            # roles edited in the admin
  roles: { librarian: ['*.view', Book.*, Author.*] }
admin: { title: LocalLibrary administration }
views: { baseTemplate: base_generic, paginateBy: 10 }
redirects: { /: index }

The environment goes over the file, as Django's settings read it: DATABASE_URL, SECRET_KEY, DEBUG, PORT, HOST, SITE_URL, EMAIL_URL, and APP__<KEY>__<KEY> for any other key. xufa start serves it, and every command (migrate, makemigrations, seed, shell, test, routes, createsuperuser) finds it. In code, await loadProject(dir) gives the project, project.build() its app, and reverse(name, ...params) of xufa/project the address of a named route.

An app is a folder: models.js and models.yaml (models as data: a spec of the ORM, whose relations name models of the app, or of others as accounts.User; in development, edited on the data model page of the admin too; with designer: database, kept in the database as versions instead, in production too), urls.yaml (its routes, of the views views.js exports), admin.yaml (its models in the admin, by name, with their options), templates/, static/ and migrations/. Its urls.yaml is its urls.py: 

# catalog/urls.yaml
prefix: /catalog
routes:
  - { path: /, name: index, view: index }               # a function of views.js
  - { path: mybooks/, name: my-borrowed, view: LoanedBooksByUser }   # a view of a class
  - { path: book/<uuid:pk>/renew/, name: renew-book, view: renewBook, methods: [GET, POST], permission: BookInstance.markReturned }
  - { path: about/, name: about, template: about }      # a TemplateView
  - crud: Book                                          # books, book-detail, book-create, book-update, book-delete
    fields: [title, author, summary, isbn, genre, language]
    list: { selectRelated: author }
    detail: { selectRelated: [author, language], prefetchRelated: [genre, bookInstanceSet] }
    delete: { blockedText: "You can't delete this book until all copies have been deleted:" }

crud gives the five pages of a model with the names of the Django tutorial, Book.add, .change and .delete for the forms, and templates of the app (catalog/book_list.html...) or, when it has none, the built-in ones of @xufa/views, which extend views.baseTemplate. A model whose <model>-detail route exists gets absoluteUrl without writing it. The LocalLibrary example is a whole project in this form.

Jobs in the background, pipelines and tenants are keys of the file too, and the admin shows them (Jobs, Pipeline runs, and the tenant to choose): 

queue: { work: { concurrency: 2 } }   # @xufa/queue in the database; work: false leaves it to xufa work
pipelines: true
tenants:
  apps: [catalog]                       # a database for each tenant, with the models of these apps
  database: { url: 'sqlite:data/tenants/{id}.db' }
  list: [central, north]                # or { model: accounts.Branch, field: slug, label: name }
  labels: { central: Central library }
  resolve: subdomain                    # the tenant of a request (north.example.com), or user.<field>
// The apps of tenants (catalog) have their tables in each tenant's database only, migrated when it is first opened:
// not in the project's (xufa migrate leaves them out). Outside a tenant, their models are an error, never another
// tenant's data.

// catalog/jobs.js: the jobs of the app, by name (app.queue.enqueue('remind', { loan: 7 }))
export async function remind({ loan }) {
  // ...
}
export const report = { attempts: 5, timeout: '2m', run: async ({ month }) => ({ month }) };

// catalog/blocks.js: the blocks of its pipelines
export const fetchCover = async (book) => ({ ...book, cover: `${book.isbn}.jpg` });
# catalog/pipelines.yaml: its pipelines, as data
- name: new-book
  steps:
    - { id: cover, block: fetchCover }
    - { id: approve, block: wait, after: cover }

The queue is that of the project's database (db.queue, app.queue; its tables are in the migrations of the project), its workers run in xufa start unless work: false (then xufa work runs them), and db.pipelines runs the pipelines on it. Each tenant's database is made the first time it is used, with the migrations of its apps; the other models (the users, the sessions, the jobs) stay in the project's. Without resolve, only the admin chooses a tenant; project.tenants().run(id, fn) runs code in one (a seed gets the project too: export default async (db, models, { project }) => {}). The Helpdesk example has organizations as tenants, by subdomain.

Apps

Without a project file, the same is code. A project grows as Django's, in apps (INSTALLED_APPS): each a folder with its models, its routes, its templates (templates/), its static files (static/), its models in the admin and its migrations (migrations/). Its tables are named by it, as Django's db_table: catalog_book, catalog_bookinstance (unless a model gives its own table). 

// catalog/app.js (Django's apps.py)
import { defineApp } from 'xufa/apps';
import * as models from './models.js';
import views from './views.js';
import admin from './admin.js';

export default defineApp({
  name: 'catalog',
  dir: import.meta.dirname,
  models, // a list or a module of models (or a function that gives them)
  routes: views, // a plugin of routes (urls.py), under prefix
  admin: admin.models, // its entries in the admin (admin.py)
  ready: (app) => {}, // AppConfig.ready
});
// app.js: the project
import { Apps } from 'xufa/apps';
import accounts from './accounts/app.js';
import catalog from './catalog/app.js';

const APPS = new Apps([accounts, catalog], { migrations: 'migrations' });

function database() {
  const db = APPS.register(Database.fromUrl(process.env.DATABASE_URL)); // the models of the apps
  db.sessions = ormStore(db); // models of no app: the migrations of the project
  return db;
}

function build() {
  const app = xufa();
  app.register(orm.plugin, { database: database(), migrate: (db) => APPS.migrate(db) });
  app.register(template.plugin, { root: ['templates', ...APPS.templates] }); // the project's first
  app.register(xufa.staticFiles, { root: APPS.static, prefix: '/static/' });
  app.register(APPS.plugin); // the routes of the apps, and their ready()
  app.register(admin, { prefix: '/admin', models: APPS.admin });
  return app;
}

export { build, database, APPS };

With APPS in app.js, xufa makemigrations writes a migration in the folder of each app that changed (xufa makemigrations catalog --name add_isbn: of one), xufa migrate applies them app after app (those of the project first: the tables of no app, as the sessions, as Django's contrib apps), and xufa showmigrations lists them by app. They are recorded by app (catalog.0001_initial), so apps can have the same numbers. List the apps that others point to first.

Several databases

Databases holds several databases by name, and routes each model to one of them: the database option of the model, or the routes given, or the default database. 

import { Databases } from 'xufa/orm';
import config from './config.js'; // with events: { url: { type: 'url', env: 'EVENTS_URL', sensitive: true } } in its schema

const dbs = new Databases(
  {
    default: { ...config.database },
    events: { backend: 'mongodb', url: config.events.url },
  },
  { routes: { Event: 'events' } }
);
dbs.register(Author, Book, Event);
await dbs.connect();
await dbs.migrate({ dir: 'migrations' }); // migrations/default and migrations/events

Relations between models of different databases are followed with more queries (prefetchRelated, load(), reverse accessors, deletes); a query cannot join them.

A database per tenant

Tenants opens a database for each tenant the first time it is used, from your config(tenantId). Code run in a tenant uses its database: inside it, Book.objects is the books of that tenant. The databases of the last max tenants used stay open. 

import { Tenants } from 'xufa/orm';

const tenants = new Tenants({
  models: [Author, Book],
  config: async (id) => ({ backend: 'postgres', url: `postgres://app@db:5432/tenant_${id}` }),
  setup: (db) => db.migrate({ dir: 'migrations' }),
});

// Each request runs in its tenant: resolve() says which, authorize() whether its user may use it.
app.register(orm.plugin, {
  tenants: {
    tenants,
    resolve: (request) => request.headers['x-tenant'],
    authorize: (request, id, reply) => app.auth.canUseTenant(request, id, reply),
  },
});

// Or, outside requests:
await tenants.run('acme', () => Book.objects.count());

A request without a tenant gets a 400 (unless required: false), and a tenant whose config gives nothing gets a 404.

A tenant taken from a header is only what the client says: check that the user may use it, before its database is opened. With the auth plugin, a user may use the tenants of its claims ('*' is every tenant), so the login puts them in its tokens; a request of a tenant that is not the user's gets a 403, and one without a user a 401. Routes can ask for more: 

// in the options of the auth plugin
login: { findUser, claims: (user) => ({ sub: String(user.id), role: user.role, tenants: user.tenants }) },

app.delete('/books/:id', { config: { auth: { tenant: true, roles: 'admin' } } }, handler); // an admin of this tenant
app.get('/admin/stats', { config: { auth: { tenant: '*' } } }, handler); // a user of every tenant

Without authorize, any request may use any tenant it names, and the app warns when it starts.

Caching objects

A model with the cache option answers get() by primary key, or by a unique field of its indexes, from a cache. Saving or deleting an object removes it, and update() or delete() of a QuerySet clears the model. Inside transactions the cache is neither read nor filled. 

class User extends Model {
  static fields = { email: fields.string({ unique: true }), name: fields.string() };

  static options = { cache: { ttl: 60000, indexes: ['email'] } };
}

await User.objects.get({ email: 'ada@example.com' }); // the database
await User.objects.get({ email: 'ada@example.com' }); // the cache

The cache of a database is a MemoryCache (an LRU in the process) unless you give one: new Database({ ..., cache }). In a cluster, a SharedCache keeps one copy in the primary process, and a LocalCache keeps a copy in each process, with invalidations sent to the others.

Running in a cluster

@xufa/cluster runs an app in a process per CPU: it forks the workers, forks again those that die, and stops them all gracefully on SIGINT and SIGTERM. Its bus carries messages between the processes. 

import { start, bus } from '@xufa/cluster';
import { Database, LocalCache } from 'xufa/orm';
import config from './config.js'; // read in each process: the primary and every worker
import { build } from './app.js';

start({
  primary: async ({ bus }) => {
    let visits = 0;
    bus.on('visit', () => (visits += 1));
    bus.on('visits', () => visits); // a request: the result is the reply
  },
  worker: async ({ onShutdown }) => {
    const database = new Database({ ...config.database, cache: new LocalCache({ bus }) });
    const app = build({ database });
    app.addHook('onRequest', async () => bus.send('visit'));
    app.get('/visits', () => bus.request('visits'));
    await app.listen({ port: config.server.port, host: '0.0.0.0' });
    onShutdown(() => app.close());
  },
});

With workers: 0 everything runs in one process, and the same bus calls work: handy in development. A configuration with errors stops the primary before it forks a worker.

Jobs

xufa/scheduler (@xufa/scheduler) runs jobs every so often, on cron expressions, or once: each on a timer of its own, without overlapping runs, with timeouts and retries. In a cluster, run them in the primary, not in every worker; on several machines, a lock in the database makes one of them run each time, and its history catches up the times missed while it was down. 

import { start } from '@xufa/cluster';
import { Database } from 'xufa/orm';
import { Scheduler, ormLock, ormHistory } from 'xufa/scheduler';
import config from './config.js';
import { Author, Book } from './models.js';
import { purgeOldUploads, sendReport } from './jobs.js';

start({
  primary: async ({ onShutdown }) => {
    const db = new Database({ ...config.database }).register(Author, Book);
    const scheduler = new Scheduler({ lock: ormLock(db), history: ormHistory(db) }); // their tables: db.sync()
    await db.connect();
    await db.sync();
    scheduler.add({
      name: 'purge old uploads',
      every: config.jobs.purgeEvery, // 10 minutes in production, an hour elsewhere
      catchUp: true,
      retries: 2,
      run: ({ signal }) => purgeOldUploads({ signal }),
    });
    scheduler.add({ name: 'daily report', cron: '0 8 * * mon-fri', timezone: 'Europe/Madrid', timeout: '5m', run: sendReport });
    scheduler.start();
    onShutdown(async () => {
      await scheduler.stop(); // the runs going on end first
      await db.close();
    });
  },
  worker: async ({ onShutdown }) => { /* the app, as above */ },
});

The command line

xufa is also a command, as Rails' rails, Laravel's artisan and Django's manage.py: it makes a project and its apps, makes and applies migrations, loads seeds, and opens a REPL with the models. 

npx xufa new shop                     # xufa.yaml, templates/base.html, home/ (its first app), seeds/, test/
cd shop && npm install
npx xufa startapp catalog             # catalog/: models.js, urls.yaml, views.js, admin.yaml, templates/catalog/
npx xufa makemigrations && npx xufa migrate

xufa new shop --api makes an app of an API instead, without a project file: app.js, server.js, a model in each file of models/, a plugin of routes in each file of routes/, and jobs; xufa generate writes its models and resources.

cd shop && npm install

CommandWhat it does
xufa new <folder>A new project (Django's startproject): xufa.yaml, templates/base.html, its first app (home, or --app name) with a home page, seeds/ and a test of useTestApp()
xufa startapp <name>A new app of the project (Django's startapp): models.js, urls.yaml, views.js, admin.yaml, templates/<name>/, migrations/; added to apps of xufa.yaml
xufa new <folder> --apiA new app of an API: app.js (build(), database(), jobs()), server.js, a model in each file of models/, a plugin in each file of routes/ at the path of its name, jobs of the queue in jobs/, a test
xufa generate model <Name> field:type...A model (models/<name>.js) and its migration. Types: string, text, integer, bigint, float, decimal, boolean, date, datetime, json, uuid, email, references; modifiers :null, :unique, :index; createdAt and updatedAt unless --no-timestamps
xufa generate resource <Name> ...The model, and its routes: routes/<names>.js with orm.resource() (list with filters, search, ordering and pages; get, create, update, delete)
xufa makemigrations, migrate, showmigrationsThe migrations of the models, as Django's (with designer: database, those kept there too; makemigrations leaves out the apps whose models are there)
xufa ejectThe models kept in the database (designer: database) as files again: each app's models.yaml and its migrations, with their names (applied already); then a version with none, so every server starts again with the files
xufa routesThe routes of the app
xufa seed [name...]Runs the seeds of seeds/, each in a transaction: fixtures of YAML or JSON (objects by model), or functions of the database and its models (made with factories): data for development
xufa startServes the project of xufa.yaml (PORT, HOST), applying its migrations
xufa createsuperuserA superuser of the model of users (AbstractUser of @xufa/auth): --username, --email, the password asked twice; --noinput with XUFA_SUPERUSER_PASSWORD
xufa shellA REPL with app, db, queue and the models (await Book.objects.count())
xufa devThe server, started again when a file of the project changes (its code, and its YAML: xufa.yaml, models.yaml...; not node_modules nor data/); an app of server.js under node --watch
xufa workWorkers of the queue (--concurrency 4 --queues mail,reports)
xufa downThe maintenance mode on: a 503 for every request but /health (--message, --retry 60, --allow ip,ip, --secret [path]: a path that lets a browser through). This machine (.xufa/down.json), or every one with --everywhere (in the database)
xufa upThe maintenance mode off (--everywhere: in the database too)
xufa test [files...]The tests of the app with NODE_ENV=test: by vyntra when the app has it (--runner node or vyntra to choose), else node --test. Each test in a transaction rolled back: rollbackEach
xufa healthThe checks of GET /health, run once: their status, time and errors (exit code 1 when the app is down)

The database is DATABASE_URL (sqlite:data/app.db by default; postgres://..., mongodb://..., memory:): Database.fromUrl() of the ORM. The app shows errors to browsers with xufa.devErrors unless NODE_ENV is production, its jobs run in @xufa/queue, and it has the routes of its health (its database and its queue) and the maintenance mode. For test data, factories.

Testing

app.inject() sends fake requests without a socket. With the memory backend, or SQLite in memory, each test gets a fresh database in no time. 

import { Database } from 'xufa/orm';
import { build } from './app.js';
import { Author } from './models.js';

describe('books', () => {
  let app;

  beforeEach(async () => {
    app = build({ database: new Database({ backend: 'sqlite', filename: ':memory:' }) });
    await app.ready();
  });

  afterEach(() => app.close());

  it('creates and finds a book', async () => {
    const author = await Author.objects.create({ name: 'Ada' });
    const created = await app.inject({
      method: 'POST',
      url: '/books',
      payload: { title: 'Notes', pages: 120, authorId: author.pk },
    });
    expect(created.statusCode).toBe(201);
    const found = await app.inject({ url: `/books/${created.json().id}` });
    expect(found.json().title).toBe('Notes');
  });

  it('refuses a book of no pages', async () => {
    const author = await Author.objects.create({ name: 'Ada' });
    const res = await app.inject({ method: 'POST', url: '/books', payload: { title: 'Empty', pages: 0, authorId: author.pk } });
    expect(res.statusCode).toBe(400);
  });
});

In a project, useTestApp() of xufa/testing is Django's TestCase: it builds the app of xufa.yaml once for the file (SQLite in memory, migrated, light password hashes, the emails kept), rolls back each test, and loads the fixtures it is given before each one. Each tenant gets a database in memory too (tenantsUrl), made the first time a test uses it and rolled back after each test as that of the project. It works with the hooks of the runner, globals or those of node:test. 

import { test } from 'node:test';
import assert from 'node:assert/strict';
import { useTestApp } from 'xufa/testing';

const app = useTestApp({ fixtures: ['library'] }); // fixtures/library.yaml (or seeds/)

test('a reader sees what they borrowed', async () => {
  await app.createUser('rita', 'a-password'); // by auth.loginBy
  const client = app.client(); // Django's self.client
  await client.login({ username: 'rita', password: 'a-password' });
  const res = await client.get(app.reverse('my-borrowed'));
  assert.equal(res.statusCode, 200);
  assert.equal(app.mails.length, 0); // Django's mail.outbox
});

Fixtures are data files (Django's loaddata): objects by model, in order. $key names an object, relations point to it by that name, dates take today and days from it, and users get their passwords hashed. xufa seed runs them from seeds/ too, next to seeds of JS; $unless runs a file only once. 

# seeds/library.yaml
$unless: { User: { username: admin } }
User:
  - { username: admin, password: xufa-library, isStaff: true, isSuperuser: true }
  - { $key: rita, username: rita, password: xufa-library }
Author:
  - { $key: leguin, firstName: Ursula, lastName: Le Guin, dateOfBirth: 1929-10-21 }
Book:
  - { $key: earthsea, title: A Wizard of Earthsea, author: $leguin, isbn: '9780547773742', genre: [$fantasy] }
BookInstance:
  - { book: $earthsea, status: o, borrower: $rita, dueBack: +14d }

xufa's own tests run with vyntra, but any runner with the API of Jest or Vitest works.

What the app does when its database fails is tested too: db.faults makes operations fail, wait or hang (Faults). 

it('answers 503 while the database is down', async () => {
  db.faults.down();
  expect((await app.inject('/books')).statusCode).toBe(503);
  db.faults.up();
});

it('retries a write that failed once', async () => {
  const rule = db.faults.fail({ operations: 'insert', models: [Book], times: 1 });
  await app.inject({ method: 'POST', url: '/books', payload });
  expect(rule.hits).toBe(1);
  expect(await Book.objects.count()).toBe(1);
});

The rest fails the same way, with the rules of @xufa/faults: cache.faults (the app answers without its cache), client.faults of the APIs it calls (failed connections, respond({ status: 503 }), hangs ended by the timeout) and bus.faults of the cluster (messages lost or late). xufa/faults/register in the setup files of the runner clears every fault after each test, so one that fails before its up() leaves none to the next; xufa/faults/register-strict also fails a test that ends with faults still set.

TypeScript

The HTTP layer has fastify's declarations, with xufa's names: XufaInstance, XufaRequest, XufaReply, the type providers. The ORM types models from their fields: give the model an interface of the same name, and use Model.query() for typed QuerySets. 

import xufa, { type XufaInstance } from 'xufa';
import { Model, fields, type Fields } from 'xufa/orm';

const bookFields = { title: fields.string(), pages: fields.integer({ null: true }) };
class Book extends Model {
  static fields = bookFields;
}
interface Book extends Fields<typeof bookFields> {}

const books: Book[] = await Book.query().filter({ pages__gte: 100 });
books[0].pages; // number | null

The schemas of xufa/schema carry their types: Infer<typeof Review> is the type of a review, and with its type provider the requests and replies of routes are typed by their schemas. 

import { s, type Infer, type SchemaTypeProvider } from 'xufa/schema';

const app = xufa().withTypeProvider<SchemaTypeProvider>();
app.post('/reviews', { schema: { body: Review } }, async (request) => {
  request.body.stars; // number
  request.body.text; // string | undefined
});
type Review = Infer<typeof Review>;
