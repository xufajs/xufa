Guide

@xufa/auth (or xufa/auth) is the authentication of xufa, with no dependencies: everything is node:crypto. Passwords hashed with scrypt, JSON Web Tokens with keys that rotate, one-time codes of authenticator apps, logins locked after failures, refresh tokens that rotate, API keys, HTTP Basic, the strategies of Passport, and the plugin of @xufa/http that puts them together.

An app with logins

Users in the ORM, logins with an optional second factor, and routes that need a user or a role:

import xufa from 'xufa';
import { Database, Model, fields, plugin as orm } from 'xufa/orm';
import * as auth from 'xufa/auth'; // or from '@xufa/auth'

class User extends Model {
  static fields = {
    email: fields.string({ unique: true }),
    password: fields.string(),
    role: fields.string({ default: 'user' }),
    totpSecret: fields.encrypted(fields.string(), { null: true }), // keys: XUFA_ENCRYPTION_KEYS
    totpStep: fields.integer({ null: true }),
  };
}

class RefreshToken extends Model {
  static fields = auth.refreshTokenFields(fields);

  static options = { indexes: [{ fields: ['expiresAt'], expireAfter: 0 }] }; // deleted when they expire
}

const db = new Database({ backend: 'sqlite', filename: 'app.db' });
db.register(User, RefreshToken);

const app = xufa();
app.register(orm, { database: db, sync: true, expire: true });
app.register(auth.plugin, {
  keys: process.env.JWT_KEY,
  accessToken: { expiresIn: '15m' },
  login: {
    findUser: (email) => User.objects.filter({ email: email.toLowerCase() }).first(),
    claims: (user) => ({ sub: String(user.id), role: user.role }),
    totp: (user) => user.totpSecret, // users with a secret need the code of their app
    lastTotpStep: (user) => user.totpStep,
    onTotp: (user, step) => User.objects.filter({ id: user.id }).update({ totpStep: step }),
    rehash: (user, hash) => User.objects.filter({ id: user.id }).update({ password: hash }),
  },
  refresh: { store: auth.modelStore(RefreshToken), ttl: '30d' },
});

app.get('/me', { config: { auth: true } }, (request) => request.user);
app.delete('/users/:id', { config: { auth: ['admin'] } }, async (request) => {
  await User.objects.filter({ id: request.params.id }).delete();
  return { deleted: true };
});

The plugin

  • keys: a secret, a KeySet (or its options), or a function of the request that gives them: a KeySet per tenant, (request) => keysOf(request.tenant). Needed by the strategy 'jwt', logins and refresh tokens.
  • strategies: how requests say who they are, tried in order on every request (['jwt'] when keys are given): see Strategies.
  • accessToken: expiresIn ('15m'), issuer, audience, algorithms, clockTolerance.
  • token: where tokens are read from: the Authorization header (Bearer), then the cookie cookie and the query parameter query, when they are given.
  • user(claims, request): the user of a valid token (its claims by default; null refuses it).
  • hook: the hook that verifies the token of every request ('onRequest'), or false.

Every request gets request.user (null without a valid token), request.auth (the claims) and request.authError. Routes that need a user say so with config: { auth: true }, a role ('admin'), roles (['admin', 'staff']: any of them, from user.roles or user.role) or a function ((user, request) => boolean); or with the hooks app.authenticate and app.authorize(...roles). Without a valid token they answer 401 (with WWW-Authenticate), and 403 without the role. app.auth has sign(claims, request), verify(token, request), the keys and the passwords. tenants: of(request), the tenant of a request, and claim(user), the tenants of a user (see Tenants).

Login routes

With login, the plugin adds POST /auth/login, /auth/refresh and /auth/logout (prefix: '/auth'):

  • findUser(username, request): the user, or null. password(user) gives its hash (user.password).
  • claims(user): the claims of its tokens ({ sub: String(user.id) }).
  • totp(user): its secret of TOTP, when it has one: then the login needs code (without it, 401 with the code XUFA_AUTH_TOTP_REQUIRED, for the client to ask for it). lastTotpStep(user) and onTotp(user, step) keep the step of each login, so codes are used once.
  • lockout: a Lockout or its options (5 failures in 15 minutes lock for 15 minutes), or false. A locked login is answered with 429 and Retry-After.
  • rehash(user, hash): the new hash of a password whose hash had other parameters.
  • reload(subject, data, request): the claims of a refresh, read from the user again (null: it can no longer log in).
  • fields: the names of the fields of the body (username, password, code).

refresh: RefreshTokens or its options (false: none; given without login, for the logins of Passport, it adds /refresh and /logout). refreshCookie: true keeps the refresh token in an HttpOnly, Secure, SameSite=Strict cookie of the path of the prefix, instead of the body. A login answers the same Invalid credentials (401) for a user that does not exist and for a wrong password, and verifies a password in both cases, so neither the answer nor its time tells which.

Users

AbstractUser(Model, fields) is the model of users of Django's django.contrib.auth, of the Model and fields of @xufa/orm (@xufa/auth does not depend on it): a unique username, email, the hash of password, firstName and lastName, isStaff, isSuperuser, isActive, dateJoined, lastLogin, a role (of an Rbac, as Django's groups) and its own permissions (as user_permissions), and sessionGeneration: raised by each "log out everywhere" of @xufa/session, read with the user (so no request reads it apart). Extend it with fields of your own. 

import { Model, fields } from '@xufa/orm';
import { AbstractUser } from '@xufa/auth';

class User extends AbstractUser(Model, fields, { email: { unique: true } }) {
  static fields = { ...super.fields, totpSecret: fields.encrypted(fields.string({ null: true })) };
}

const admin = await User.createSuperuser({ username: 'admin', email: 'admin@example.com', password: 'a long password' });
const ada = await User.createUser({ username: 'ada', email: 'ada@example.com', password: 's3cret-enough', role: 'librarian' });
await ada.checkPassword('s3cret-enough'); // true
ada.hasPerm('Book.add');                   // its own permissions (and every one for a superuser)
ada.fullName;                              // 'Ada Lovelace' with its names

setPassword(raw) hashes with scrypt, setUnusablePassword() (a user who logs in elsewhere), checkPassword(raw). The accounts (model: User, with loginBy: 'username' to log in by username) and the admin (login: { model: User }) take the model as it is: they find, check and change its users, refuse those not isActive and set lastLogin. xufa createsuperuser makes one.

Accounts of a site

For sites with sessions (pages, not tokens), auth.accounts gives the routes of the accounts, as Laravel Breeze: sign up, log in and out, reset a forgotten password with a link by email, change it, and verify the email. It needs @xufa/session (registered before) and, for the links, a Mailer of @xufa/mail; your app keeps the users, and tells the plugin how to find, create and change them. 

app.register(sessionPlugin, { secret: process.env.SESSION_SECRET, store: ormStore(db), csrf: true });
app.register(auth.accounts, {
  secret: process.env.ACCOUNTS_SECRET, // signs the links (32 characters or more)
  users: {
    findByEmail: (email) => User.objects.filter({ email }).first(),
    findBySkeleton: (key) => User.objects.filter({ emailSkeleton: key }).first(), // look-alike emails are taken too
    findById: (id) => User.objects.filter({ pk: id }).first(),
    create: (values) => User.objects.create(values), // { email, emailSkeleton, password (its hash), name }
    setPassword: (user, hash) => User.objects.filter({ pk: user.pk }).update({ password: hash }),
    markVerified: (user) => User.objects.filter({ pk: user.pk }).update({ emailVerifiedAt: new Date() }),
  },
  signup: { fields: ['name'] },
  mailer, // new Mailer({ model: Email, app: { name: 'Shop' } })
  links: {
    reset: (token) => `https://shop.example/reset-password?token=${token}`,
    verify: (token) => `https://shop.example/verify-email?token=${token}`,
  },
});

app.get('/orders', { preHandler: app.accounts.required }, async (request) => Order.objects.filter({ user: request.account.pk }));

Pages of users who logged in

For sites of pages, the accounts guard routes as Django's login_required and permission_required: loginRequired sends a page to loginUrl with ?next= (a client that asks for JSON gets 401), and permissionRequired(...permissions) answers 403 to a user without them. The permissions are those of the roles of rbac (an Rbac or its options) and each user's own (userPermissions(user), user.permissions by default, as Django's user_permissions). 

app.register(auth.accounts, {
  ...options,
  loginUrl: '/accounts/login/',
  rbac: { roles: { librarian: ['Book.*', 'BookInstance.markReturned'] } },
});
app.get('/mybooks/', { preHandler: app.accounts.loginRequired }, myBooks);
app.post('/book/:pk/renew/', { preHandler: app.accounts.permissionRequired('BookInstance.markReturned') }, renew);
await app.accounts.can(user, 'Book.add'); // true or false

With @xufa/template, every view of a request has user (null for nobody) and perms ({{#if perms.has('Book.add')}}), whatever the order of the plugins. The 403 is an error of status 403: the error handler of the app shows its page.

Pages of the accounts

Their forms are those of @xufa/forms, their errors the messages of the accounts (translated with translateAuth).

Credentials

The logins of auth.accounts, of the login route of the plugin and of the admin are one: Credentials. Use it for a login of your own (a form, a CLI, a WebSocket): 

const credentials = new auth.Credentials({
  findUser: (email) => User.objects.filter({ email }).first(),
  totp: (user) => user.totpSecret,
  setPassword: (user, hash) => User.objects.filter({ pk: user.pk }).update({ password: hash }),
});
try {
  const user = await credentials.login({ identifier: body.email, password: body.password, code: body.code, ip: request.ip });
} catch (err) {
  if (!(err instanceof auth.CredentialError)) throw err;
  // err.reason: 'invalid', 'code' (err.needsCode: ask for it), 'throttled' (err.retryAfter), 'locked'...
}
  • login(): the same answer and time for a user that is not there, a wrong password and a user that allow(user) refuses; a user that active(user) refuses is told it is locked (403) once its password is right; then the code of an authenticator app (each code once with lastTotpStep/onTotp) or a recovery code; failures locked out by identifier (5 in 15 minutes) and by address (20); a hash made with other passwordOptions made again (rehash, or setPassword).
  • The account of a user: changePassword(user, { current, password, email }) and setPassword() (the policy: minPassword 8, maxPassword 256, not the email in it, checkPassword); startTotp(user, { password, label, issuer, session }) gives the QR code of a new secret kept in the session for 10 minutes, confirmTotp(user, { code, session }) turns it on with new recovery codes, disableTotp(), renewRecoveryCodes(), state(user). Each asks for the password again, its failures locked out by account.
  • Errors: a CredentialError has a reason, statusCode, errors by field, needsCode, recovery and retryAfter; messages: { invalid: 'Wrong email or password' } words them your way (a text, a key of your catalogs, or 'auth.invalidEmail': a message of @xufa/auth). Every message users read is a key of auth.AUTH_MESSAGES: i18n.translateAuth(auth) gives them, and the emails of the links, in the language of each request.

Tenants

A user may use the tenants of its claims: tenants (a list) or tenant; '*' is every tenant (the admins of the whole service). Put them in the claims of its tokens: claims: (user) => ({ sub: String(user.id), tenants: user.tenants }).

  • config: { auth: { tenant: true } }: a user of the tenant of the request; 403 for the others, 401 without a user.
  • config: { auth: { tenant: '*' } }: a user of every tenant.
  • With roles, check or strategy, all of them: { tenant: true, roles: 'admin' } is an admin of that tenant.

The tenant of a request is request.tenant (set by the plugin of the ORM), or tenants.of(request) of the options. Rules are checked when routes are added: a wrong one stops the app from starting. The tenants of the ORM should check the user before the tenant is entered, so a request of a tenant that is not the user's does not even open its database: 

app.register(auth.plugin, { keys, login });
app.register(orm.plugin, {
  tenants: {
    tenants,
    resolve: (request) => request.headers['x-tenant'],
    authorize: (request, id, reply) => app.auth.canUseTenant(request, id, reply), // 401, 403, or the tenant
  },
});

Roles and permissions

Rbac gives roles their permissions and users their roles by tenant: a user may be an editor in one tenant, a viewer in another and nothing in the rest, while the people who run the service have a role in every tenant ('*') or are superusers. A permission is a name ('Book.change'); a role lists them, with patterns ('Book.*', '*.view', '*'; a * never crosses a dot), and may take those of other roles (inherits). 

import { Rbac } from '@xufa/auth';

const rbac = new Rbac({
  roles: {
    viewer: ['*.view'],
    editor: { inherits: 'viewer', permissions: ['Book.add', 'Book.change'] },
    manager: { inherits: 'editor', permissions: ['Book.delete', 'Author.*'] },
    support: ['*.view', 'Ticket.*'],
  },
});

// Grants: a role in a tenant, or in every tenant (no tenant, or '*').
const eve = { grants: [{ role: 'editor', tenant: 'acme' }, { role: 'viewer', tenant: 'globex' }] };
const sam = { grants: [{ role: 'support' }] }; // the support team: every tenant
const root = { superuser: true };

(async () => {
  console.log(await rbac.can(eve, 'Book.change', { tenant: 'acme' }));
  console.log(await rbac.can(eve, 'Book.change', { tenant: 'globex' }));
  console.log(await rbac.can(eve, 'Book.view', { tenant: 'initech' }));
  console.log(await rbac.can(sam, 'Ticket.close', { tenant: 'initech' }));
  console.log(await rbac.can(root, 'Book.delete', { tenant: 'anywhere' }));
  console.log(rbac.tenantsIn(await rbac.access(eve)), rbac.tenantsIn(await rbac.access(sam)));
})();

The grants of a user are grants(user) when it is given (a table of memberships, say); else user.grants (a list of { role, tenant }, or { acme: 'editor' }), or its roles in its tenants. Superusers are superuser(user) (user.superuser or user.isSuperuser by default; false: none). access(user) is what a user may as plain data ({ superuser, grants }), to keep in a session or a token and ask with allows(access, permission, tenant) without loading the user.

Given to the plugin as rbac, routes ask for permissions in the tenant of the request with { can }, handlers with request.can(), and the tenants of a user are those of its grants (for canUseTenant and { tenant: true }): 

app.register(auth.plugin, {
  keys,
  login,
  rbac: {
    roles: { viewer: ['*.view'], editor: { inherits: 'viewer', permissions: ['Book.add', 'Book.change'] } },
    grants: (user) => Membership.objects.filter({ user: user.sub }).values('tenant', 'role'),
  },
});

app.delete('/books/:id', { config: { auth: { can: 'Book.delete' } } }, handler); // 403 without it in the tenant
app.get('/books/:id', async (request) => {
  const book = await Book.objects.get({ id: request.params.id });
  return { ...book.toJSON(), editable: await request.can('Book.change') };
});
// The resources of the ORM: Book.view (list, get), Book.add, Book.change and Book.delete.
app.register(orm.resource(Book, { permissions: true }), { prefix: '/books' });

The admin takes the same Rbac: each user sees the models it may view in the tenant it chooses, and only the buttons of what it may do.

Rules of objects

A permission of a role can be for some objects only, as Django's get_queryset and has_change_permission(request, obj): where gives, by patterns of permissions, the conditions of the ORM of the objects (a function of the user; true for all, false for none). A user with several roles has the objects of any of them; a role without a where for a permission has all its objects; a role that inherits keeps the limits of what it inherits. rbac.scopeOf(access, user, permission) (and app.auth.scopeOf(request, permission)) gives null (all), false (none) or the conditions. The resources of the ORM with permissions and the admin follow them: their lists, objects, counts, changes, deletes and actions are those of the rules (another object is not found). A where for Model.add is of the new objects (Django's has_add_permission of its values): one that does not meet it is not kept (403, its transaction rolled back). The choices of the admin are the objects one may view. 

const rbac = new auth.Rbac({
  roles: {
    viewer: ['*.view'],
    // An editor sees every book, and changes and deletes its own.
    editor: {
      inherits: 'viewer',
      permissions: ['Book.change', 'Book.delete'],
      where: { 'Book.change': (user) => ({ ownerId: user.id }), 'Book.delete': (user) => ({ ownerId: user.id }) },
    },
  },
});
rbac.scopeOf(await rbac.access(ada), ada, 'Book.change'); // [{ ownerId: 7 }]

Groups

As Django's groups, roles can live in the database and be edited in the admin: AbstractGroup(Model, fields) is their model (a name, its permissions and the roles it inherits), and the option model of Rbac takes its rows as roles, next to those in code (a group named as a role in code adds to it). Users are in groups with AbstractUser(Model, fields, { groups: () => Group }) (a many-to-many, user.groups): the roles of a user are its groups, and its role or roles. A save or delete of a group is seen at the next question; changes made by other processes after refresh (60 seconds). In the admin, the permissions of users and groups and the roles a group inherits are picked from lists (those of its models, and the roles of its rbac). 

class Group extends auth.AbstractGroup(Model, fields) {}
class User extends auth.AbstractUser(Model, fields, { groups: () => Group }) {}

const rbac = new auth.Rbac({ roles: { viewer: ['*.view'] }, model: Group });
await Group.objects.create({ name: 'editors', permissions: ['Book.*'], inherits: ['viewer'] });
await ada.groups.set([editors.pk]);
await rbac.can(ada, 'Book.change'); // true

app.register(admin, { prefix: '/admin', models: [Book, User, Group], rbac }); // groups edited in the admin

Strategies

Each request is tried with the strategies of strategies, in order, until one identifies its user: request.user, request.auth (what the strategy knows: the claims of a JWT, { apiKey: id }, { username }) and request.authStrategy (its name). Credentials that are not valid make request.authError, and a route that needs a user answers 401 with the WWW-Authenticate challenges of the strategies. 

app.register(auth.plugin, {
  keys: process.env.JWT_KEY,
  strategies: [
    'jwt',
    auth.apiKey({
      find: (id) => ApiKey.objects.filter({ id }).first(), // static fields = auth.apiKeyFields(fields)
      user: (key) => User.objects.get({ id: key.subject }),
    }),
    auth.basic({ findUser: (email) => User.objects.filter({ email }).first() }),
  ],
});

app.get('/reports', { config: { auth: { strategy: 'apiKey' } } }, handler); // only API keys
app.get('/admin', { config: { auth: { strategy: ['jwt', 'basic'], roles: 'admin' } } }, handler);
  • auth.apiKey({ find, user, header, scheme, query }): keys from x-api-key, Authorization: <scheme> <key> or a query parameter (off by default: URLs end in logs). A key is <id>.<secret>: find(id, request) gives its record ({ hash }), refused when its expiresAt passed or it has a revokedAt; user(record, request) gives its user.
  • auth.generateApiKey({ prefix: 'xk_' }): { key, id, hash }. Give key once and keep id and hash: only a SHA-256 of the 32 random bytes of the secret is kept, compared in constant time. auth.apiKeyFields(fields): the fields of a model of keys.
  • auth.basic({ findUser, password, lockout, cache }): HTTP Basic against the scrypt hashes of the users, with a Lockout. A checked password is remembered for cache ('5m'), so requests do not pay scrypt each time; a changed password is checked again.
  • Your own: { name, challenge, authenticate(request, reply) }, whose promise is { user, info }, { fail: { message, challenge } } or null (no credentials of its kind).

A route says which strategies may identify its user with config: { auth: { strategy, roles, check } }, or the hook app.auth.authenticateWith('apiKey', 'basic'). Each strategy runs once per request. With @xufa/openapi, the strategies are the security schemes of the document (each has its openapi: bearer JWT, API keys, Basic, OAuth 2.0 of Passport), and routes with config.auth get their security.

Passport

The strategies of Passport work unchanged, without Passport: auth.passport(strategy) gives them what Passport would (success, fail, redirect, pass, error, and a request with what Express has that they read). Tested with passport-local, passport-http, passport-http-bearer, passport-headerapikey, passport-jwt and passport-oauth2. 

import { Strategy as BearerStrategy } from 'passport-http-bearer';
import { Strategy as GitHubStrategy } from 'passport-github2';

// Credentials in every request: one more strategy.
app.register(auth.plugin, {
  keys: process.env.JWT_KEY,
  refresh: true,
  strategies: ['jwt', auth.passport(new BearerStrategy(verifyToken))],
});

// Logins: the redirect to the provider and its callback, in routes.
const github = auth.passport(
  new GitHubStrategy(
    { clientID, clientSecret, callbackURL: '/auth/github/callback', store: auth.oauthState({ secret: process.env.STATE_KEY }) },
    (accessToken, refreshToken, profile, done) => findOrCreateUser(profile).then((user) => done(null, user))
  )
);
app.get('/auth/github', github.login({ scope: ['user:email'] }));
app.get('/auth/github/callback', github.login());

There are no sessions: login({ onLogin, onFailure, claims }) answers a login with the tokens of the plugin (app.auth.issue(claims(user)): the access token, and a refresh token when there are refresh tokens), or with what onLogin(user, info, request, reply) returns (a redirect to the app, a cookie...). Failures are 401 (or the status the strategy gives) unless onFailure(failure, request, reply) answers. The options of the strategy (scope...) go with them.

auth.oauthState({ secret }) is the store of OAuth 2.0 strategies: the state sent to the provider is a random handle, and a cookie keeps it, with the code verifier of PKCE, sealed with AES-256-GCM, for 10 minutes, used once (HttpOnly, Secure, SameSite=Lax: the redirect of the provider carries it). A strategy that keeps other things in req.session needs a plugin that gives requests a session.

Passwords

hashPassword(password, options) gives $scrypt$ln=17,r=8,p=1$<salt>$<hash>: scrypt with N = 217, r = 8, p = 1 (128 MiB, as OWASP recommends). verifyPassword(password, hash) reads the parameters from the hash, so older hashes still verify, and compares in constant time. needsRehash(hash, options) says when a hash should be made again with the current parameters.

JSON Web Tokens

const keys = new auth.KeySet({ current: '2026-10', keys: { '2026-10': process.env.JWT_KEY, '2026-07': oldKey } });
const token = auth.signJwt({ sub: '42', role: 'admin' }, keys, { expiresIn: '15m', issuer: 'app' });
const claims = auth.verifyJwt(token, keys, { issuer: 'app' }); // or a TokenError (401) with its reason

A KeySet has keys by id: the current one signs (its id is the kid of the tokens) and all of them verify, so keys rotate without logging anyone out. A key is a secret (32 bytes or more, HS256/384/512) or a PEM or KeyObject: RSA (RS256, PS256...), EC (ES256, ES384, ES512) or Ed25519 (EdDSA). A set of public keys only verifies, as another service would; keys.toJWKS() publishes them. signJwtAsync() and verifyJwtAsync() are the same as Promises: RSA keys sign in libuv's thread pool, so the event loop does not wait for their half a millisecond; the rest takes 20 to 90 µs and is done on the loop. The plugin uses them. The tokens are signed and verified by @xufa/jwt (the checks and tests of jsonwebtoken): RSA keys under 2048 bits do not sign, and tokens with critical extensions (crit) are refused.

verifyJwt() takes only the algorithms of its keys (a token cannot choose none, nor HMAC with a public key), checks exp and nbf (with clockTolerance) and, when they are given, issuer, audience, subject and maxAge. Its TokenError (401) says why in reason.

Keys per tenant

A KeyVault keeps the keys of each tenant in a store: its tokens are signed with its keys, and a token of one tenant is no token of another. The private keys are kept encrypted, with keys derived from the secret of the vault, the tenant and the key: a copy of the store is no key, and the keys of one tenant cannot be moved to another. 

import { KeyVault, vaultModelStore, vaultFields } from '@xufa/auth';

class TenantKeys extends Model {
  static fields = vaultFields(fields);
}

const vault = new KeyVault({ secret: process.env.VAULT_SECRET, store: vaultModelStore(TenantKeys) });
await vault.create('acme'); // when the tenant is made: its first key (ES256 by default)

app.register(auth.plugin, { keys: (request) => vault.keys(tenantOf(request)), login });
app.get('/.well-known/jwks.json', (request) => vault.jwks(tenantOf(request)));

await vault.rotate('acme'); // a new key
MethodWhat it does
keys(tenant)The KeySet of the tenant, kept ttl in memory.
create(tenant, { algorithm })Its first key: HS, RS, PS, ES or EdDSA.
rotate(tenant, { algorithm, immediate })A new key: it verifies at once, and signs after ttl (immediate: at once). The key it replaces verifies keep more.
revoke(tenant, keyId)Removes a key that leaked (not the one that signs: rotate first).
jwks(tenant), remove(tenant), invalidate(tenant)Its public keys; all its keys gone; forgotten in this process.

Options: secret (32 bytes or more), store (a MemoryKeyStore by default), algorithm ('ES256'), ttl ('5m'), keep ('1d'), rotateAfter (keys older are rotated when used), max (tenants in memory) and autoCreate (false: a tenant without keys is an error, since tenants may come from what clients send).

Rotation in a cluster. Each process keeps the keys of a tenant ttl; a new key is published at once and signs only ttl after, when every process has loaded it, so no process meets a token of a key it does not know. Two processes that change the keys of a tenant at once do not lose a key: the records change by compare-and-swap on their version. A KeySet also takes an encrypted private key as { key, passphrase }.

One-time codes

// Enrolling: the app scans the QR code of the URI, and the user types a code to confirm it.
const secret = auth.generateSecret();
const uri = auth.totpUri({ secret, issuer: 'Acme', label: 'ada@example.com' });
const svg = auth.qrSvg(uri); // the QR code to show: <svg ...>
const step = auth.verifyTotp(code, secret); // null, or the time step to keep with the user

verifyTotp(code, secret, { window, after }) takes the codes of window steps around now and returns the step of the code; codes of the step after or before are refused, so keeping the step of each login makes each code work once. totp() and hotp() follow RFC 6238 and RFC 4226 (SHA1, SHA256 or SHA512, 6 to 10 digits). generateRecoveryCodes(n) gives codes to log in without the app; keep their hashRecoveryCode(). qrSvg(text, { level, border, size }) draws the QR code of the URI with no dependencies (qrCode(text) gives its matrix). Keep the secrets of TOTP encrypted (they are passwords that never change), in fields.encrypted() of the ORM, as in the example.

Lockout

const lockout = new auth.Lockout({ maxAttempts: 5, window: '15m', lockFor: '15m' });
await lockout.check(email); // throws Locked (429, retryAfter) while it is locked
ok ? await lockout.succeed(email) : await lockout.fail(email);

The failures are kept in a store with get, set and delete: one of the process by default, or a cache of the ORM. With a SharedCache they are in the primary of a cluster, so every worker counts the same failures.

Keys are counted by normalizeIdentifier(key): Unicode NFKC and lower case, so names a person cannot tell apart are one key ('ＡＤＭＩＮ', full-width, and 'Admin' are 'admin') with one count of failures. Store and find users by it too. Letters of other scripts that look the same (Cyrillic а) are not changed.

skeleton(value) covers those: the skeleton of Unicode's security mechanisms (UTS #39), the same for texts that look alike across scripts ("pаypal" with a Cyrillic а, and "paypal"). Keep skeleton(normalizeIdentifier(name)) with each user, unique, and refuse a new name whose skeleton is taken: no one signs up as a look-alike of another.

Refresh tokens

const refresh = new auth.RefreshTokens({ store: auth.modelStore(RefreshToken), ttl: '30d' });
const { token } = await refresh.issue(user.id, claims);
const next = await refresh.rotate(token); // { token, record }: the old one is spent
await refresh.revoke(next.token); // logout (its family)
await refresh.revokeSubject(user.id); // logout everywhere (a changed password)

The store keeps the id of each token and the SHA-256 of its secret (a stolen store gives no usable token), its subject, its data and its dates. Each use spends the token (atomically) and gives a new one of its family. A token used twice means that two parties have it: its whole family is revoked, so the thief's token and the user's stop working. Stores: MemoryTokenStore and modelStore(Model), for a model of the ORM with the fields of refreshTokenFields(fields). A TTL index on expiresAt deletes the tokens that expired (or call refresh.prune() now and then).

Errors

TokenError (401, XUFA_AUTH_INVALID_TOKEN, with its reason), Unauthorized (401), TotpRequired (401), Forbidden (403) and Locked (429, with retryAfter), all made with @xufa/errors.
