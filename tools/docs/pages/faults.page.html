@xufa/faults

Faults made to happen, to see what an app does when what it uses fails: operations that fail, wait, hang or find their service down, by rules that say which operations, how often and how many times. It is the engine of the faults of the database, the caches, the HTTP client and the bus of xufa. No dependencies.

Quick start

db.faults.fail({ operations: 'write', models: [Order], rate: 0.2 }); // 1 write of Order in 5 fails
client.faults.respond({ status: 503, headers: { 'retry-after': '1' }, paths: '/payments', times: 3 });
cache.faults.down(); // the cache is lost: the database answers
bus.faults.drop({ events: 'invalidate', rate: 0.1 }); // 1 message in 10 is lost
const hung = netcache.faults.hang({ keys: 'session:' }); // until hung.release()

Rules

fail(options), delay({ ms, jitter, ...options }), hang(options) and down(options) (every operation fails until up()) add a rule and give it back; clear() removes them all and lets go what they hold.

  • operations: names or groups; the defaults of those faults when not given.
  • Filters (models, keys, paths...): names, prefixes (keys, paths, urls) or regular expressions; classes by their names. match(context): a check of your own.
  • rate: the chance of each match (faults.random of your own in tests); after: the first matches are left alone; times: removed after that many hits.
  • A rule counts its hits; remove() takes it away; release() lets what it holds go on. Waits end with the signal of the operation: the timeout of a client call ends a hang.
  • Without rules, the operations are as they were: one check of an empty list.

In tests

// In the setup files of the runner (setupFiles of Jest, Vitest or vyntra; --require of Mocha):
import 'xufa/faults/register'; // or '@xufa/faults/register'

// Or in a test file:
import { useFaults } from 'xufa/faults';
useFaults(); // the afterEach of the runner; useFaults(await import('node:test')) for node:test

After each test, clearFaults() removes every rule of every faults (the database, its caches, the clients, the bus...) and lets go what they hold, so a test that fails before its clear() leaves no fault to the next one. activeFaults() gives the faults that have rules now. With strict (useFaults({ strict: true }), or xufa/faults/register-strict), a test that ends with faults still set fails, naming them (database: fail of insert (hits 0)); they are cleared all the same. xufa's own suites that use faults run this way.

Scenarios

A scenario makes faults come and go on a timeline, as an outage does: the database gets slow, then the cache goes down, then the payment provider answers 503 now and then. For game days in staging, and for tests of what an app does through all of it. 

import { scenario } from 'xufa/faults';

const brownout = scenario({
  name: 'payments brownout',
  steps: [
    { at: 0, target: db, kind: 'delay', options: { operations: 'read', ms: 300 }, for: '2m' },
    { at: '30s', target: payments, kind: 'respond', options: { status: 503, rate: 0.2 }, for: '1m' },
    { at: '1m', target: db.cache, kind: 'down', for: '30s' },
  ],
  onEvent: (event) => logger.warn(event, 'fault scenario'),
});
await brownout.run(); // or brownout.start() ... brownout.stop()
  • A step makes its rule at its time from the start (0, '30s', '2m') and removes it after for; without for, it stays until the end. target is faults or what has them, or the name of one of targets.
  • The scenario ends at duration, or when its last step ends. Its end, and stop(), remove every rule it made and let go what they hold; the steps not made yet are skipped.
  • Steps are checked when the scenario is made (targets, kinds, operations, rates, durations): a mistake fails at once, not in the middle of a game day.
  • status(): its state, the time gone, each step (waiting, active, done, skipped) with its hits, and the events, which onEvent is told of as they happen.
  • Every week: a job of @xufa/scheduler whose run({ signal }) runs it (and stops it when the signal is aborted).
  • Over HTTP, the plugin's scenarios option defines them by name (their steps name targets); they are started and stopped by the routes below and from the page.

Over HTTP (staging)

import { plugin } from 'xufa/faults';

app.register(plugin, {
  targets: { db, cache: db.cache, payments, bus }, // faults, or what has them
  token: process.env.FAULTS_TOKEN, // Authorization: Bearer <token>
});
curl -X POST localhost:3000/_faults/payments/respond -H "authorization: Bearer $FAULTS_TOKEN" \
  -H 'content-type: application/json' -d '{"status": 503, "paths": "/charges", "rate": 0.2, "for": "10m"}'
RouteWhat it does
GET /_faultsThe targets: operations, filters, kinds and rules.
POST /_faults/:target/:kindA rule (fail, delay, hang, down, respond, drop), its options as JSON.
DELETE /_faults/:target/rules/:idThat rule removed; POST .../rules/:id/release lets what it holds go on.
POST /_faults/:target/upNo more down.
DELETE /_faults/:target, DELETE /_faultsThe rules of a target, or of all of them, removed.
GET /_faults/scenariosThe scenarios defined, and those run (with their status).
POST /_faults/scenarios/:nameA scenario defined, started (409 while it runs).
POST /_faults/scenariosA scenario of the body ({ name, steps, duration }), started.
DELETE /_faults/scenarios/:idA scenario stopped: its rules removed.
GET /_faults/uiA page that does all of this.
  • Options as JSON: operations, rate, after, times, ms, the filters of the target (names, or { "regex": "..." }); functions cannot be sent, other keys are a 400.
  • for: how long the rule stays, never more than maxDuration (1 h); the rules made by the routes go when the app closes.
  • Always protected: token (constant-time), authorize(request) or auth (a rule of @xufa/auth); without one, registering fails. Off in production unless enabled and allowProduction.
  • Every change is logged at warn; the routes are left out of OpenAPI.
  • The page (/_faults/ui; ui: false leaves it out): the targets and their rules, refreshed every 2 seconds (hits, whether a hang holds, the time left), a form for new rules (the operations and filters of the target, the fields of each kind), buttons to remove, release, bring up and clear, and the scenarios (start, stop, their steps as they go, and one written there as JSON, checked by the server). Its files have no data, so they are served without the protection; what it shows and changes goes through the protected routes (with token it asks for the token and keeps it in the tab; with authorize or auth, the cookies of the browser go with its requests). Presets keep the form by name, and a button switches between light and dark (both kept in the browser). It has a strict Content-Security-Policy and sets every value as text.

Errors

The errors of fail and down are FaultErrors (code XUFA_FAULT, status 503), the error given, or those of each part: the ORM's FaultError (XUFA_ORM_ERR_FAULT), a refused connection for the client (a RequestError, retried), a BusError for the bus. err instanceof FaultError and isFault(err) are true of all of them: of every error whose code ends in FAULT.

Faults of your own

import { Faults, wrap, cacheFaults } from '@xufa/faults';

const faults = new Faults({
  operations: ['charge', 'refund'],
  groups: { money: ['charge', 'refund'] },
  filters: { customers: 'customer' }, // the option customers matches context.customer
});
const charge = (customer, amount) => faults.apply({ operation: 'charge', customer }, () => gateway.charge(customer, amount));

faults.add('declined', { operations: 'charge', times: 1 }, { replace: () => ({ status: 'declined' }) });
  • faults.apply(context, run) runs the operation through the rules; faults.pick(context) gives the rules that act on it at once, for operations that cannot wait.
  • faults.add(kind, options, { replace }): a kind of its own; replace(context) is what the operation gives instead.
  • wrap(faults, object, methods, contextOf): the methods of an object go through the faults. cacheFaults(cache, name): those of an object with get, set, delete and clear.
