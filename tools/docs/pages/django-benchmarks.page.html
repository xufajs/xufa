xufa and Django

The same app on both: the LocalLibrary of the Django tutorial, and its port to xufa (examples/locallibrary), on the same PostgreSQL with the same data, the same number of processes, and Django served by each server that serves it well. Each card compares xufa with the fastest of them in that scenario.

Results

The app

examples/django-locallibrary is the MDN tutorial as it is published; examples/locallibrary is its port, page by page. Both get the same rows (bench/django/data.mjs: 500 authors, 2,000 books, 6,000 copies, 10 genres, 5 languages, a reader with loans and a librarian), each in a database of its own on one PostgreSQL, vacuumed and analyzed after the rows go in. Both apps have an index on the books' title and author, the order of their list, that also holds the id (INCLUDE; the tutorial has none: each page sorted every book), and keep the four counts of the home page for 10 s (Django's cache, xufa's cached(), which also forgets them when their model is written). Sessions are kept in the database on both sides; xufa's app writes them with asyncCommit, the setting of a new project (PostgreSQL confirms them before they reach the disk; Django has no such option for its sessions). Two pages are only for the benchmark, the same on each: a plain text, and a book as JSON.

Django at its best

The tutorial is written to learn, not to be fast, so Django runs as it would be deployed (bench/django/site/benchsite): DEBUG off (cached templates), psycopg 3 with its compiled implementation, persistent connections (Django's pool under ASGI, as its docs advise), no static files middleware, no log of requests. The tutorial's list views load the author of each book with a query of its own; here they load their relations as the port does (select_related, prefetch_related), so both make the same queries. Four servers run it, four processes each: gunicorn with sync workers and with threads (gthread, 4 per process), granian (WSGI, 4 threads per process) and uvicorn (ASGI). xufa runs as deployed: NODE_ENV=production, four workers of node:cluster, no log of requests.

The scenarios

ScenarioWhat it does
Plain textA text of 13 bytes: the framework alone
A book as JSONA book with its author, language and genres: 2 queries, as JSON
Home page4 counts (kept 10 s), the visits of the browser kept in its session (a write), a template; 100 visitors
Book listA page of 10 books with their authors, ordered by title, and its paginator
Book detailA book with its author, language, genres and copies
Loans of the userThe copies the reader borrowed: a logged-in page
Edit an authorThe form of an author sent back (CSRF token, validation, an UPDATE, a redirect) by a librarian; 50 authors

Each request is checked before it is measured (its status, and the size of its answer, about the same on both sides). The writes go to rows of their own (100 visitors, 50 authors), as real traffic does: on one row, every request would wait for the lock of the one before it, and both would measure PostgreSQL.

What to keep in mind

  • The book list is the closest. Its pages go up to the 200th (OFFSET 1990, as Django's paginator). From an offset of 100, xufa's ORM asks PostgreSQL for the ids of the page first, from the index alone, then loads those ten books with their authors; Django skips the rows of the whole join. Django orders by author through the author's own order (last name, first name), which the index cannot give: it still sorts.
  • The home page writes its session on every visit. With asyncCommit that write doesn't wait for the disk (a crash of PostgreSQL could lose the last fraction of a second of session writes); without it, xufa's home page answers about half as many requests.
  • gunicorn's sync workers serve one request at a time: with 64 connections, requests wait seconds in its queue (its p99). They are still the most common way to deploy Django.
  • xufa takes more memory under load, and it is not data it keeps: each worker starts at about 93 MB, as a process of Django, and after a collection its live heap is the same 21 MB as when idle. What grows is V8's young generation, made bigger to collect less often: @xufa/cluster caps it at 32 MB a half (semiSpace), which keeps a worker near 200 MB with the same speed.
  • Linux in WSL 2 shares the machine with Windows: ⚠ marks rounds more than 10% apart. Even so, in every scenario the slowest round of xufa answered at least six times as many requests as the fastest round of any server of Django.

Run them yourself

pnpm bench:linux django --out results/django-5       # from Windows, in WSL
node bench/django.js --rounds 3 --duration 10          # on Linux
node bench/django.js --servers xufa,granian-wsgi --scenarios hello,json,book

It needs PostgreSQL (apt install postgresql) and Python 3; it makes a cluster of PostgreSQL of its own and a venv with Django and its servers in ~/bench-django.
