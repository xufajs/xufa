@xufa/admin

The admin of the models of @xufa/orm, as Django's: a page with the list of each model (search, filters, order, pages) and its forms (from its fields, with the errors of its validation), for every backend of the ORM, as a plugin of @xufa/http. The page is made with React and comes built in the package: installing the admin installs nothing else, and the app builds nothing.

Quick start

import xufa from '@xufa/http';
import { Database, Model, fields } from '@xufa/orm';
import { admin } from '@xufa/admin';

class Author extends Model {
  static fields = { name: fields.string(), country: fields.string({ null: true, choices: ['ES', 'UK', 'US'] }) };
}
class Book extends Model {
  static fields = { title: fields.string(), pages: fields.integer({ null: true }), author: fields.foreignKey(() => Author) };
  toString() {
    return this.title; // how a book is shown (as Django's __str__)
  }
}
const db = new Database({ backend: 'memory' }).register(Author, Book);
await db.sync();

const app = xufa();
app.register(admin, {
  prefix: '/admin',
  models: [Book, [Author, { search: ['name'] }]],
  authorize: (request) => true, // who may use it: required (request.user?.role === 'staff'...)
  title: 'Bookshop',
});

const page = await app.inject('/admin/');
console.log(page.statusCode, page.headers['content-type']); // open /admin/ in a browser
200 text/html; charset=utf-8

In a project, each app's admin.yaml (Django's admin.py) lists its models by name, in order, with these options; the admin takes those of every app, and admin: of xufa.yaml its own options: 

# catalog/admin.yaml
Genre:
Author:
  list: [lastName, firstName, dateOfBirth, dateOfDeath]
  fields: [firstName, lastName, [dateOfBirth, dateOfDeath]]
  inlines: [{ relation: bookSet, fields: [title, summary, isbn] }]
BookInstance:
  list: [book, status, borrower, dueBack]
  filters: [status, dueBack]
  fieldsets:
    - [null, { fields: [book, imprint, id] }]
    - [Availability, { fields: [status, dueBack, borrower] }]

The page

A sidebar with the models (and their counts), the jobs and the pipeline runs; a header with where you are, the tenant chosen and your account; and a dashboard with every model, the jobs and runs by status, what waits in the queue (the jobs due now and how long the oldest has waited, in amber after 5 minutes; those scheduled later), and the health of the app. It works on phones (the sidebar becomes a drawer), in a light and a dark theme (or that of the system), and from the keyboard.

  • Addresses keep what you see: the search, filters, order and page of a list are in the address (#/Book?search=ada&f.published=true&order=-pages&page=2), so going back, reloading and sharing a link keep them.
  • Forms as Django's: Save, Save and keep editing (Ctrl+S), Save and add another; the errors of the server under each field; required fields checked before sending; foreign keys chosen in a combobox that searches; a question before leaving a form with changes.
  • Lists: search (/ goes to it), filters, columns that order, rows per page, objects selected and deleted at once or given to the actions of their model.
  • Jobs and runs read again while they are live; dialogs ask before deleting, cancelling or retrying everything; toasts say what happened.

Its files are served under assets/ with their hash in their address (cached for good), compressed with brotli or gzip, and need no build of the app. To change the page itself, its sources are in packages/admin/client/src (React), and npm run build makes lib/client/dist again (a test says when it is not the build of the sources).

Lists

Each model has a list: the columns of list (the first six fields that are not text nor json), a search in the fields of search (its string fields), filters by the fields of filters (booleans, choices and foreign keys), an order by any column (a click on it), and pages of 25. The objects of foreign keys are shown by their labels. 

app.register(admin, {
  prefix: '/admin',
  models: [[Book, { list: ['title', 'author', 'published'], search: ['title', 'isbn'], filters: ['published'] }], Author],
  authorize,
});
Option of a modelWhat it is
labelThe name shown
list, search, filtersIts columns, the fields its search looks in, the fields it filters by
editableBooleans and choices of its list changed in its rows, each saved as it changes (Django's list_editable)
fields, fieldsetsThe fields of its form, their order and groups (Fields and fieldsets)
readOnlyFields shown in its forms but not changed (besides keys, automatic dates and fields given by the backend)
readOnlyModelOnly shown: no creates, updates nor deletes
actionsIts actions on the objects selected in its list, by name (Actions)
inlinesIts related lists, by relation name (['bookSet']); all by default, none with false

A search is of words: each must be in one of the fields of search (ada notes finds the notes of Ada), and "quoted words" are one. Its fields can be paths across relations, as in the conditions of the ORM: author__name (the name of the author of a book), or back, bookSet__title (an author by the titles of its books: each author once). ^name searches the start of a field and =code the whole of it (as Django's); all ignore case. A search that is not a path of the model is an error when the app starts. 

models: [[Book, { search: ['title', '=isbn', 'author__name'] }], [Author, { search: ['^name', 'bookSet__title'] }]],

Actions

The objects selected in a list can be deleted at once, and given to the actions of their model (Django's admin actions): each a button of the bar of the selection. Its run(objects, context) gets a QuerySet of them (those still there; with softDelete, those not deleted) and { request, user, tenant, pks, model }; it answers the message shown, the number of objects it changed, or nothing (then the message counts those selected). An action needs <Model>.change unless its permission says another, and a user sees only those it may run. confirm asks before it runs (true, or the question), danger makes it red. An AdminError thrown is shown as its message. 

import { admin, AdminError } from '@xufa/admin';

app.register(admin, {
  models: [
    [Book, {
      actions: {
        // Its button: "Mark published"; the message: "Mark published: 3 objects".
        markPublished: (books) => books.update({ published: true }),
        archive: {
          label: 'Send to the archive',
          confirm: 'Archive the books selected?',
          permission: 'Book.delete',
          run: async (books, { user }) => {
            if (await books.filter({ published: false }).exists()) throw new AdminError('Drafts are not archived');
            const count = await books.update({ archivedBy: user.email });
            return `${count} sent to the archive`;
          },
        },
      },
    }],
  ],
  authorize,
});

editable: ['published', 'status'] (Django's list_editable) makes those columns a switch or a select in each row, for those who may change the model: each change is saved at once (the validation of the model, its error shown, the value back). Columns, above the list, hides and shows its columns (but the first), kept by the browser for each model.

Columns

As Django's list_display, a column of list is a field, or: a path across foreign keys ('author__name', its relations loaded with the page, ordered by it), a method or a getter of the model ('displayGenre'; async too; its header is the label of the function, as Django's short_description), a many-to-many field (its objects), or a column of its own, { name, label, value(object) }. Columns that are not fields nor paths are not ordered by. 

class Book extends Model {
  async displayGenre() {
    return (await this.genre.all()).slice(0, 3).map((genre) => genre.name).join(', ');
  }
}
Book.prototype.displayGenre.label = 'Genre';

models: [[Book, { list: ['title', 'author', 'displayGenre', 'author__country', { name: 'size', value: (book) => book.pages }] }]],

Forms

A form has an input for each field: text, numbers, checkboxes, dates and times, the choices of a field, a select of the objects of a foreign key, the objects of a many-to-many (chips, and a select that adds others; required unless it may be blank), JSON. The required ones are marked; keys, automatic dates and readOnly fields are shown, not changed. Saving runs the validation of the model (its fields, its rules, its unique values), and its errors are shown by field. A delete is that of the model: with softDelete, the object is kept with its date.

Below the form of an object are its related lists: the objects of the other models of the admin that point to it (the books of an author), in pages, each a link to its page. Add Book there opens a new book with its author given, and In their list the list of books filtered by it (when author is one of its filters). The other way, a foreign key is a link to its object, in the form and in lists. The option inlines of a model chooses its related lists by the names of their relations; a user sees only those of the models it may view. 

models: [Book, [Author, { inlines: ['bookSet'] }], [Tag, { inlines: false }]],

An inline { relation, fields, extra } is Django's TabularInline: the objects of the relation edited in rows in the page of their object (fields: those of the rows, all that can be by default; extra: the empty rows to add another, 1), with a box to delete each. Save of the card sends them at once: every row is checked first (by the model; the errors are shown in their rows, and nothing is saved), then they are created, changed and deleted in a transaction. Each kind of change needs its permission on their model. In the page of a new object, its inlines have their empty rows too: Save creates the object and its rows together, in one transaction (an error of a row, and nothing is kept). 

models: [[Author, { inlines: [{ relation: 'bookSet', fields: ['title', 'isbn', 'language'], extra: 2 }] }], Book],

Fields and fieldsets

As Django's fields and fieldsets: fields gives the fields of the form in their order, a list of names on one line; fieldsets groups them, each with a title (or none), a description, and collapse (closed until opened). Only the fields they name are in the form, and are changed by it; the read-only ones they name are shown in their place. 

models: [
  [Author, { fields: ['firstName', 'lastName', ['dateOfBirth', 'dateOfDeath']] }],
  [
    BookInstance,
    {
      fieldsets: [
        [null, { fields: ['book', 'imprint', 'id'] }],
        ['Availability', { fields: ['status', 'dueBack', 'borrower'], description: 'On loan or on the shelf' }],
      ],
    },
  ],
],

History

With the audit log of the database (new Database({ ..., audit: true })), the admin has Django's history: the page of an object has its History (each change, newest first: when, who, and the fields that changed, from what to what; redacted fields say only that they changed), and the dashboard the Recent actions of the models the user may view, each a link to its object. The writes of the admin (creates, changes, deletes, actions, inlines) are recorded with who made them (the user of its login, or request.user) and via: 'admin' (and its tenant); the others, as the app records them.

Pipeline runs and health

app.register(xufa.health, { checks: { database: db.health(), queue: queue.health() } });
app.register(admin, { prefix: '/admin', models: [Book], pipelines, authorize });
  • Health: with xufa.health registered, the first page shows its report: the status of the app and each check with its time and its error or details (health: false leaves it out).
  • Runs: with pipelines (a Pipelines of @xufa/queue), the page lists their runs (by status and pipeline, newest first) and shows each run: the graph of its steps in columns by depth, colored by status (a skipped one dashed), with arrows: each column in the order that crosses the fewest of them, and arrows that skip columns drawn around the steps between, a graph that pans and zooms (React Flow, in the bundle), with a minimap when it is large, whose steps may be moved by hand while it is shown (a button puts them back); the step chosen with its block, attempts, times, the end of its wait (pausedUntil), its output and its error; the input and the result of the run. A run that runs is read again every 3 seconds.
  • Pipelines in pipelines: a step of the block pipeline links to the run it started, and shows how far that run is (its steps ended of all, as a bar colored by its status); that run links to the run and step that started it.
  • Actions: Retry (a failed or cancelled run goes on from where it stopped), Cancel (a running one), and Resume of a paused step with its output, as JSON.
  • Start a run: a button of Work and of the runs (for _runs.change) opens a form: the pipeline (with the graph of its steps: a click shows the definition of one), its input as JSON, now or later (in some time, 10m or 1h30m, or at a date), its priority (higher first) and a key (a run of that key still running is opened instead of a new one).

Jobs of the queue

app.register(admin, { prefix: '/admin', models: [Book], queue, login });
  • With queue (a Queue of @xufa/queue), the page lists its jobs, newest first: by status (with the counts of each), name and queue, with their attempts, when they run (or finished) and the first line of their last error. The jobs of the steps of pipelines are hidden (their runs show them; a choice shows them), and such a job links to its run: it is tried again with its run, which goes on from its failed steps.
  • A job shows its queue, priority, attempts, key, times, the worker that runs it, its payload, its result (kept with keepDone) and the whole error of its last run.
  • Retry a failed job, or Retry all failed (those of the name filtered, not those of pipelines): queue.retry(), the workers of the process told at once. Delete a job that does not run: a pending one is cancelled so.

Work

With queue and pipelines, Work in the sidebar lists the jobs of the app and the runs of the pipelines together, newest first, by status (GET api/_work), with a switch to the jobs and the runs, each with its own filters. The jobs of the steps of pipelines are left out: their runs show them. Runs that start later (start() with delay or at) are scheduled until then. With rbac, each kind is for those with _jobs.view or _runs.view.

With scheduler (a Scheduler of @xufa/scheduler), Schedules in Work lists its jobs: their schedule, when they run next, and their last run. Those that start runs of pipelines (pipelines.schedule()) show the last run of the pipeline and link to all of them (the runs filtered by ?trigger=schedule:<name>); a run says the schedule that started it. Run now starts a run (or runs the job) at once. They are for those with _runs.view, and Run now with _runs.change. 

app.register(admin, { prefix: '/admin', models, pipelines, queue, scheduler, login });

Sessions

With its login and @xufa/session, the menu of the account opens Your sessions: each browser logged in as you, with its device, address, login and last request, this one marked; any other is ended with a button (this one, by logging out). With the permission _sessions.view, the page shows those of another user by its id, and with _sessions.change ends them, one or all (a stolen laptop, an employee who leaves).

Data model

The page Data model draws the models as a diagram of entities and relations: a box for each model (its name, app and table, and its fields: keys, types, which may be empty and which are unique) and a line for each relation, from its field to the model it points to (n:1, 1:1 for a unique foreign key, n:m dashed). It has the models of the admin and those they point to (users of @xufa/auth, say), but not the tables the ORM makes for many-to-many relations, drawn as the relation itself. With tenants, the models of the database of the project and those of each tenant's database are in two areas.

  • Models are laid out by their relations: those others point to on the left. They can be moved (kept in the browser) and put back; a search dims those that do not match by name, app or field.
  • A click on a model shows its details: table, app, database, its options (ordering, display, permissions...), and every field with all its options; and a link to its list when the admin lists it.
  • It is for _schema.view (superusers, without rbac: every user of the admin); schema: false hides it. appOf(model) names the app of each model (in a project of xufa, its app).
  • Each model is drawn from specOf() of @xufa/orm: the same data models.yaml holds, for models of code and of data alike.

Editing the models

With a designer (the option designer; a project of xufa gives its own in development), Edit makes the models of the apps' models.yaml editable, for _schema.change; models of code (models.js) keep a lock, and relations can point to them.

  • A model's panel edits its name, ordering and text (display), and its fields: name, type, the model a relation points to and what its deletion does, the longest text, default, label, help, and whether it may be empty, is unique or indexed. Options written by hand (rules, choices...) are kept as they are.
  • New model adds one to an app; a line drawn from a model to another adds a foreign key to it.
  • The changes are a draft, kept in the browser while the files are as they were. Renamed models and fields are remembered, so their migration renames tables and columns instead of dropping them and their data.
  • Review the changes shows the migration of each app (made by the server, in a process of its own: the running app is not touched) and what it drops or may fail on; Publish writes models.yaml and the migration in each app. xufa dev starts the server again on that change, and xufa start applies the migration; the page waits for it.
  • With designer: database in xufa.yaml (in production too), Publish keeps a new version of the models in the project's database instead of files (table xufa_schema: the models of every app and their migrations so far) and migrates it; tenants' databases are migrated when they are opened. Each server looks for a newer version every poll (5s) and starts again with it: xufa start runs its server under a process that starts it again, and workers of @xufa/cluster are made again. A draft of an older version than the last is refused (409). xufa eject turns the last version back into files (models.yaml and migrations), to review them in git or to leave the database for files.
  • The designer: { store, apps(), editable(model), pending(), preview(draft), publish(draft) }; its routes are POST api/_schema/preview and POST api/_schema/publish (a draft that cannot be is 400).

Your account

With its login and reload, the menu of the account opens Your account. Each change asks for the password (its failures locked out as those of the login): 

login: {
  findUser, reload, totp: (user) => user.totpSecret,
  setPassword: (user, hash) => User.objects.filter({ pk: user.pk }).update({ password: hash }),
  setTotp: (user, secret) => User.objects.filter({ pk: user.pk }).update({ totpSecret: secret }), // null: removed
  recoveryCodes: (user) => user.recoveryCodes, // hashes
  setRecoveryCodes: (user, hashes) => User.objects.filter({ pk: user.pk }).update({ recoveryCodes: hashes }),
},
  • Password: with setPassword, a new one (minPasswordLength, 10 by default), hashed with passwordOptions; the other sessions of the user end, this one goes on.
  • Authenticator app: with setTotp, a QR code to scan (qrSvg of @xufa/auth, the key written too), kept in the session for 10 minutes until the first code of the app turns it on; or the app removed.
  • Recovery codes: with recoveryCodes and setRecoveryCodes, ten codes (xxxx-xxxx) shown once when the app is set up, to copy or save; each logs in once in place of a code (Lost the app? in the login page). The page says how many are left, and makes new ones.

Who may use it

Its login page: with login, the admin has a page of its own to log in (GET login, POST login, POST logout) built on @xufa/auth and @xufa/session (registered before the admin): 

app.register(sessionPlugin, { secret: process.env.SESSION_SECRET, store: ormStore(db), csrf: true });
app.register(admin, {
  prefix: '/admin',
  models: [Book, Author],
  login: {
    findUser: (email) => User.objects.filter({ email: email.toLowerCase() }).first(),
    allow: (user) => user.role === 'staff', // who may use the admin
    reload: (id) => User.objects.filter({ pk: id }).first(), // the user again in every request (optional)
    totp: (user) => user.totpSecret, // a code of an authenticator app after the password (optional)
    lastTotpStep: (user) => user.totpStep,
    onTotp: (user, step) => User.objects.filter({ pk: user.pk }).update({ totpStep: step }),
    rehash: (user, hash) => User.objects.filter({ pk: user.pk }).update({ password: hash }),
  },
});

With a model of users (AbstractUser of @xufa/auth), login: { model: User } is all: users log in by username, the active staff (and superusers) may, passwords are changed in the account page, authenticator apps and recovery codes when the model has totpSecret and recoveryCodes, and lastLogin is set. Options given go over those.

  • The login and the account page are the Credentials of @xufa/auth, as its accounts: the same checks, lockouts and codes.
  • Their messages, and the errors of the API the page shows, speak the language of each request with i18n.translateAuth(auth).translateAdmin(admin).
  • Passwords are the hashes of auth.hashPassword() (user.password, or password(user)), checked in constant time; a user that is not there takes the same time, and wrong users, wrong passwords and users that allow refuses get the same answer.
  • Failures lock out: 5 by user in 15 minutes (lockout), 20 by address (ipLockout, so an office behind one address is not locked for a few typing errors); a Lockout of @xufa/auth with a shared store counts them for every worker. Locked attempts get 429 with Retry-After.
  • With totp, the page asks for the code only once the password was right; each code works once (lastTotpStep, onTotp).
  • The user logged in is kept in the session, whose id changes at the login; logging out ends it. The menu of the account logs out of the other sessions of the user, or of every one (POST logout with { others: true } or { everywhere: true }: every browser, process and machine with the store of the sessions; see @xufa/session). With reload(id, request), every request loads the user again and asks allow: one deleted or not allowed any more is logged out at once (allowed again, it logs in again); without it, a user logged in stays so until it logs out or its session ends. Without a user, the page goes to the login page and the API answers 401. The page sends the CSRF token of the session with its writes, so sessions with csrf: true work.
  • authorize, given too, is asked after the login, with request.adminUser ({ id, name }).

Or your own check: authorize(request, reply) is asked for every request of the admin (the page and its API), and is required without login: 'development' lets in every request while NODE_ENV is not production. With @xufa/auth, register the admin after it and look at request.user. Writes need the header the page sends (x-xufa-admin: 1): a form of another site cannot send it (browsers ask the server first), so they need no CSRF token.

Roles and tenants

With rbac (an Rbac of @xufa/auth, or its options), each user sees the models it may view and only the buttons of what it may do: <Model>.view, .add, .change and .delete. With tenants (the Tenants of the ORM), the page has a tenant to choose among those of the user, its models are those of that tenant, and the permissions those of the user in it: 

app.register(admin, {
  prefix: '/admin',
  models: [Book, Author],
  login: { findUser, reload }, // the session keeps what the user may; reload makes it again in every request
  rbac: {
    roles: {
      viewer: ['*.view'],
      editor: { inherits: 'viewer', permissions: ['Book.add', 'Book.change'] },
      owner: ['*'],
      operator: ['_jobs.*', '_runs.*', '_health.view'],
    },
    grants: (user) => Membership.objects.filter({ user: user.pk }).values('tenant', 'role'),
    superuser: (user) => user.isSuperuser,
  },
  tenants: {
    tenants, // new Tenants({ models: [Book, Author], config })
    list: () => Organization.objects.valuesList('slug', { flat: true }), // for superusers and grants in every tenant
    label: (id) => id.toUpperCase(),
  },
  queue,
});
  • A user with an editor grant in acme and a viewer grant in globex chooses between the two: it adds and changes books in acme, and only sees them in globex. A grant in every tenant (tenant: '*') or a superuser chooses among all of list().
  • The page sends the tenant chosen as x-xufa-tenant; a tenant that is not the user's is answered with 403 before its database is opened. The admin enters the tenant itself: the plugin of the ORM leaves its routes alone (they have config: { tenant: false }), so the app's own routes can resolve their tenants as they like.
  • The jobs, the pipeline runs and the health are not of one tenant: they need _jobs.view, _runs.view and _health.view in every tenant (and .change to retry, cancel or resume, _jobs.delete to delete).
  • The permissions of users and groups (AbstractUser, AbstractGroup) are picked in their forms, as Django's: chips of those given, and a list to find others in, by the label of each model (Can add book, Meta.permissions too), with every one of a model (Book.*), all (*, *.view) and those of the jobs, runs, health and sessions the admin has. A pattern not in the list is added as typed. The roles a group inherits are picked the same way, from those in code and the groups. Any JSON field with the option widget: 'permissions' or 'roles' gets them.
  • With login, users without any grant cannot log in (unless allow says otherwise), and the session keeps their access from the login; with reload (as login: { model } has), it is made again at each request, so a role or a group given or taken away (groups) counts at the next one. Without login, the access is that of request.user (of @xufa/auth).

Languages

The page speaks the language of each request: Spanish, French, German, Portuguese and Italian come with the admin, English otherwise. It is the option language when given, else request.locale (of @xufa/i18n, pt-BR gives pt), else the first language of the Accept-Language of the browser the admin has. Dates and numbers follow it too. With uiMessages, the app changes texts of the page (by their English) or adds languages: 

app.register(admin, {
  models: [Book, Author],
  authorize: (request) => request.user?.isStaff === true,
  language: null, // 'es': Spanish for everyone
  uiMessages: {
    es: { Save: 'Grabar' }, // over the Spanish of the admin
    ca: { Save: 'Desa', Models: 'Models' }, // a language of its own: its texts, English for the rest
  },
});

The texts of the page are those of its t() calls (node packages/admin/client/texts.js prints them), with parameters such as {count} kept as they are in each language. The names of models and fields are those the app gives them (their labels), not translated by the admin.

Its API

The page uses an API of its own, under the prefix (it can be used by scripts too, with the header for writes). A key that cannot be one (/Book/nope for an integer key) is not found, and never reaches the database.

GET api/_runsThe runs of the pipelines: ?status=, ?pipeline=, ?page=; the counts by status and the names of the pipelines
GET api/_runs/:idA run: its input, result, error, the graph of its definition and its steps
GET api/_runs/schedules, POST api/_runs/schedules/:name/runThe jobs of the scheduler (schedule, next, their runs; pipeline, trigger, lastPipelineRun, pipelineRuns), and Run now: { run } for those of pipelines, 202 for others
GET api/_runs/pipelinesThe pipelines to start: { name, trigger, steps, graph } (the graph as a run's)
POST api/_runsStarts a run: { pipeline, input, delay | at, priority, key }; 201 with the run, or 200 with existing: true (the running run of the key); 400 with errors by field
POST api/_runs/:id/retry, /cancel, /steps/:step/resumeThe actions (resume takes { output }); 409 when the run or step is not in a state for them
GET api/_jobs, GET api/_jobs/:idThe jobs of the queue (?status=, ?name=, ?queue=, ?page=, ?pipelines=1 with those of pipelines; the counts by status, and retryable: the failed ones Retry all takes; due: { now, later, oldest, wait, late, workers }, what waits in the queue), and a job with its payload, result and error
POST api/_jobs/:id/retry, POST api/_jobs/retry, DELETE api/_jobs/:idRetry a failed job (409 otherwise), every failed one (?name=: of a name; gives { retried }), and delete one that does not run (409 when it runs)
GET api/_healthThe report of xufa.health, its checks run now (404 without it)
