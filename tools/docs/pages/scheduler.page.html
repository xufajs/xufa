@xufa/scheduler

Jobs that run every so often, on cron expressions, or once, with no dependencies. Each job has a timer of its own, so a slow job delays no other one and a failure stops none; a run does not overlap the one before it; a timeout aborts the signal of a run, and a run that fails is tried again with backoff; a history records every run (and runs the times missed when a process starts again); and, with a lock in a database, each time of a job runs in one process among those of several machines.

Quick start

npm install @xufa/scheduler
import { Scheduler } from '@xufa/scheduler'; // or from 'xufa/scheduler'

const scheduler = new Scheduler({ logger, timezone: 'Europe/Madrid' });
scheduler.add({ name: 'purge sessions', every: '10m', run: () => Session.objects.filter({ expired: true }).delete() });
scheduler.add({
  name: 'daily report',
  cron: '0 8 * * mon-fri',
  timeout: '5m',
  run: async ({ signal, scheduledAt }) => sendReport({ day: scheduledAt, signal }),
});
scheduler.start();
// ...
await scheduler.stop(); // waits for the runs going on (10 s), then aborts their signals

Jobs

scheduler.add(job): a name, a run(context) function, and one of:

  • every: '10m': at the multiples of the interval since 1970 (:00, :10, :20...), so processes on other machines agree on the times; align: false counts from the start.
  • cron: '0 8 * * mon-fri': a cron expression, in timezone (of the job, of the scheduler, or the local one).
  • at: date: once, at a date (a time past runs at the start); in: '30s': once, that long after the start.

Durations are milliseconds or texts: '500ms', '30s', '10m', '2h', '1d', '1w', '1h30m'.

OptionDefaultWhat it does

run gets { name, scheduledAt, attempt, signal, data, scheduler }; what it returns (or the promise of it) ends the attempt. An attempt that does not stop when its signal is aborted goes on by itself, but its job goes on. Times missed (the process was stopped, or busy) are not run later, but with catchUp.

Cron expressions

minute hour day-of-month month day-of-week, or six fields with seconds first. Each field is *, a value, a range (1-5), a list (1,15,30) or steps (*/15, 0-30/10); months and days of the week by name too (jan, mon-fri; 0 and 7 are Sunday); the macros @yearly, @monthly, @weekly, @daily and @hourly. As in Vixie cron, when both the day of the month and of the week are given, a day matching either runs. An expression that can never run (0 0 30 2 *) is an error.

In a time zone that changes its clock, a time that does not exist (02:30 when 02:00 is 03:00) is skipped, and an hour that repeats runs once. nextRuns(expression, count, { timezone, from }) gives the next times of an expression.

Retries

With retries, a run that fails (or times out) is tried again after retryDelay, then after that multiplied by retryFactor, up to maxRetryDelay; each attempt gets its number (attempt) and has the timeout. The attempts are one run: the job is running between them (its times are skipped, or wait), it keeps its claim of the lock, and only the last error is a failure. stop() ends the waits between them. 

scheduler.add({ name: 'sync prices', every: '15m', retries: 3, retryDelay: '30s', timeout: '2m', run: syncPrices });

State and events

scheduler.jobs() and scheduler.job(name): { name, schedule, next, running, runs, failures, skipped, lastRun, lastDuration, lastError }. remove(name), has(name), and runNow(name): a run now, out of the schedule. Events: 'run', 'retry', 'done', 'failure', 'catchUp' and 'skip' (with why: 'running' or 'locked'); onError(error, job) and the logger see every failure.

Health

scheduler.health() is a check of xufa.health: degraded when a job missed a run, failed its last runs, or runs for too long, with each job's next run, last run and status in its details. 

app.register(xufa.health, {
  checks: {
    scheduler: scheduler.health({ late: '1m', failures: 3, maxRun: '30m' }),
  },
});
  • Missed: a job of every or cron was due more than late ('1m') ago and nothing ran it. With a shared history it is a run of no machine (the process that runs it, behind a lock, may be another); without one, the timers of this process.
  • Failing: its last failures runs (1) failed or timed out, in the history (of every machine) or in this process.
  • Too long: a run of this process going on for longer than maxRun.
  • jobs: ['report'] checks only those; critical (false) and timeout are those of every check.

History and catch-up

With a history, the scheduler records every run: { name, scheduledAt, startedAt, duration, status, attempts, error, host }, its status 'done', 'failed' or 'timeout'; scheduler.history(name, { limit }) gives them, the last first. memoryHistory({ keep }) keeps the last runs of each job in the process; ormHistory(db, { maxAge }) keeps them in a table of a database (xufa_scheduler_runs), shared by every machine, and deletes those older than maxAge (30 days). 

const scheduler = new Scheduler({ history: ormHistory(db), lock: ormLock(db) }); // their tables: db.sync()
scheduler.add({ name: 'invoices', cron: '0 2 * * *', catchUp: true, run: makeInvoices });

A job with catchUp runs, when the scheduler starts, the last time due that the history has no run of (once, not every time missed); a new job, with no runs in the history, does not. With a history and a lock in a database, one machine catches up a time, and those that start later do not again.

Runs of pipelines

A job runs in the process of the scheduler, and keeps no more than its history. For work that should be kept, retried and seen, make the job start a run of a pipeline of @xufa/queue: the scheduler only starts it, the workers of the queue do it. 

pipelines.task('nightly-export', () => exportRows(), { attempts: 3 });
pipelines.schedule(scheduler, 'nightly-export', { cron: '0 2 * * *', timezone: 'Europe/Madrid' });

The admin (option scheduler) lists the jobs of the scheduler in Work: when each runs next, its last run (for those of pipelines, the last run of the pipeline and all of them), and Run now.

Clusters and machines

A scheduler runs its jobs in its process: in a cluster of @xufa/cluster, make it in the primary (or in one worker), not in every worker. On several machines, give the schedulers a lock in a database of @xufa/orm (any backend), and each time of a job runs in one of them: 

import config from './config.js'; // loadConfig() of @xufa/config

start({
  primary: async ({ onShutdown }) => {
    const db = new Database({ ...config.database });
    const scheduler = new Scheduler({ lock: ormLock(db), history: ormHistory(db), timezone: config.timezone }); // db.sync() makes their tables
    await db.connect();
    await db.sync();
    scheduler.add({ name: 'purge', every: config.jobs.purgeEvery, catchUp: true, run: purge }); // a duration of the schema: ms
    scheduler.start();
    onShutdown(async () => {
      await scheduler.stop();
      await db.close();
    });
  },
  worker: async () => { /* the app */ },
});

The times of a job agree between machines (every is aligned to the clock), and a claim is taken by one atomic conditional update. While a run goes on its claim is renewed, and no other machine starts that job; when the process of a run dies, its claim expires after lockTtl. Keep the clocks of the machines in time (NTP). A lock of your own is { claim, renew, release }; memoryLock() is one in the process.

The plugin

For @xufa/http and fastify: app.scheduler, started when the app is ready (start: false leaves that to you), and stopped when it closes, its runs waited for. Its options are those of a Scheduler (the logger of the app by default), and jobs, or scheduler: one made before. 

app.register(schedulerPlugin, { jobs: [{ name: 'purge', every: '10m', run: () => Session.purge() }] });
