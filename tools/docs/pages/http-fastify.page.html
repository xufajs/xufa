From fastify

@xufa/http has fastify's API, and runs fastify's own test suite. For most apps, moving is changing a require; this page is the rest: the names that differ, the validator, the logger, and plugins.

The steps

  1. Install it, and change the module the app is made with:

    npm install @xufa/http
npm uninstall fastify
    // import fastify from 'fastify';
import fastify from '@xufa/http'; // the name you call it does not matter
const app = fastify({ logger: true });
  2. Code that compares error codes: FST_ERR_* are XUFA_ERR_* (Names).
  3. TypeScript: FastifyInstance is XufaInstance, and so on (TypeScript names).
  4. A logger with transport: xufa's logger has none. Pipe the output to the tool (node app.js | pino-pretty), or give pino itself as loggerInstance (Logger).
  5. ajv plugins (ajv.plugins): see what @xufa/schema has in their place.
  6. Run the tests of the app. The plugins you use are in fastify's ecosystem.

Which fastify

xufa follows fastify's main branch: the test suite it runs is that of 6.0.0-alpha.4, so it behaves as fastify 6 will. Apps written for fastify 5 run on it unless they use what fastify 6 changes. Among what it has: handlerTimeout and request.signal, router options in routerOptions (at the top of the options they still work), and a second setErrorHandler() in the same plugin is an error (XUFA_ERR_ERROR_HANDLER_ALREADY_SET) unless allowErrorHandlerOverride: true.

Validation: @xufa/schema

The default validator compiles schemas with @xufa/schema instead of ajv, and reports errors as ajv does (instancePath, keyword, params, message), so attachValidation, schemaErrorFormatter and error handlers work unchanged. It is configured as fastify configures ajv: coerceTypes: 'array', useDefaults, removeAdditional. It passes every test of the JSON-Schema-Test-Suite, draft-04 to 2020-12 (Benchmarks), and is loaded when a route first has a schema.

A route that needs what is not supported can still use ajv: setValidatorCompiler() takes any compiler, for the app, a plugin or one route. 

import Ajv from 'ajv';
import ajvErrors from 'ajv-errors';

const ajv = new Ajv({ allErrors: true });
ajvErrors(ajv);

app.register(async (legacy) => {
  legacy.setValidatorCompiler(({ schema }) => ajv.compile(schema));
  legacy.post('/signup', { schema: { body: SignupWithErrorMessages } }, signup);
});

Options of @xufa/schema itself go in validation: xufa({ validation: { foldMessages: true } }) builds the errors of invalid requests faster, for compiling the routes about 4% slower (its options).

Logger

logger: true, or logger options, make an @xufa/logger: pino's options and API (levels, child loggers, serializers, redact, mixin, formatters), in the same JSON lines, without transports. Give it a stream (logger: { stream }), or a logger of your own as loggerInstance: pino itself works, with its transports. 

// Transports, as with fastify: pino is the logger.
import pino from 'pino';
const app = xufa({ loggerInstance: pino({ transport: { target: 'pino-pretty' } }) });

Plugins

xufa.plugin() is fastify-plugin:

import { plugin } from '@xufa/http';

export default plugin(
  async (app, options) => {
    app.decorate('db', await connect(options.url));
  },
  { name: 'db', xufa: '0.x' }
);

The range of versions a plugin needs is xufa in its metadata. Plugins written for fastify, with fastify-plugin, load as they are: their fastify range is not checked, since it is a range of fastify's versions, and decorators.fastify counts as decorators.xufa.

Responses as bytes

Routes with a response schema whose output can be large (arrays, maps, recursive schemas) write their JSON as UTF-8 bytes and send that Buffer, without making a string first. A string joined from many pieces must be copied into one before it can be written to a socket; for large responses that copy costs about as much as making the JSON. When the route has onSend hooks, they get a string, as in fastify.

The head of responses

For most responses, xufa writes the status line and the headers itself, as one string, instead of calling res.writeHead(): they are the same bytes (a self-test compares them with those of Node.js when the server starts, and turns this off for good if they differ), and the names and values of the headers are checked as Node.js checks them. It covers HTTP/1.1 responses kept alive with any status from 200, with a body of known length or none (HEAD, 204, 304, empty replies), and headers set on reply.raw too, merged as writeHead() merges them. Node.js writes the others: streams, trailers, HTTP/1.0 and connections that close.

  • reply.raw.getHeaders() gives what it gives after writeHead(): the headers set on reply.raw, and those of the reply too when there were some. Code that wraps res.writeHead() of Node.js (some tracing tools do) does not see these responses go through it.
  • xufa({ fastHead: false }) leaves every head to Node.js.

Where it is faster

  • The head of most responses, written by xufa (above), where Node.js checks and assembles every header of every response: most of what a small response costs.
  • The router matches static paths with one map lookup, and compiles its tree into one function once it is hot: 1.15× to 1.67× find-my-way on routes with parameters (Router performance).
  • The query string is left unparsed until request.query is read.
  • Serializers write large responses as bytes (above): about 1.4× fastify on a big JSON response.
  • Validation is compiled by @xufa/schema: about 2× ajv on payloads (its benchmarks).

The numbers are in Benchmarks.

How it is tested

The tests of fastify and of the libraries it uses (find-my-way, pino, fast-json-stringify, light-my-request, avvio) are ported, not rewritten: a tool of the repository converts their node:test suites to vyntra and renames what fastify calls itself. 2,288 tests of fastify's suite pass. Of the 23 skipped, 12 are of ajv's plugins and asynchronous validation, 6 check fastify's documentation files, and the others need what the machine they run on may lack (Unix sockets, IPv6, Node.js 24). Tests of what xufa does differently are written apart, so a new port does not overwrite them. The TypeScript declarations are checked by fastify's type tests, ported.
