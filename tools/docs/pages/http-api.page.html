API

Everything @xufa/http has, as fastify's documentation describes it, with xufa's names and defaults. Where xufa adds or differs, the entry says so; the reasons are in From fastify. The Guide shows them in use.

Plugins

import { plugin } from '@xufa/http';

export default plugin(async (app, options) => { /* ... */ }, {
  name: 'my-plugin', // for hasPlugin() and the dependencies of others
  xufa: '0.x', // the versions of xufa it needs (a semver range)
  dependencies: ['db'], // plugins that must be registered before
  decorators: { xufa: ['db'], request: ['user'], reply: [] }, // decorators that must be there
  encapsulate: false, // true: wrapped, but still encapsulated (to name it)
});

A plugin of fastify's ecosystem, made with fastify-plugin, loads as it is: its fastify range is not checked (it is of fastify's versions), and decorators.fastify counts as decorators.xufa.

Error codes

errorCodes of @xufa/http: classes of errors (instanceof works), each with its code and statusCode. The codes are fastify's with XUFA_ERR_ in place of FST_ERR_; … is where a value of the error goes.

TypeScript types

The types of fastify, renamed: XufaInstance, XufaRequest, XufaReply, XufaPluginAsync, XufaPluginCallback, XufaPluginOptions, XufaSchema, XufaServerOptions, XufaError, XufaBaseLogger, RouteOptions, RouteShorthandOptions, RouteGenericInterface, XufaTypeProvider, XufaTypeProviderDefault... Decorators are declared by augmenting the module: 

declare module '@xufa/http' {
  interface XufaInstance {
    db: Database;
  }
  interface XufaRequest {
    user: { id: string } | null;
  }
}
