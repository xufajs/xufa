@xufa/pg

A PostgreSQL driver with the API of pg (node-postgres) for what applications use, Client, Pool and query(text, values), and no dependencies. It prepares statements, sends and reads values in the binary format and pipelines queries on a connection, so the same code runs from 1.3 to 5 times faster than on pg. The PostgreSQL backend of @xufa/orm is made with it.

Quick start

npm install @xufa/pg
const { Pool } = require('@xufa/pg');

const pool = new Pool({ connectionString: 'postgres://user:password@localhost:5432/app', max: 10 });

const { rows } = await pool.query('SELECT id, name FROM users WHERE name ILIKE $1', ['a%']);
console.log(rows); // [{ id: 1, name: 'Ada' }]

await pool.end();

Code written for pg runs as it is: require('pg') can be replaced by require('@xufa/pg'). The differences are few and listed in Coming from pg.

Client

One connection, opened by connect().

const { Client } = require('@xufa/pg');

const client = new Client('postgres://user:password@localhost:5432/app');
await client.connect();
const { rows, rowCount, fields } = await client.query('SELECT $1::int + 1 AS n', [41]);
const asArrays = await client.query({ text: 'SELECT 1, 2', rowMode: 'array' }); // rows: [[1, 2]]
await client.end();

await using client = ... (explicit resource management) ends a client at the end of its block.

Pool

Connections opened when they are needed, up to max. pool.query() sends a query to the least busy connection without waiting for the ones before it (they are pipelined: pg runs one query at a time on a connection), and opens another only when every connection is busy. 

const pool = new Pool({ connectionString: process.env.DATABASE_URL, max: 20, idleTimeoutMillis: 30_000 });
pool.on('error', (err) => log.warn(err)); // a connection closed while idle: the pool opens another

await Promise.all(ids.map((id) => pool.query('SELECT * FROM users WHERE id = $1', [id])));
MemberWhat it does
query(text, values)A query on a connection of the pool.
connect()A PoolClient: a connection of its own (for a transaction) until release(). release(err) (or true) closes it instead. using client = await pool.connect() releases it at the end of its block.
end()Ends the pool: it waits for the queries sent and for the clients given by connect() to be released.
totalCount, idleCount, waitingCountThe connections, those idle, and who waits for one.
openConnection(options)Opens the connections of the pool: replace it to wrap them (the layer of Sequelize does, for _connect).
Eventsconnect, notice, and error for connections closed by the server or the network while idle. Listen to it: an error event without a listener ends the process.
OptionDefaultWhat it does

idleTimeoutMillis10000A connection idle this long is closed.
acquireTimeoutMillis0How long a query or connect() waits for a connection, free or being opened (0: no limit). Past it, an error of code ACQUIRE_TIMEOUT; a connection that comes late is given back.

And every option of a Client, for each connection.

Transactions

A transaction needs a connection of its own: take one with connect().

const client = await pool.connect();
try {
  await client.query('BEGIN');
  await client.query('UPDATE accounts SET balance = balance - $1 WHERE id = $2', [100, 1]);
  await client.query('UPDATE accounts SET balance = balance + $1 WHERE id = $2', [100, 2]);
  await client.query('COMMIT');
} catch (err) {
  await client.query('ROLLBACK');
  throw err;
} finally {
  client.release();
}

A connection given back in a transaction (or broken) is closed, not given to anyone else.

Connection strings and PG*

Connection strings are read as libpq reads them: postgres://user:password@host:port/database?..., with host, port, dbname, user, password, application_name, options and connect_timeout (seconds) as parameters too, and the parameters of TLS below. The variables of libpq are read as well:

TLS

sslmode has its meaning in libpq:

sslmodeWhat it does
disableNo TLS.
allow, preferTLS when the server has it.
requireEncrypted, without checking the certificate (unless sslrootcert is given).
verify-caThe chain of the certificate is checked.
verify-fullThe chain and the host (an IP address too).
no-verifypg's: encrypted, nothing checked.

With ssl=true|false, sslcert, sslkey, sslrootcert (files; system for the authorities of the system) and sslpassword. Data a server sends before TLS is set up is refused, as libpq does since CVE-2021-23222.

Authentication

SCRAM-SHA-256 (bound to the TLS channel, SCRAM-SHA-256-PLUS, when the server offers it), MD5 and cleartext passwords, and OAuth tokens (oauthBearerToken, a string or a function: OAUTHBEARER of PostgreSQL 18). As in libpq, require_auth names the methods the server may ask for (scram-sha-256, password,md5, !password, none...) and channel_binding (prefer by default, require, disable) whether SCRAM is bound to the channel: with require, a server that asks for a password instead is refused without sending it.

Every request of the server is checked before it is answered: a server that asks twice is refused, and so is one that makes the connection usable without authenticating it. 

new Pool({
  connectionString: 'postgres://app@db.internal/app?sslmode=verify-full',
  require_auth: 'scram-sha-256',
  channel_binding: 'require',
  password: async () => secrets.get('db-password'), // asked for every connection
});

Several hosts

host and port as lists ('db1,db2', arrays, or postgres://u@db1:5432,db2:5433/app) are tried in order until one connects. target_session_attrs skips the hosts that are not what is asked for: read-write, read-only, primary, standby or prefer-standby (read from what PostgreSQL 14 and later report, or asked to older servers); load_balance_hosts=random tries them in a random order. Each connection of a pool finds its host. 

const writes = new Pool({ connectionString: 'postgres://app@db1,db2,db3/app?target_session_attrs=read-write' });
const reads = new Pool({ connectionString: 'postgres://app@db1,db2,db3/app?target_session_attrs=prefer-standby&load_balance_hosts=random' });

COPY

On Client, PoolClient and Pool (which takes a connection for it):

// Rows (arrays, or objects by column): binary COPY when every column has a binary encoder.
const count = await pool.copyRows('users', ['id', 'name', 'joined'], [
  [1, 'Ada', new Date()],
  { id: 2, name: 'Grace', joined: new Date() },
]);

// COPY ... FROM STDIN with data in the format of the COPY: a Buffer, a string, or an (async) iterable of them.
await pool.copyFrom('COPY events FROM STDIN (FORMAT csv)', fs.createReadStream('events.csv'));

// COPY ... TO STDOUT as an async iterator of Buffers (the socket waits while too much is unread).
for await (const chunk of pool.copyTo('COPY events TO STDOUT (FORMAT csv)')) out.write(chunk);

copyRows(table, columns, rows) reads the types of the columns from the table and sends the rows in the binary format of COPY (the server parses nothing) when every column has a binary encoder: numbers, booleans, text, json and jsonb, dates and timestamps, bytea, uuid, and arrays of them; in the text format otherwise. The table is 'schema.table', or [schema, table] for names with dots. An error of the data fails the whole COPY: nothing is copied.

Cancelling and timeouts

const controller = new AbortController();
setTimeout(() => controller.abort(), 1000);
await pool.query({ text: 'SELECT pg_sleep(10)', signal: controller.signal }); // AbortError

await pool.query({ text: 'SELECT slow()', timeout: 500 }); // code QUERY_TIMEOUT
new Pool({ query_timeout: 2000 }); // for every query

The query rejects at once, and the server is asked to stop it (a CancelRequest). Such a query has its connection to itself (it is not pipelined), so the cancel stops it and no other. When the server has ended it, the connection is given to whoever waits for it.

Describing a query

const { params, fields } = await pool.query({ text: 'SELECT id, name FROM users WHERE id = $1', describe: true });
// params: [23] (the oid of int4); fields: [{ name: 'id', dataTypeID: 23, ... }, { name: 'name', ... }]

The types of the parameters and the columns of a text, without running it.

LISTEN and NOTIFY

const client = new Client(process.env.DATABASE_URL);
await client.connect();
client.on('notification', ({ channel, payload, processId }) => console.log(channel, payload));
await client.query('LISTEN orders');
// elsewhere: NOTIFY orders, 'order 42 paid'

After changes of the schema

Prepared statements remember the types of their tables. After tables or types are dropped and made again, forgetStatements() (of a client or a pool) makes every connection prepare its statements again before its next query, so queries, in a transaction too, find the new types instead of failing. Statements that fail with type errors after such changes are prepared again by themselves. The ORM calls it after its migrations.

Tracing

node:diagnostics_channel, with the channels of pg: pg:query, pg:connection and pg:pool:connect (tracing channels: their contexts have the query, the client and the result or the error), and pg:pool:release and pg:pool:remove. Nothing is made when no one subscribes. 

const dc = require('node:diagnostics_channel');
dc.tracingChannel('pg:query').subscribe({
  start: (ctx) => (ctx.started = performance.now()),
  asyncEnd: (ctx) => metrics.observe(ctx.query.text, performance.now() - ctx.started),
});

Errors

DatabaseError, with the fields of pg: code (the SQLSTATE: 23505 for a unique violation), detail, hint, constraint, table, column, position... ConnectionError for the connection, and PgError for both. Pool timeouts have the code ACQUIRE_TIMEOUT, and query timeouts QUERY_TIMEOUT.

Performance

  • Queries are prepared once per connection the second time their text runs: after that, only their values are sent. A text that runs once (with its values written in it, as Sequelize does) runs as in pg, so it does not fill the cache of statements (up to 1000 by connection).
  • Prepared queries send parameters and read results in the binary format for the types that have it (integers, floats, booleans, timestamps, dates, bytea, uuid): the server neither formats nor parses them as text.
  • Queries are pipelined on the connections of a pool.
  • Values are parsed from the bytes of the rows (numbers and dates without making strings), and rows are made by a function compiled for their columns.

Coming from pg

  • bigint (int8) is a number while it is a safe integer, and a bigint beyond; pg gives strings. Code that expects strings can pass a parser in types (oid 20).
  • Queries are prepared the second time their text runs, without a name (pg prepares only named queries). prepare: false turns it off, for poolers in transaction mode (PgBouncer before 1.21).
  • pool.query() pipelines on a connection: queries no longer wait for the ones before them on a busy connection.
  • The text format of the values is used only for the types without a binary one; custom parsers (types) get text, as in pg.
  • Not there: pg-native, pg-cursor and pg-query-stream (use copyTo for large exports).

TypeScript

Declarations are in the package: Client, Pool, PoolClient, QueryResult<R>, QueryConfig, DatabaseError...

import { Pool, QueryResult } from '@xufa/pg';

interface User { id: number; name: string }
const pool = new Pool({ connectionString: process.env.DATABASE_URL });
const { rows }: QueryResult<User> = await pool.query<User>('SELECT id, name FROM users');
