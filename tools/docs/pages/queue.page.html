@xufa/queue

Jobs in the background, kept in a database of @xufa/orm (SQLite, PostgreSQL, MongoDB, files or memory): the queues of Laravel and Rails' Active Job, with no dependencies and no Redis. Workers run on any process or machine that has the database, each job once; jobs that fail are tried again with backoff; and a job enqueued in a transaction is there only when the transaction commits. Pipelines run graphs of steps as its jobs, each run and step kept in the database.

Quick start

const { Database } = require('@xufa/orm');
const { Queue } = require('@xufa/queue');

const db = new Database({ backend: 'memory' }); // or postgres, sqlite, mongodb...
const queue = new Queue(db); // its model (table xufa_jobs) is registered in db
await db.sync();

queue.define('welcome', async ({ name }) => {
  console.log(`Welcome, ${name}!`);
});
await queue.enqueue('welcome', { name: 'Ada' });
await queue.enqueue('welcome', { name: 'Grace' }, { delay: '1h' });
console.log(await queue.counts());

console.log(await queue.runDue()); // without workers: the jobs due now
{ pending: 2, running: 0, done: 0, failed: 0 }
Welcome, Ada!
{ done: 1, retrying: 0, failed: 0 }

In an app, workers run the jobs as they come: queue.work({ concurrency: 4 }).

Jobs

define(name, handler, options) names a kind of job: its function gets the payload and the job (an object of the model: attempts, signal, runAt...). 

queue.define('invoice', async ({ orderId }, job) => {
  const order = await Order.objects.get({ pk: orderId });
  await renderInvoice(order, { signal: job.signal }); // aborted at the timeout
  return { pages: 2 }; // kept as its result with keepDone: true
}, { attempts: 5, backoff: { delay: '10s', max: '1h' }, timeout: '1m', queue: 'billing' });
OptionDefaultWhat it is
attempts3Runs before the job is failed
backoff5 s to 1 hThe delay before a job is tried again: exponential ({ delay, max }, doubling, with jitter), { type: 'fixed', delay }, ms, or a function of the attempts
timeout'5m'A run longer is failed, and its signal aborted
queue'default'The queue of its jobs (workers can take some queues only)

new Queue(db, options) takes the same options as defaults of its jobs, and table (xufa_jobs), model, keepDone (done jobs kept with their results; deleted otherwise) and logger.

Enqueueing

await queue.enqueue('invoice', { orderId: 7 });
await queue.enqueue('report', { month: 10 }, { delay: '10m' });          // or at: new Date(...)
await queue.enqueue('alert', { id: 1 }, { priority: 10, queue: 'urgent' }); // higher first
await queue.enqueue('sync', { userId: 3 }, { key: 'sync:3' });           // not twice while one is pending or running

enqueue gives the job (with key, the one there when there is one). The payload is JSON.

Failures and retries

A job that throws (or goes over its timeout) is tried again after its backoff, up to its attempts; then it is kept as failed, with the stack of its error in lastError. queue.retry() takes the failed jobs back (all, or those of the ids given). 

queue.on('failed', (job, err) => log.error({ err, job: job.pk }, 'job failed'));
const failed = await queue.jobs.filter({ status: 'failed', name: 'invoice' }); // a queryset of the jobs
await queue.retry(failed.map((job) => job.pk));

The queue emits completed (job, result), retrying (job, error, delay) and failed (job, error). The option onFailure(job, err, final) of define is waited for when a run fails, before the job is tried again or failed.

Workers

queue.work({ concurrency, queues, poll }) starts a worker in the process: it runs up to concurrency jobs at once (1), of some queues (all), looking for jobs every poll (1 s) and at once when its process enqueues one. Workers claim each job with an update only one of them can make (a pending job to running), so every worker of every machine with the database can run them, and each job runs once. A job whose worker died while it ran (past lockedUntil: its timeout and 30 s) is taken back by the others, or failed when it has no attempts left. queue.stop() stops the workers, waiting for the jobs they run.

Pools of nodes

A kind of job whose work goes to other servers that take a few tasks at once (document converters) can run on a pool of nodes of @xufa/cluster: its jobs wait for a free node before they are claimed, so they stay pending while they wait (other machines can take them), their timeout counts their run only, and they run with job.node. The pool hands the nodes out among every worker of the process's cluster, in order. 

const { Database } = require('@xufa/orm');
const { Queue } = require('@xufa/queue');
const { createPool } = require('@xufa/cluster');

const db = new Database({ backend: 'memory' });
const queue = new Queue(db);
await db.sync();

const converters = createPool('converters', { nodes: [{ id: 'converter-1', url: 'http://10.0.0.7:8080' }], leaseTimeout: '5m' });
queue.define(
  'convert',
  async ({ file }, job) => {
    // fetch(`${job.node.url}/convert`, { method: 'POST', body: file, signal: job.signal })
    console.log(`${file} on ${job.node.id}`);
  },
  { pool: converters, attempts: 3 }
);
await queue.enqueue('convert', { file: 'a.docx' });
await queue.enqueue('convert', { file: 'b.docx' });
console.log(await queue.runDue());
converters.close();
a.docx on converter-1
b.docx on converter-1
{ done: 2, retrying: 0, failed: 0 }

A job waiting for a node takes a place of the worker's concurrency: give such jobs their own queue and worker when other jobs must not wait behind them. When the pool takes the node back (its leaseTimeout, the node gone), job.signal is aborted and the run fails, to be tried again after its backoff; a node that answers busy (429) is left aside for a while. In a worker of a cluster, pool: usePool('converters') uses the pool of the primary, and with shared slots the pools of several machines share the nodes.

In transactions

The jobs are objects of the database, so a job enqueued in a transaction is written with the rest: when the transaction fails, there is no job; when it commits, the job sees the data it was enqueued for. A message sent after the commit, or lost before, does not happen (the pattern of the outbox). 

await db.transaction(async () => {
  const order = await Order.objects.create({ total });
  await queue.enqueue('invoice', { orderId: order.pk });
});

The plugin

const { queuePlugin } = require('@xufa/queue');

app.register(queuePlugin, { queue, work: { concurrency: 4 } }); // leave out work in processes that only enqueue
app.post('/signup', async (request, reply) => {
  await app.queue.enqueue('welcome', { email: request.body.email });
  return reply.code(202).send();
});

The workers start when the app is ready, and stop when it closes. With @xufa/scheduler jobs can be enqueued by time, and with the mail backends of the ORM a message can be sent in the background: queue.define('mail', (message) => Email.objects.create(message)).

Health

queue.health() is a check of xufa.health: the counts of the jobs, the lag (how long the oldest job due has waited: workers that do not keep up, or none at all) and the workers of the process. It is degraded when the lag is more than maxLag ('5m'), or the jobs pending or failed more than maxPending or maxFailed, and down when the jobs cannot be read. Not critical by default (critical: true makes it so). 

app.register(xufa.health, {
  checks: { database: db.health(), queue: queue.health({ maxLag: '2m', maxFailed: 100 }) },
});
// GET /health: { status: 'up', checks: { queue: { status: 'up', details: { pending, running, failed, lag, workers } } } }

In tests

queue.runDue() runs the jobs due now one after another, without workers, and gives counts by outcome; queue.counts() and queue.jobs tell what is there. With the memory backend, a test needs no database server.

Pipelines

A pipeline is a graph of steps run as jobs of the queue, and every run keeps, in the database, the status, output, error and attempts of each of its steps. It is data, so it can be stored, edited by users and shown: each step runs a block (a kind of work your code registers) with its config, after other steps (fan out and join), when a condition holds, and the outputs of some steps make the result of the run. 

const { Database } = require('@xufa/orm');
const { Queue, Pipelines } = require('@xufa/queue');

const db = new Database({ backend: 'memory' });
const queue = new Queue(db);
const pipelines = new Pipelines(queue); // its models (xufa_pipeline_runs, _steps) registered in db
await db.sync();

pipelines.block('measure', (doc) => ({ words: doc.words, links: doc.links.length }));
pipelines.block('score', (input, { config }) => Math.round(input.links * config.weight * 100) / 100);

pipelines.define({
  name: 'ingest',
  trigger: 'document.uploaded',
  steps: [
    { id: 'measure', block: 'measure' },
    { id: 'links', block: 'score', after: 'measure', config: { weight: 0.5 } },
    { id: 'detail', block: 'score', after: 'measure', config: { weight: 2 }, when: 'input.words >= 1024' },
    {
      id: 'report',
      block: 'transform',
      after: ['links', 'detail'],
      config: { map: { links: 'input.links', detail: 'input.detail ?? "skipped"', user: 'run.input.user' } },
    },
  ],
});

const [run] = await pipelines.trigger('document.uploaded', { user: 'ada', words: 800, links: [1, 2, 3] });
await queue.runDue(); // workers in an app: queue.work()

const { run: done, steps } = await pipelines.get(run.pk);
console.log(done.status, done.result);
console.log(Object.fromEntries(Object.entries(steps).map(([id, step]) => [id, step.status])));
done { links: 1.5, detail: 'skipped', user: 'ada' }
{ measure: 'done', links: 'done', detail: 'skipped', report: 'done' }

The document had under 1024 words, so detail was skipped and the join (report) got the outputs of the steps done: { links: 1.5 }. run.input is the input of the run, in every step.

Steps

KeyWhat it does
idIts name in the run (a string or a number).
blockThe block it runs (or run, a function, in code).
configAn object the block reads (ctx.config), checked by the block's validate.
afterThe steps it runs after: one (parent too) or a list. Its input is the run's input (none), the output of the step (one), or the outputs by step (a join).
whenAn expression of @xufa/expression over input, outputs, run and config (or a function, in code). False: the step is skipped; a step after only skipped steps is skipped too, and a join runs with the steps done.
resultIts output is part of the result of the run (merged when objects). Without any, the result is the output of the last step (the outputs by step when several end the run).
attempts, priority, queueOf its job.
waitTimeout, onTimeoutHow long it can be paused ('24h'), and then: 'fail' (its run fails: the default), 'skip' (its branch is skipped) or { output } (it goes on with that output: an approval by default).

pipelines.check(definition) gives every error of a definition (blocks that are not there, steps after steps that are not there, cycles, conditions that do not parse, ids twice, configs a block refuses), and define() throws a PipelineError with all of them (err.errors). A run keeps the definition it started with: changing a pipeline does not change the runs on their way.

Blocks

pipelines.block('extract', {
  // Its jobs' options: attempts, backoff, timeout, queue, and a pool of nodes of @xufa/cluster.
  pool: usePool('converters'),
  timeout: '2m',
  attempts: 3,
  validate: (config) => (typeof config.format === 'string' ? undefined : 'config.format is the format to convert to'),
  run: async (doc, { config, node, signal, outputs, run, step, attempt }) => convert(node.url, config.format, doc, { signal }),
});

run(input, ctx) gives the step's output (kept as JSON). ctx has its config, the outputs of the steps done, the run (id, pipeline, input), the job, its signal (aborted at the timeout), the node of its pool and its attempt. Two blocks are built in:

  • transform: the values of expressions, config.map ({ key: expression }, an object) or config.value (one value).
  • wait: the step is paused until pipelines.resume(runId, stepId, output): an approval, the callback of another system. Any block can give ctx.wait() to do the same after starting something, and ctx.wait({ timeout, onTimeout }) with a time limit of its own. The end of the wait is a job of the queue (its time in pausedUntil of the step): it holds when processes restart, and does nothing when the step was resumed.
  • pipeline: the step runs another pipeline, config.pipeline, with its input (or config.input, an expression over input, outputs, run and config), and waits for it as a paused step: the result of that run is its output. A child run that fails, or is cancelled, fails the step and its run (the error says which run); the step's waitTimeout holds, and cancels the child when it ends the wait; cancelling a run cancels its children. A child run knows its parent, parentStep and depth, and the step its child; pipelines that start pipelines go maxDepth deep at most (10, an option of Pipelines), so a cycle stops.
pipelines.define({
  name: 'publish',
  steps: [
    { id: 'document', block: 'fetch' },
    // Another pipeline for the text, waited for (an hour at most), with an input of its own.
    { id: 'translated', block: 'pipeline', after: 'document', config: { pipeline: 'translate', input: '{ text: input.text, to: "es" }' }, waitTimeout: '1h' },
    { id: 'site', block: 'upload', after: 'translated' },
  ],
});

Code can define steps with functions instead of blocks (the run keeps the rest as data):

pipelines.define({
  name: 'welcome',
  steps: [
    { id: 'user', run: ({ userId }) => User.objects.get({ pk: userId }).then((user) => user.toJSON()) },
    { id: 'mail', after: 'user', when: (user) => user.newsletter, run: (user) => Email.objects.create(welcomeOf(user)) },
  ],
});

Runs

  • start(name, input, { key }) starts a run (a running run with the same key is given instead); trigger(event, input) starts one of every pipeline with that trigger.
  • get(runId) gives the run and its steps by id; pipelines.runs is the queryset of the runs (pipelines.runs.filter({ status: 'failed' })).
  • A run is running, done, failed or cancelled; a step waiting, queued, running, retrying, paused, done, skipped, failed or cancelled.
  • concurrency: n in a pipeline: at most n steps of each run queued or running at once, among every worker (a counter of the run, inFlight, taken and given back with updates only one process can make); paused steps do not count. Other runs have their own.
  • A step that fails is tried again after its backoff, up to its attempts; then the step and its run are failed, with the error. retry(runId) makes it go on from the steps that failed (those done are not run again); cancel(runId) stops it.
  • Events: started, step (run, step, status), completed and failed (run, error, step).

The steps of a run go to every worker of every machine with the database. Every change of a step or a run is an update made from the status it expects, so two branches that end at once do not overwrite each other, and a step whose job runs twice (taken back after its worker died) runs once. A process that stops between a step and the next leaves its run to the jobs taken back, or to pipelines.recover().
